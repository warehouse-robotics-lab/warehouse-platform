## Журнал согласований

- **Решения, принятые при подготовке change (2026-11-17), устно, до ревью:**
  - способ сессии — серверная сессия в Redis и непрозрачная httpOnly-cookie;
  - срок жизни — абсолютный, задаётся конфигурацией (по умолчанию 7 суток), продление
    при активности в пределах срока;
  - контракт — Zod-схемы в `@warehouse/contracts` плюс Swagger, ts-rest/tRPC не
    вводится;
  - формат ошибки — `code`, `message`, необязательное `fields`; `httpStatus` в теле не
    дублируется;
  - вход — единый ответ `401 INVALID_CREDENTIALS` без `fields` для любой причины;
    регистрация — раскрывает проблемное поле и код нарушения (`409` и `fields`);
  - адреса — `/auth/register`, `/auth/login`, `/auth/logout`, `/users/current`;
  - хеширование — argon2id;
  - требования к паролю — 8–36 символов, цифра, заглавная и строчная буквы, спецсимвол;
    имя — 2–64 символа;
  - защита от перебора — лимит на пару `email` и IP, отдельным change после входа;
  - сроки, пороги и параметры хеширования — переменными окружения со значениями
    по умолчанию из `design.md`.
  Письменного подтверждения Стаса по этим пунктам пока нет — см. 1.4.
- **Спецификация.** Ожидается: Полина и Дмитрий проверяют документ друг друга, затем
  Стас согласует спецификацию с указанием ревизии. Запись появится после 1.2–1.4.
- **Поля, ошибки и коды.** Ожидается согласование с Юрой и Таней: 1.4.
- **Расхождение с `login-form` (PR #34).** Зафиксировано 2026-11-17: клиентская проверка
  правил пароля в спецификации формы отсутствует, текст для `TOO_MANY_ATTEMPTS` не
  задан. Правки — F2 и F4, до подключения Web к API.
- **Доверие прокси и источник IP клиента.** Решение отложено до реализации; определить
  в B1, от него зависит корректность счётчика неудачных попыток.
