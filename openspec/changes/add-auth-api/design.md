# Design

## Context

Текущее состояние, важное для решения:

- В `apps/api` есть Prisma-модель `User` и `PrismaService`; отдельного слоя аутентификации,
  HTTP-модулей пользователей и клиента Redis нет. `main.ts` не настраивает валидацию
  входных данных, обработку ошибок и CORS.
- В `packages/contracts` нет ни схем, ни сборки: пакет — заглушка, выбор контрактной
  библиотеки (ts-rest/tRPC) не сделан ([packages/contracts/README.md](../../../../packages/contracts/README.md)).
- В `apps/web` есть страница входа с базовой разметкой (PR #31). Поведение формы описано
  в Draft PR #34 (ветка `docs/login-form-behavior`, capability `login-form`): проверка
  полей, тексты ошибок, состояние ожидания, локальный тестовый обработчик.
  Там же зафиксировано, что ограничения длины и сложности пароля вводятся отдельным
  согласованием.
- ADR-003 (Accepted) предполагает несколько процессов API, обмен через Redis и BullMQ и
  проверку прав доступа на HTTP-запросах. Redis в стеке есть, но в локальном Compose
  сейчас только PostgreSQL.
- В ТЗ проекта перечислены Swagger, Redis и библиотека хеширования не названы;
  `argon2` в `apps/api` не подключён.

Порядок работы — ADR-002 (Accepted): спецификация → человеческое ревью → тесты и их
ревью → реализация. Этот change — spec-first: он договаривается о поведении, а
реализация разбивается на небольшие сценарии в связанной задаче.

## Goals / Non-Goals

**Goals:**

- Один согласованный внешний контракт для регистрации, входа, выхода и получения
  текущего пользователя, пригодный для подключения формы Web без догадок.
- Способ сессии, который работает на нескольких процессах API, допускает мгновенный
  выход и не требует новой контрактной библиотеки.
- Разделение ответственности: хеширование и проверка пароля — вне операции сохранения
  из `user-account`, которая по-прежнему получает готовый хеш.
- Единый механизм ошибок и единый способ защиты закрытых маршрутов, переиспользуемые
  в следующих сценариях API.
- Настраиваемые без правки кода сроки жизни сессии, cookie и параметры защиты от перебора.

**Non-Goals:**

- Роли, склады, приглашения, права доступа к складам — следующий этап.
- OAuth, Telegram-привязка, восстановление пароля по почте, смена пароля.
- Токены для нативных мобильных клиентов, refresh-токены, хранение токена в
  localStorage. Мобильный клиент — отдельная задача со своим транспортом сессии.
- Защита складов и проверка прав доступа из ADR-003 — она описывает доступ к складам,
  а не аутентификацию.
- Изменение схемы данных пользователя: `user-account` и модель `User` не меняются.
- Выбор контрактной библиотеки (ts-rest/tRPC) — остаётся открытым.
- Кэш-контроль и HTTP-кэширование ответов аутентификации.

## Decisions

### 1. Сессия в Redis и непрозрачная cookie

Сессия хранится на сервере в Redis по ключу с криптографически стойким идентификатором,
клиент получает cookie с этим идентификатором.

Альтернативы: JWT access + refresh в httpOnly cookie и полностью stateless JWT в cookie.
Обе требуют новой библиотеки и переноса доверия на клиента: при stateless JWT выход
означает только забвение токена на стороне клиента, а отзыв доступа пользователя до
истечения срока невозможен — это расходится с требованием «при отзыве доступа прекращать
работу» из ADR-003. Refresh-подход переносит решение о том, где Web хранит access-токен,
в отдельную задачу и заранее создаёт два способа аутентификации.

Выбранный вариант использует Redis, который уже есть в стеке, не добавляет контрактных
библиотек, даёт мгновенный выход и отзыв на любом процессе API. Для нативного мобильного
клиента cookie подходит, если клиент умеет хранить cookie-jar (например, OkHttp с
persistent cookie store); отдельный токен-транспорт для мобильных — вне этой задачи.

### 2. Срок жизни: абсолютный предел из конфигурации и продление в его пределах

Сессия получает абсолютный срок с момента создания, заданный переменной окружения
`SESSION_TTL_SECONDS` (по умолчанию 7 суток). Каждый авторизованный запрос продлевает
время жизни записи в Redis, но не дальше абсолютного срока: TTL записи равен остатку до
абсолютного срока. Отдельного idle-таймаута меньшего срока нет — решение усложняет
объяснение поведения пользователю, а абсолютный предел закрывает риск вечной сессии.

Альтернатива: скользящий срок без абсолютного предела (сессия живёт, пока пользователь
активен) — отклонена: она не даёт верхней границы.

### 3. Контракт: Zod-схемы в `@warehouse/contracts` + Swagger

Схемы запросов, ответов и ошибок живут в `packages/contracts` на Zod и переиспользуются
Web и API. ts-rest/tRPC в этом change не вводится: выбор не сделан, а контрактная
библиотека — новая зависимость, которую по условию задачи нельзя добавлять без
согласования. Чтобы изменения контракта ломали сборку обоих приложений, пакет
экспортирует типы и схемы, а Web и API зависят от него через `workspace:*`.

Swagger (в ТЗ проекта) становится живой документацией: схемы в OpenAPI собираются из
тех же Zod-схем встроенным преобразованием Zod 4 (`z.toJSONSchema`), без отдельной
библиотеки конвертации. Ручное описание DTO-классов в NestJS не дублируется.

### 4. Формат ошибки: `code`, `message`, `fields`

Тело ошибки — `{ "code", "message", "fields"? }`. HTTP-статус передаётся статусом ответа
и в теле не дублируется: одно поле — один источник истины, а дублирование расходится
при копировании ответа и усложняет генерацию клиента.

Альтернатива: RFC 9457 `application/problem+json` — подходит внешним потребителям, но
для формы нужны коды ошибок полей, которые всё равно задаются расширением; выбранный
формат проще для Web и ближе к тому, что уже описано в `login-form`.

Коды ошибок — стабильные машинные значения (`EMAIL_INVALID`, `PASSWORD_WEAK`,
`EMAIL_ALREADY_TAKEN`, `INVALID_CREDENTIALS`, `UNAUTHENTICATED`, `TOO_MANY_ATTEMPTS`).
Поле `fields` используется для ошибок формата и правил входных данных: оно указывает,
какое поле нарушило какое правило. Поле `fields` не используется для ошибок
аутентификации — там неизвестно, какое поле «виновато», и это скрывается намеренно
(решение 5). Тексты `message` — человекочитаемые, без технических подробностей.
Отображение текста в интерфейсе остаётся за Web: `login-form` уже фиксирует русские
формулировки («Неверная почта или пароль»), API не должен подменять их.

### 5. Вход и регистрация: разная степень раскрытия

Вход и регистрация решают разные задачи, поэтому степень раскрытия при отказе у них
разная.

**Вход.** Любой отказ аутентификации даёт один ответ: `401`, код `INVALID_CREDENTIALS`,
сообщение «Неверная почта или пароль», без `fields`. Одинаково для несуществующего email,
неверного пароля и временной блокировки входа. Здесь скрытность бесплатна: человек
знает свой адрес, ему достаточно общего отказа, а по ответу нельзя перебором узнать,
какие адреса зарегистрированы.

**Регистрация.** Отказ раскрывает проблемное поле и код нарушения: занятый email —
`409` и `EMAIL_ALREADY_TAKEN` в `fields.email`, нарушение правил формата или пароля —
`400` с кодами в `fields`. Здесь скрытность вредит: человек вводит адрес, нажимает
«Зарегистрироваться» и получает отказ без деталей — что исправлять, непонятно.
Перечисление при регистрации частично неизбежно: тот, кто пытается зарегистрировать
чужой адрес, узнает, что он уже занят. Поэтому раскрытие ограничено рамками задачи:
сервер сообщает только о поле и нарушении, и не сообщает никаких других сведений о
существующем пользователе — ни его имени, ни даты регистрации, ни числа попыток.

Альтернатива для обоих случаев — единый обезличенный отказ везде. Отклонена для
регистрации: нечитаемый UX без практической выгоды, потому что скрывать сам факт
занятости всё равно нельзя.

Отдельно: клиент проверяет правила до отправки по тем же Zod-схемам, что и сервер,
поэтому чаще всего точная ошибка приходит от клиента, а сервер выступает страховкой
для обхода клиентской проверки.

Правила проверки при этом не размываются: `user-credentials` задаёт однозначные коды
нарушений (`PASSWORD_TOO_SHORT`, `EMAIL_INVALID` и другие), одинаковые у Web и API.
Наружу отдаётся только общий отказ.

### 6. Пароль: argon2id, требования отдельно от хранения

Хеширование и проверка живут в сервисе аутентификации (`user-credentials`), а операция
сохранения из `user-account` по-прежнему получает готовый хеш и ничего о пароле не знает.
Алгоритм — argon2id с параметрами `m=19456 KiB, t=2, p=1` (рекомендация OWASP):
memory-hard, устойчив к аппаратному подбору, без ограничения в 72 байта, как у bcrypt.
bcrypt отклонён из-за 72-байтового предела и слабой стойкости к GPU; `scrypt` из
`node:crypto` не требует зависимости, но требует собственной реализации кодирования и
настройки параметров.

Требования к паролю: 8–36 символов, хотя бы одна цифра, одна заглавная и одна строчная
буквы, один специальный символ (любой не буква и не цифра, кроме пробела). Пароль не
обрезается и не изменяется — это правило `login-form`, и API сохраняет его, чтобы вход
по сохранённому хешу совпадал с тем, что вводит пользователь.

Параметры хеширования задаются переменными окружения. Если они изменятся, старые хеши
останутся проверяемыми (параметры хранятся внутри хеша), а при успешном входе система
перезапишет хеш новыми параметрами — перехеширование без принудительного сброса паролей.

### 7. Защита от перебора: счётчик в Redis по паре `email` + IP

Счётчик неудачных попыток хранится в Redis по ключу пары «почта + IP». Порог, окно
подсчёта и срок блокировки задаются переменными окружения (`AUTH_LOGIN_MAX_ATTEMPTS`,
`AUTH_LOGIN_WINDOW_SECONDS`, `AUTH_LOGIN_BLOCK_SECONDS`; по умолчанию 5 попыток, 15 минут
и 15 минут). Успешный вход сбрасывает счётчик. Счётчик по паре, а не только по IP: один IP
за NAT не должен блокировать других пользователей, а разные IP против одной почты
ограничиваются числом аккаунтов на одной почте.

Альтернатива: ограничение только по IP проще, но не защищает от распределённого перебора
одной учётной записи. Ограничение только по почте защищает, но наказывает жертву чужой
атаки; пара сочетает обе стороны.

### 8. Адреса: действия аутентификации и ресурс текущего пользователя

`POST /auth/register`, `POST /auth/login`, `POST /auth/logout` — действия аутентификации,
живут под `/auth`. `GET /users/current` — ресурс текущего пользователя, доступен и
другим частям API (кабинет, профиль), поэтому вынесен в `/users`.

Альтернатива: держать всё под `/auth` (`GET /auth/me`) — короче, но смешивает действия и
данные и оставляет `/users` без назначения, когда появится профиль и настройки. Разделение
`/auth/*` и `/users/*` даёт место для будущих адресов пользователей без изменения
существующих.

Объект пользователя в ответах: `uuid`, `email`, `name`, `createdAt`. Поле `password`
не возвращается никогда.

### 9. Механизм ошибок NestJS, переиспользуемый дальше

В `apps/api` вводится собственный слой ошибок вместо разрозненных `HttpException`:

- базовый класс исключения с кодом, сообщением, HTTP-статусом и необязательными полями
  (`fields`) — единственное место, где решается, чем ошибка выглядит наружу;
- конкретные исключения домена: отказ регистрации, неверные учётные данные,
  неавторизованный запрос, превышенное число попыток, некорректный запрос;
- глобальный фильтр исключений, который превращает любое исключение в единое тело
  `{ "code", "message", "fields"? }`: доменные исключения — в их код и статус, ошибки
  валидации — в `400` с кодами нарушений по полям, неизвестные ошибки — в
  `500 INTERNAL_ERROR` без технических деталей (подробности уходят в журнал);
- тонкий слой валидации входных данных на Zod: штатный `ValidationPipe` NestJS о Zod
  не знает, поэтому используется собственная проверка схемой пакета контрактов;
  для маршрутов аутентификации ошибка проверки сводится к общему отказу (решение 5).

Фильтр и слой ошибок не относятся к аутентификации и используются всеми следующими
модулями API (склады, задания, права доступа).

### 10. Guard и декораторы для закрытых маршрутов

Авторизация закрытых маршрутов — один глобальный guard, подключённый как `APP_GUARD`:
он читает cookie сессии, проверяет сессию в Redis и кладёт пользователя в запрос.
Открытые маршруты помечаются декоратором `@Public()` — guard их пропускает. Данные
текущего пользователя в обработчике получаются параметр-декоратором `@CurrentUser()`.

Альтернатива: проверка сессии в каждом контроллере руками — быстрее сделать, но
рано или поздно закрытый маршрут останется без проверки; глобальный guard с явным
исключением `@Public()` делает защиту «по умолчанию включённой».

Ответ guard — тот же единый формат ошибки с кодом `UNAUTHENTICATED` и статусом `401`.
Роли и права на склады guard не проверяет: это следующий этап (ADR-003).

### 11. Параметры окружения

Сроки и пороги задаются переменными окружения, чтобы их можно было менять без правки
кода и в разных средах. Имена — в верхнем регистре, по образцу существующих `PORT`,
`DATABASE_URL`. Значения проверяются Zod-схемой окружения: некорректное значение
останавливает запуск API, как это уже происходит для `PORT` и `DATABASE_URL`.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `REDIS_URL` | `redis://localhost:6379` | Redis: сессии и счётчики попыток |
| `SESSION_TTL_SECONDS` | `604800` | Абсолютный срок жизни сессии (7 суток) |
| `SESSION_COOKIE_NAME` | `warehouse_session` | Имя cookie сессии |
| `SESSION_COOKIE_PATH` | `/` | Путь cookie |
| `SESSION_COOKIE_SAME_SITE` | `lax` | Политика `SameSite` |
| `SESSION_COOKIE_SECURE` | `true` | Признак `Secure`; в локальной разработке `false` |
| `SESSION_COOKIE_DOMAIN` | — | Домен cookie; в продакшене — домен приложения |
| `AUTH_LOGIN_MAX_ATTEMPTS` | `5` | Порог неудачных попыток входа |
| `AUTH_LOGIN_WINDOW_SECONDS` | `900` | Окно подсчёта неудачных попыток |
| `AUTH_LOGIN_BLOCK_SECONDS` | `900` | Длительность блокировки входа |
| `PASSWORD_ARGON2_MEMORY_KIB` | `19456` | Параметр `memoryCost` argon2id |
| `PASSWORD_ARGON2_TIME_COST` | `2` | Параметр `timeCost` argon2id |
| `PASSWORD_ARGON2_PARALLELISM` | `1` | Параметр `parallelism` argon2id |

Значения по умолчанию описаны здесь как точки старта; конкретные числа для продакшена
уточняются при настройке развёртывания. Требования спецификаций описывают поведение
через конфигурацию и не фиксируют числа: правила полей (длина пароля, email и имени) —
продуктовые решения и остаются числами, они переменными окружения не выносятся.

### 12. Cookie и CORS

Cookie: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` в продакшене, `Max-Age` равен
остатку абсолютного срока сессии.

Web и API работают на разных источниках (3000 и 3001), поэтому API настраивает CORS с
явным списком доверенных источников и `credentials: true`; запросы с credentials требуют
точного origin, а не `*`. Список источников — тоже переменная окружения.

### 13. Скрытие пароля и равное время ответа

В журналы не попадают исходный пароль, хеш и идентификатор сессии. При входе на
несуществующий email система выполняет фиктивную проверку хеша, чтобы время ответа не
отличалось от ответа при неверном пароле и по времени нельзя было перечислить
существующие учётные записи.

## Risks / Trade-offs

- [Ошибки входа не различают причину, поэтому пользователь с неверным паролем не может
  понять, верна ли его почта] → это осознанный выбор: единый ответ «Неверная почта или
  пароль» защищает от перебора зарегистрированных адресов.
- [Регистрация раскрывает, что адрес уже занят] → перечисление при регистрации
  частично неизбежно; раскрытие ограничено полем и кодом нарушения, других сведений о
  существующем пользователе сервер не отдаёт; лимит попыток ограничивает перебор.
- [Поле `fields` заполняется только для ошибок формата] → ошибки аутентификации идут
  без `fields`; Web показывает общий текст в общей области под полями.
- [Cookie-сессия не подходит мобильным клиентам без cookie-jar] → мобильный транспорт
  выносится в отдельную задачу; для него понадобится либо cookie-jar в клиенте, либо
  новый способ выдачи сессии, а не изменение текущего контракта.
- [Redis стал обязательной зависимостью API для входа] → локальный Compose дополняется
  сервисом Redis; проверка доступности Redis при старте и понятная ошибка при его
  недоступности описаны в задачах реализации.
- [Сессия в памяти процесса недопустима при нескольких процессах API] → хранение только
  в Redis, это же проверяется тестом на двух экземплярах.
- [Тексты ошибок живут в Web, а коды — в API] → расхождение текста и кода возможно;
  митигация: коды перечислены в контракте, а `login-form` фиксирует тексты по кодам,
  изменение текста требует изменения спецификации `login-form`.
- [Правила пароля (8–36 символов, цифра, регистр, спецсимвол) расходятся с текущей
  `login-form`, где ограничения только «вводятся отдельным согласованием»] → расхождение
  зафиксировано: до подключения Web к API спецификация `login-form` обновляется
  (проверка пароля на клиенте, тексты ошибок поля, код `TOO_MANY_ATTEMPTS`), иначе формы
  и API будут показывать разные ошибки об одном и том же.
- [Смена параметров argon2id через окружение требует перехеширования] → перехеширование
  выполняется при успешном входе; при смене параметров старые пароли продолжают работать
  до первого входа.
- [Глобальный guard требует явного `@Public()` для каждого открытого маршрута] → забытый
  `@Public()` закрывает маршрут, а не открывает лишний; это безопасный порядок ошибки.

## Migration Plan

Данные не мигрируют: схема `User` не меняется, пользователей в базе нет.
Разворачивание — добавление переменных окружения и сервиса Redis; откат — откат
контейнера API, записи сессий в Redis живут не дольше абсолютного срока и удаляются сами.

## Open Questions

- Параметры защиты от перебора (5 попыток, окно и блокировка 15 минут), срок жизни
  сессии (7 суток), имя cookie и отсутствие `httpStatus` в теле ошибки — подтвердить
  у Стаса вместе с решением по сессии; при изменении правятся спецификации `auth-api`
  и `user-session`.
- Тексты сообщений Web для кодов (`TOO_MANY_ATTEMPTS`, `EMAIL_ALREADY_TAKEN`, нарушения
  правил пароля) — согласовать с Таней в рамках обновления `login-form`.
- Клиентская проверка правил до отправки выносится в отдельную задачу: `login-form`
  сейчас проверяет только обязательность и формат почты, а проверка пароля по общим
  Zod-схемам ещё не описана.
- Регистрация раскрывает занятость адреса — подтвердить у Юры и Таней, что такой
  уровень раскрытия приемлем для продукта.
- Форма регистрации в Web ещё не существует: нужен ли для неё отдельный текст ошибки,
  отличный от текста входа, — определить вместе с формой регистрации.
- Список доверенных источников CORS и домен cookie — вынести в конфигурацию API с
  примером в `.env.example`; конкретные значения зависят от среды разработки и
  продакшена.
