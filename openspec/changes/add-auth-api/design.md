# Design

## Context

Текущее состояние, важное для решения:

- В `apps/api` есть Prisma-модель `User` и `PrismaService`; отдельного слоя аутентификации,
  HTTP-модулей пользователей и клиента Redis нет. `main.ts` не настраивает валидацию
  входных данных, обработку ошибок и CORS.
- В `packages/contracts` нет ни схем, ни сборки: пакет — заглушка, выбор контрактной
  библиотеки (ts-rest/tRPC) не сделан ([packages/contracts/README.md](../../../packages/contracts/README.md)).
- В `apps/web` есть страница входа с базовой разметкой (PR #31). Поведение формы описано
  в Draft PR #34 (ветка `docs/login-form-behavior`, capability `login-form`), которая ещё
  не слита: текущий текст спецификации формы — источник истины только после слияния, а
  расхождения с этим change зафиксированы в журнале согласований. Там же зафиксировано,
  что ограничения длины и сложности пароля вводятся отдельным согласованием.
- ADR-003 (Accepted) предполагает несколько процессов API, обмен через Redis и BullMQ и
  проверку прав доступа на HTTP-запросах. Redis в стеке есть, но в локальном Compose
  сейчас только PostgreSQL.
- В ТЗ проекта перечислены Swagger, Redis и библиотека хеширования не названы;
  `argon2` в `apps/api` не подключён.

Порядок работы — ADR-002 (Accepted): спецификация → человеческое ревью → тесты и их
ревью → реализация. Этот change — spec-first: он договаривается о поведении, а
реализация разбивается на небольшие сценарии в связанной задаче.

## Goals / Non-Goals

**Goals:**

- Один согласованный внешний контракт для регистрации, входа, выхода и получения
  текущего пользователя, пригодный для подключения формы Web без догадок.
- Способ сессии, который работает на нескольких процессах API, допускает мгновенный
  выход и не требует новой контрактной библиотеки.
- Разделение ответственности: хеширование и проверка пароля — вне операции сохранения
  из `user-account`, которая по-прежнему получает готовый хеш.
- Единый механизм ошибок и единый способ защиты закрытых маршрутов, переиспользуемые
  в следующих сценариях API.
- Настраиваемые без правки кода сроки жизни сессии, cookie и параметры защиты от перебора.

**Non-Goals:**

- Роли, склады, приглашения, права доступа к складам — следующий этап.
- OAuth, Telegram-привязка, восстановление пароля по почте, смена пароля.
- Токены для нативных мобильных клиентов, refresh-токены, хранение токена в
  localStorage. Мобильный клиент — отдельная задача со своим транспортом сессии.
- Защита складов и проверка прав доступа из ADR-003 — она описывает доступ к складам,
  а не аутентификацию.
- Изменение схемы данных пользователя: `user-account` и модель `User` не меняются.
- Выбор контрактной библиотеки (ts-rest/tRPC) — остаётся открытым.
- Кэш-контроль и HTTP-кэширование ответов аутентификации.

## Decisions

### 1. Сессия в Redis и непрозрачная cookie

Сессия хранится на сервере в Redis по ключу с криптографически стойким идентификатором,
клиент получает cookie с этим идентификатором.

Альтернативы: JWT access + refresh в httpOnly cookie и полностью stateless JWT в cookie.
Обе требуют новой библиотеки и переноса доверия на клиента: при stateless JWT выход
означает только забвение токена на стороне клиента, а отзыв доступа пользователя до
истечения срока невозможен — это расходится с требованием «при отзыве доступа прекращать
работу» из ADR-003. Refresh-подход переносит решение о том, где Web хранит access-токен,
в отдельную задачу и заранее создаёт два способа аутентификации.

Выбранный вариант использует Redis, который уже есть в стеке, не добавляет контрактных
библиотек, даёт мгновенный выход и отзыв на любом процессе API. Для нативного мобильного
клиента cookie подходит, если клиент умеет хранить cookie-jar (например, OkHttp с
persistent cookie store); отдельный токен-транспорт для мобильных — вне этой задачи.

### 2. Сроки жизни: неактивность и абсолютный предел

У сессии два срока, оба из конфигурации. `SESSION_IDLE_SECONDS` (по умолчанию 24 часа) —
срок неактивности: авторизованный запрос продлевает его. `SESSION_TTL_SECONDS`
(по умолчанию 7 суток) — абсолютный срок от момента создания, который активность не
меняет. Сессия прекращается при истечении любого из сроков.

Один срок без другого плохо объясняется пользователю: «продление» без абсолютного
предела даёт вечную сессию, а абсолютный срок без idle-таймаута выбрасывает
пользователя посреди работы. Пара «неактивность + абсолютный предел» покрывает оба
случая и позволяет настроить оба независимо.

Альтернатива: скользящий срок без абсолютного предела (сессия живёт, пока пользователь
активен) — отклонена: она не даёт верхней границы.

### 3. Контракт: Zod-схемы в `@warehouse/contracts` + Swagger

Схемы запросов, ответов и ошибок живут в `packages/contracts` на Zod и переиспользуются
Web и API. Пакет ещё не создан: в `packages/contracts` пока только README, а сам пакет
появляется первым change в плане реализации. ts-rest/tRPC в этом change не вводится:
выбор не сделан, а контрактная библиотека — новая зависимость, которую по условию задачи
нельзя добавлять без согласования. Чтобы изменения контракта ломали сборку обоих
приложений, пакет экспортирует типы и схемы, а Web и API зависят от него через
`workspace:*`.

Swagger (в ТЗ проекта) становится живой документацией: схемы в OpenAPI собираются из
тех же Zod-схем встроенным преобразованием Zod 4 (`z.toJSONSchema`), без отдельной
библиотеки конвертации. Ручное описание DTO-классов в NestJS не дублируется.

### 4. Формат ошибки: `code`, `message`, `fields`

Тело ошибки — `{ "code", "message", "fields"? }`. HTTP-статус передаётся статусом ответа
и в теле не дублируется: одно поле — один источник истины, а дублирование расходится
при копировании ответа и усложняет генерацию клиента.

Альтернатива: RFC 9457 `application/problem+json` — подходит внешним потребителям, но
для формы нужны коды ошибок полей, которые всё равно задаются расширением; выбранный
формат проще для Web и ближе к тому, что уже описано в `login-form`.

`fields` — объект «поле → массив кодов нарушений». Массив, а не одиночный код: одно
поле может нарушать несколько правил одновременно (пароль короче минимума и без
нужных символов), и клиенту полезно знать все нарушения, а не только первое.

Справочник кодов ошибок и сообщений. Код — источник истины, сообщение — часть контракта;
клиент может показывать свою формулировку, опираясь на код.

| Код | Статус | Сообщение | Назначение |
| --- | --- | --- | --- |
| `INVALID_REQUEST` | 400 | Некорректный запрос | тело не JSON-объект, неверный тип содержимого, лишние или неверно типизированные поля |
| `VALIDATION_FAILED` | 400 | Проверьте поля формы | поля не проходят правила; в `fields` — коды нарушений |
| `EMAIL_ALREADY_TAKEN` | 409 | Адрес уже зарегистрирован | адрес занят (регистрация) |
| `INVALID_CREDENTIALS` | 401 | Неверная почта или пароль | неверные учётные данные (вход) |
| `UNAUTHENTICATED` | 401 | Требуется вход | нет действующей сессии |
| `CSRF_REJECTED` | 403 | Источник запроса недопустим | изменяющий запрос с недоверенного источника |
| `TOO_MANY_ATTEMPTS` | 429 | Слишком много попыток. Повторите позже. | превышен лимит пары `email` + IP |
| `EMAIL_RATE_LIMITED` | 429 | Слишком много попыток. Повторите позже. | превышен лимит попыток по адресу почты |
| `REGISTRATION_RATE_LIMITED` | 429 | Слишком много попыток. Повторите позже. | превышен лимит регистраций с IP |
| `ROUTE_NOT_FOUND` | 404 | Маршрут не найден | неизвестный маршрут |
| `METHOD_NOT_ALLOWED` | 405 | Метод не поддерживается | неподдерживаемый метод; в ответе заголовок `Allow` |
| `SERVICE_UNAVAILABLE` | 503 | Сервис временно недоступен. Повторите позже. | Redis недоступен: сессию или счётчик не прочитать, не создать, не удалить |
| `INTERNAL_ERROR` | 500 | Внутренняя ошибка сервера | непредвиденная ошибка, без технических деталей |

Коды нарушений полей, которые передаются в `fields`: `REQUIRED`, `EMAIL_INVALID`,
`PASSWORD_TOO_SHORT`, `PASSWORD_TOO_LONG`, `PASSWORD_WEAK`, `NAME_TOO_SHORT`,
`NAME_TOO_LONG`.

Поле `fields` используется для ошибок входных данных — включая конфликт занятости
адреса, который возвращается в `fields.email`. В ошибках аутентификации его нет: там
неизвестно, какое поле «виновато», и это скрывается намеренно (решение 5).

### 5. Вход и регистрация: разная степень раскрытия

Вход и регистрация решают разные задачи, поэтому степень раскрытия при отказе у них
разная. Что скрывает вход, что раскрывает регистрация и что общего у обоих адресов:

| Ситуация | Вход | Регистрация |
| --- | --- | --- |
| Неверный пароль | `401 INVALID_CREDENTIALS`, без `fields` | — |
| Неизвестный email | `401 INVALID_CREDENTIALS`, без `fields` | — |
| Email уже занят | — | `409 EMAIL_ALREADY_TAKEN` в `fields.email` |
| Нарушение правил поля | — | `400 VALIDATION_FAILED` с кодами в `fields` |
| Некорректное тело запроса | `400 INVALID_REQUEST` | `400 INVALID_REQUEST` |
| Превышение лимита попыток | `429` (`TOO_MANY_ATTEMPTS`, `EMAIL_RATE_LIMITED`) | `429 REGISTRATION_RATE_LIMITED` |

**Вход.** Любой отказ аутентификации даёт один ответ: `401`, код `INVALID_CREDENTIALS`,
сообщение «Неверная почта или пароль», без `fields`. Одинаково для несуществующего email
и неверного пароля. Здесь скрытность бесплатна: человек знает свой адрес, ему достаточно
общего отказа, а по ответу нельзя перебором узнать, какие адреса зарегистрированы.
Превышение лимита попыток — не ошибка аутентификации, а ответ о частоте попыток, поэтому
у него отдельный статус `429` и отдельный код; такой ответ не раскрывает, зарегистрирован
ли адрес, и не смешивается с `401`.

**Регистрация.** Отказ раскрывает проблемное поле и код нарушения. Здесь скрытность
вредит: человек вводит адрес, нажимает «Зарегистрироваться» и получает отказ без
деталей — что исправлять, непонятно. Перечисление при регистрации частично неизбежно:
тот, кто пытается зарегистрировать чужой адрес, узнает, что он уже занят. Поэтому
раскрытие ограничено рамками задачи: сервер сообщает только о поле и нарушении, и не
сообщает никаких других сведений о существующем пользователе — ни его имени, ни даты
регистрации, ни числа попыток.

Альтернатива для обоих случаев — единый обезличенный отказ везде. Отклонена для
регистрации: нечитаемый UX без практической выгоды, потому что скрывать сам факт
занятости всё равно нельзя.

Отдельно: клиент проверяет правила до отправки по тем же Zod-схемам, что и сервер,
поэтому чаще всего точная ошибка приходит от клиента, а сервер выступает страховкой
для обхода клиентской проверки.

Тексты ошибок — часть контракта: справочник кодов и сообщений приведён в решении 4.
Клиент может показывать собственные формулировки, опираясь на код, но API всегда
возвращает согласованный текст своего кода.

Правила проверки при этом не размываются: `user-credentials` задаёт однозначные коды
нарушений (`PASSWORD_TOO_SHORT`, `EMAIL_INVALID` и другие), одинаковые у Web и API.
Наружу отдаётся общий отказ только при отказе аутентификации; при регистрации нарушения
перечисляются по полям.

### 6. Пароль: argon2id, требования отдельно от хранения

Хеширование и проверка живут в сервисе аутентификации (`user-credentials`), а операция
сохранения из `user-account` по-прежнему получает готовый хеш и ничего о пароле не знает.
Алгоритм — argon2id с параметрами `m=19456 KiB, t=2, p=1` (рекомендация OWASP):
memory-hard, устойчив к аппаратному подбору, без ограничения в 72 байта, как у bcrypt.
bcrypt отклонён из-за 72-байтового предела и слабой стойкости к GPU; `scrypt` из
`node:crypto` не требует зависимости, но требует собственной реализации кодирования и
настройки параметров.

Требования к паролю: 8–36 символов в кодовых точках, хотя бы одна цифра, одна заглавная
и одна строчная буквы, один специальный символ. Буква — категория Unicode `L*`, цифра —
`Nd`, пробел — только `U+0020`, специальный символ — любой символ, кроме буквы, цифры и
пробела. Пароль не обрезается и не изменяется — это правило `login-form`, и API
сохраняет его, чтобы вход по сохранённому хешу совпадал с тем, что вводит пользователь.
Длина в кодовых точках, а не в байтах: иначе кириллический пароль из 20 букв не прошёл
бы ограничение в 36 «символов».

Правила длины и состава — это правила **создания** пароля, поэтому они применяются при
регистрации и смене пароля, но не при входе. При входе проверяются только наличие и
непустота пароля: иначе пользователь, зарегистрировавшийся со слабым паролем до
ужесточения правил, навсегда потерял бы доступ — восстановления пароля в проекте нет.
Это то же правило «не ломаем то, что работает у пользователя», что и запрет обрезать
пароль.

Адрес нормализуется по правилам `user-account` перед проверкой, поиском пользователя и
сохранением. Нормализация перед поиском обязательна: без неё вход по адресу в другом
регистре не нашёл бы пользователя.

Параметры хеширования задаются переменными окружения. Если они изменятся, старые хеши
останутся проверяемыми (параметры хранятся внутри хеша), а при успешном входе система
перезапишет хеш новыми параметрами — перехеширование без принудительного сброса паролей.

### 7. Защита от перебора: три лимита

Счётчики живут в Redis; счётчики входа считаются по нормализованному email, чтобы регистр
и пробелы не обходили счёт, а счётчик регистраций — по IP клиента. Три счётчика используют
разные ключи:

| Лимит | Ключ | Порог и ответ |
| --- | --- | --- |
| Попытки входа для пары | нормализованный email + IP | 5 за 5 минут, блокировка 60 секунд → `429 TOO_MANY_ATTEMPTS` + `Retry-After` |
| Попытки входа для адреса | нормализованный email | 20 за 5 минут, блокировка 60 секунд → `429 EMAIL_RATE_LIMITED` + `Retry-After` |
| Регистрации с IP | IP клиента | 10 запросов за 10 минут → `429 REGISTRATION_RATE_LIMITED` + `Retry-After` |

Пороги, окна и длительность блокировки задаются конфигурацией. Значения по умолчанию —
стартовые и настраиваемые, зафиксированы решением тимлида 2026-11-23. Для обоих лимитов
входа повторные запросы во время блокировки её не продлевают; после окончания блокировки
бюджет попыток обновляется. Блокировка не завершает действующие сессии. Механика окон,
блокировки и источник IP клиента — детали реализации B1 и B9.

Неудачной попыткой входа считается только отказ аутентификации (`401`). Ошибки формата и
тела (`400`) — это опечатка пользователя, а не перебор: они не учитываются и не блокируют
вход. Для регистрации, наоборот, учитывается каждый запрос с IP, включая `400`.

Порядок проверок на входе: маршрут и метод → источник запроса → валидация → блокировка
пары → лимит по адресу → проверка учётных данных. При превышении любого лимита учётные
данные не проверяются; если превышены оба, приоритет у блокировки пары.

Порядок проверок на регистрации: маршрут и метод → источник запроса → лимит регистраций
с IP → правила полей → занятость адреса. Поэтому при исчерпанном лимите запрос даёт
`429 REGISTRATION_RATE_LIMITED` независимо от тела, а при неисчерпанном лимите неверные
поля дают `400 VALIDATION_FAILED`.

Каждый счётчик ограничивает только свой ключ. Лимит по адресу не заменяет лимит пары и
не защищает от перебора разных адресов; лимит регистраций с IP не заменяет проверку
занятости адреса. При одновременном превышении блокировки пары и лимита по адресу
приоритет у `TOO_MANY_ATTEMPTS`.

Цена лимитов: лимит по email срабатывает независимо от IP, поэтому чужие попытки могут
кратковременно заблокировать вход владельцу адреса; лимит по IP затрагивает пользователей
за общим NAT. Это принятые компромиссы: пороги стартовые и настраиваемые.

### 7a. Защита изменяющих запросов от CSRF

Cookie сессии отправляется браузером сам, поэтому одного `SameSite=Lax` и CORS мало:
`SameSite` смотрит на site, а не на origin, и запрос с другого поддомена того же сайта
остаётся same-site и уносит cookie. Поэтому изменяющие методы (`POST`, `PUT`, `PATCH`,
`DELETE`) дополнительно проверяются по заголовку `Origin`, а при его отсутствии — по
`Referer`. Значение сверяется со списком доверенных источников; несовпадение источника,
значение `Origin: null` или отсутствие обоих заголовков дают `403 CSRF_REJECTED`.

Сравнение источника — точное: схема и хост приводятся к нижнему регистру, стандартный
порт схемы (`443` для `https`, `80` для `http`) считается равным отсутствию порта,
нестандартный порт учитывается явно; завершающий слэш и путь не учитываются. Элементы
списка задаются в формате `схема://хост[:порт]`, разделитель — запятая; для стандартного
порта его можно не указывать. Переменная обязательна и непуста: пустой список
останавливает запуск API. Проверка включена всегда; отдельного флага нет — локальная
разработка задаёт доверенный источник через `TRUSTED_ORIGINS`.

Проверка источника выполняется после определения маршрута и метода, но раньше проверки
входных данных, лимитов и сессии: неизвестный маршрут даёт `404`, а на известном адресе
недоверенный источник даёт `403` независимо от состояния тела, счётчиков и наличия
сессии.

Предварительный запрос `OPTIONS` не является изменяющим, но проверяется по тому же
списку источников: CORS с `credentials` не должен разрешать неизвестный origin. `OPTIONS`
к известному адресу с доверенного источника — `204` с разрешающими заголовками; с
недоверенного, с `Origin: null` или без `Origin` — `403 CSRF_REJECTED`; к неизвестному
адресу — `404 ROUTE_NOT_FOUND`.

Альтернативы: double-submit cookie с токеном в заголовке — работает и там, где Origin
нет, но добавляет вторую cookie и второй механизм; проверка только `SameSite=Strict`
ломает переходы по ссылкам с внешних сайтов и всё равно не покрывает other-site
поддомены.

Проверка выполняется для всех изменяющих запросов, включая регистрацию и вход: там
cookie сессии ещё нет, но браузер может приложить чужую cookie, а сам вход — тоже
изменяет состояние (создаёт сессию). Значение `Origin: null` (песочница iframe)
отклоняется.

Ограничение: нативные клиенты без `Origin` и `Referer` получают `403`, поэтому механизм
рассчитан на браузерный Web. Для мобильного клиента понадобится отдельная транспортная
договорённость — это отдельная задача, а не повод оставлять Web без защиты.

### 7b. Поведение при недоступности Redis

Redis входит в критический путь аутентификации, поэтому его недоступность описана явно:
создание, проверка и удаление сессии при сбое дают `503 SERVICE_UNAVAILABLE` без
технических подробностей. Ответ `503` означает, что исход операции может быть неизвестен:
операция могла выполниться, а подтверждение — потеряться. Распределённая транзакция здесь
не проектируется; повторная операция должна быть безопасной. Тот же принцип, что в
ADR-003: общая транзакция не нужна, при неопределённом результате — повтор.

- **Вход.** При сбое создания сессии cookie не устанавливается, повтор безопасен.
- **Регистрация.** Откат уже созданной записи не гарантируется. При повторной регистрации
  того же адреса возможен `409 EMAIL_ALREADY_TAKEN`; в этом случае клиент считает, что
  регистрация могла завершиться, и переходит ко входу.
- **Выход.** Cookie не сбрасывается; не утверждаем, что сессия обязательно осталась
  активной. Операция идемпотентна: повтор безопасен, даже если сессия уже удалена.
- **Счётчики.** Сбой чтения или записи счётчика лимита даёт `503`; для входа при сбое
  записи неудачной попытки пароль уже проверен, сессия не создаётся. Сбой сброса после
  успеха успех не отменяет; ошибки идут в журнал.

Альтернатива: `500 INTERNAL_ERROR` — хуже для клиента, которому нужно понять, что
повторять.

### 8. Адреса: действия аутентификации и ресурс текущего пользователя

`POST /auth/register`, `POST /auth/login`, `POST /auth/logout` — действия аутентификации,
живут под `/auth`. `GET /users/current` — ресурс текущего пользователя, доступен и
другим частям API (кабинет, профиль), поэтому вынесен в `/users`.

Альтернатива: держать всё под `/auth` (`GET /auth/me`) — короче, но смешивает действия и
данные и оставляет `/users` без назначения, когда появится профиль и настройки. Разделение
`/auth/*` и `/users/*` даёт место для будущих адресов пользователей без изменения
существующих.

Объект пользователя в ответах: `uuid`, `email`, `name`, `createdAt`. Поле `password`
не возвращается никогда.

### 9. Механизм ошибок NestJS, переиспользуемый дальше

В `apps/api` вводится собственный слой ошибок вместо разрозненных `HttpException`:

- базовый класс исключения с кодом, сообщением, HTTP-статусом и необязательными полями
  (`fields`) — единственное место, где решается, чем ошибка выглядит наружу;
- конкретные исключения домена: отказ регистрации, неверные учётные данные,
  неавторизованный запрос, превышение лимита попыток, недоверенный источник,
  недоступность Redis, некорректный запрос;
- глобальный фильтр исключений, который превращает любое исключение в единое тело
  `{ "code", "message", "fields"? }`: доменные исключения — в их код и статус, ошибки
  валидации — в `400 VALIDATION_FAILED` с кодами нарушений по полям, неизвестные ошибки
  — в `500 INTERNAL_ERROR` без технических деталей (подробности уходят в журнал);
- тонкий слой валидации входных данных на Zod: штатный `ValidationPipe` NestJS о Zod
  не знает, поэтому используется собственная проверка схемой пакета контрактов;
  набор правил для адреса задаёт его схема: правила создания пароля — для регистрации,
  правила входа — только наличие, непустота и формат email (решение 6).

Фильтр и слой ошибок не относятся к аутентификации и используются всеми следующими
модулями API (склады, задания, права доступа).

### 10. Guard и декораторы для закрытых маршрутов

Авторизация закрытых маршрутов — один глобальный guard, подключённый как `APP_GUARD`:
он читает cookie сессии, проверяет сессию в Redis и кладёт пользователя в запрос.
Открытые маршруты помечаются декоратором `@Public()` — guard их пропускает. Данные
текущего пользователя в обработчике получаются параметр-декоратором `@CurrentUser()`.

Альтернатива: проверка сессии в каждом контроллере руками — быстрее сделать, но
рано или поздно закрытый маршрут останется без проверки; глобальный guard с явным
исключением `@Public()` делает защиту «по умолчанию включённой».

Ответ guard — тот же единый формат ошибки с кодом `UNAUTHENTICATED` и статусом `401`.
Роли и права на склады guard не проверяет: это следующий этап (ADR-003).

### 11. Параметры окружения

Сроки и пороги задаются переменными окружения, чтобы их можно было менять без правки
кода и в разных средах. Имена — в верхнем регистре, по образцу существующих `PORT`,
`DATABASE_URL`. Значения проверяются Zod-схемой окружения: некорректное значение
останавливает запуск API, как это уже происходит для `PORT` и `DATABASE_URL`.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |

| `SESSION_IDLE_SECONDS` | `86400` | Срок неактивности сессии (24 часа) |
| `SESSION_TTL_SECONDS` | `604800` | Абсолютный срок жизни сессии (7 суток) |

лимиты. Конкретные числа для продакшена уточняются при настройке развёртывания. Требования
спецификаций описывают поведение через конфигурацию и не фиксируют числа: правила полей
(длина пароля, email и имени) — продуктовые решения и остаются числами, они переменными
окружения не выносятся.

### 12. Cookie, CORS и запрет кэширования

Cookie: `HttpOnly` — безусловно; `SameSite`, `Path` и `Secure` задаются конфигурацией,
значения по умолчанию — `SameSite=Lax`, `Path=/`, `Secure` включён по умолчанию и
выключается в локальной разработке. Имя cookie — `warehouse_session`; домен не задаётся,
cookie остаётся host-only. Срок cookie задаётся признаком `Max-Age` и равен меньшему из
остатков двух сроков сессии — неактивности и абсолютного: cookie не должна пережить
серверную сессию. При каждом авторизованном запросе cookie перевыдаётся с обновлённым
сроком, иначе браузер удалил бы её через срок неактивности, пока серверная сессия ещё
жива. При выходе cookie сбрасывается пустым значением с `Max-Age=0`.

Ответы аутентификации и текущего пользователя помечаются `Cache-Control: no-store`:
иначе промежуточный кэш мог бы отдать ответ вместе с cookie другому клиенту.

Web и API работают на разных источниках (3000 и 3001), поэтому API настраивает CORS с
явным списком доверенных источников и `credentials: true`; запросы с credentials требуют
точного origin, а не `*`. Список источников — непустая переменная окружения, и он же
используется для проверки источника изменяющих запросов (решение 7a); пустое значение
останавливает запуск. `OPTIONS` обрабатывается без cookie: доверенный источник получает
`204` с разрешающими заголовками, недоверенный — `403`, неизвестный маршрут — `404`.

### 12a. Публичные адреса и защита по умолчанию

Защита включается по умолчанию: закрыты все адреса, кроме явно открытых. Открытые адреса:
`GET /health` (проверка состояния), `POST /auth/register`, `POST /auth/login` и
`POST /auth/logout` — последние три не требуют действующей сессии и работают и без неё.
Каждый новый адрес по умолчанию закрыт, и чтобы сделать его открытым, его нужно
пометить как публичный явно.

### 13. Скрытие пароля и равное время ответа

В журналы не попадают исходный пароль, хеш и идентификатор сессии. При входе на
несуществующий email система выполняет фиктивную проверку хеша с текущими параметрами
хеширования, чтобы время ответа не отличалось от ответа при неверном пароле и по времени
нельзя было перечислить существующие учётные записи. Числовой критерий равенства времени
не задаётся: проверяется наличие фиктивной проверки, а не её длительность.

### 14. Карта контракта

Таблица собирает все адреса и ситуации в одном месте: по ней видно, что для каждой
комбинации задан ответ, и видно пробелы. Требования в `specs/` описывают ту же
поведение подробно, эта таблица — карта для ревью.

| Ситуация | `POST /auth/register` | `POST /auth/login` | `POST /auth/logout` | `GET /users/current` |
| --- | --- | --- | --- | --- |
| Успех | `201` + `{user}` + cookie | `200` + `{user}` + cookie | `204` | `200` + `{user}` |
| Некорректное тело или тип содержимого | `400 INVALID_REQUEST` | `400 INVALID_REQUEST` | тело не требуется | — |
| Нарушение правил поля | `400 VALIDATION_FAILED` + `fields` | `400 VALIDATION_FAILED` + `fields` (только `REQUIRED` и `EMAIL_INVALID`) | — | — |
| Адрес уже занят | `409 EMAIL_ALREADY_TAKEN` + `fields` | — | — | — |
| Неверные учётные данные | — | `401 INVALID_CREDENTIALS` | — | — |
| Нет действующей сессии | — | — | `204` | `401 UNAUTHENTICATED` |
| Превышен лимит | `429 REGISTRATION_RATE_LIMITED` + `Retry-After` | `429 TOO_MANY_ATTEMPTS` или `429 EMAIL_RATE_LIMITED` + `Retry-After` | — | — |
| Недоверенный источник, `Origin: null` или нет обоих заголовков | `403 CSRF_REJECTED` | `403 CSRF_REJECTED` | `403 CSRF_REJECTED` | — |
| Redis недоступен | `503 SERVICE_UNAVAILABLE` | `503 SERVICE_UNAVAILABLE` | `503 SERVICE_UNAVAILABLE` | `503 SERVICE_UNAVAILABLE` |
| Непредвиденная ошибка | `500 INTERNAL_ERROR` | `500 INTERNAL_ERROR` | `500 INTERNAL_ERROR` | `500 INTERNAL_ERROR` |
| Неизвестный маршрут или метод | `404 ROUTE_NOT_FOUND`, `405 METHOD_NOT_ALLOWED` | то же | то же | то же |

Все ответы этих адресов содержат `Cache-Control: no-store`, включая ответы с ошибками.
Ответ `503` не гарантирует откат: при регистрации запись могла сохраниться, повтор может
дать `409 EMAIL_ALREADY_TAKEN` — тогда клиент переходит ко входу; выход идемпотентен, его
повтор безопасен. Число активных сессий зафиксировано решением тимлида: одна. Блокировка
попыток входа не завершает действующие сессии. При исчерпанном лимите регистрации запрос
даёт `429` независимо от тела. Публичные адреса: `GET /health`, `POST /auth/register`,
`POST /auth/login`, `POST /auth/logout`; остальные закрыты. `OPTIONS`: доверенный
источник — `204`, недоверенный или без `Origin` — `403`, неизвестный маршрут — `404`.

## Risks / Trade-offs

- [Ошибки входа не различают причину, поэтому пользователь с неверным паролем не может
  понять, верна ли его почта] → это осознанный выбор: единый ответ «Неверная почта или
  пароль» защищает от перебора зарегистрированных адресов.
- [Регистрация раскрывает, что адрес уже занят] → перечисление при регистрации
  частично неизбежно; раскрытие ограничено полем и кодом нарушения, других сведений о
  существующем пользователе сервер не отдаёт; лимит с IP ограничивает один источник, но не
  распределённый перебор.
- [Поле `fields` заполняется для ошибок входных данных, включая конфликт занятости
  адреса] → ошибки аутентификации идут без `fields`; Web показывает общий текст в общей
  области под полями.
- [Cookie-сессия не подходит мобильным клиентам без cookie-jar] → мобильный транспорт
  выносится в отдельную задачу; для него понадобится либо cookie-jar в клиенте, либо
  новый способ выдачи сессии, а не изменение текущего контракта.
- [Redis стал обязательной зависимостью API для входа] → локальный Compose дополняется
  сервисом Redis; проверка доступности Redis при старте и понятная ошибка при его
  недоступности описаны в задачах реализации. `503` означает неизвестный исход: повтор
  безопасен, но откат регистрации не гарантируется.
- [Сессия в памяти процесса недопустима при нескольких процессах API] → хранение только
  в Redis, это же проверяется тестом на двух экземплярах.
- [Тексты ошибок живут в Web, а коды — в API] → расхождение текста и кода возможно;
  митигация: коды перечислены в контракте, а `login-form` фиксирует тексты по кодам,
  изменение текста требует изменения спецификации `login-form`.
- [Правила пароля (8–36 символов, цифра, регистр, спецсимвол) расходятся с текущей
  `login-form`, где ограничения только «вводятся отдельным согласованием»] → расхождение
  зафиксировано: до подключения Web к API спецификация `login-form` обновляется
  (проверка пароля на клиенте, тексты ошибок поля, код `TOO_MANY_ATTEMPTS`), иначе формы
  и API будут показывать разные ошибки об одном и том же.
- [Смена параметров argon2id через окружение требует перехеширования] → перехеширование
  выполняется при успешном входе; при смене параметров старые пароли продолжают работать
  до первого входа.
- [Глобальный guard требует явного `@Public()` для каждого открытого маршрута] → забытый
  `@Public()` закрывает маршрут, а не открывает лишний; это безопасный порядок ошибки.
- [Лимит по email позволяет кратковременно заблокировать вход владельцу чужими
  попытками, а лимит по IP может затронуть пользователей за общим NAT] → это принятые
  компромиссы; пороги стартовые и настраиваемые.
- [Запросы без `Origin` и `Referer` получают `403`] → механизм рассчитан на браузерный
  Web; для нативного клиента нужна отдельная договорённость, задача отложена.
- [Два независимых срока сессии могут удивить пользователя] → тексты об истечении сессии
  и о повторном входе задаются в Web и согласуются с Таней.
- [Строгая проверка тела: лишнее поле даёт `400 INVALID_REQUEST`] → это ломает
  forward-совместимость клиентов: новая версия Web со снятым полем упрётся в старый API.
  Решение осознанное — единый строгий контракт вместо «лишние поля игнорируем»; при
  появлении новых полей Web и API обновляются вместе.
- [Правила пароля применяются только при создании] → пароль, созданный по прежним
  правилам, продолжает работать, но новые аккаунты получают более строгие требования;
  переход к прежней силе пароля для старых аккаунтов возможен только принудительно.
- [Размер тела запроса не ограничен контрактом] → при входе длина и сложность пароля не
  проверяются, поэтому сервер хеширует строку любой длины; ограничение остаётся на
  инфраструктуре (прокси, веб-сервер), а не в API.
- [У пользователя одна активная сессия] → число сессий согласуется со Стасом; если
  останется одна, вход с другого устройства обрывает прежнюю, а для сценария «работа на
  двух устройствах» правило придётся пересмотреть.
- [Перечень публичных адресов придётся расширять] → закрыты все адреса по умолчанию,
  открытые перечислены явно (`/health` и адреса аутентификации); новый открытый адрес
  требует правки и требования, и справочника.
- [Обновление хеша при перехешировании — операция вне `user-account`] → спецификация
  `user-account` описывает только создание записи; операция обновления хеша описана в
  `user-credentials` и не меняет требований `user-account`.
- [Правила email строже, чем в `user-account`] → `user-account` задаёт минимальный формат
  адреса; правила проверки на границе API (запрет пробелов, длина до 254) заданы в
  `user-credentials` и применяются до сохранения, поэтому хранилище получает уже
  проверенное значение. Спецификация `user-account` при этом не меняется.
- [Спецификация формы (PR #34) ещё не слита] → до слияния её текст не является источником
  истины: правила клиентской проверки и тексты ошибок задаются этим change, а правка
  формы в PR #34 обязательна до подключения Web к API.

## Migration Plan

Данные не мигрируют: схема `User` не меняется, пользователей в базе нет.
Разворачивание — добавление переменных окружения и сервиса Redis; откат — откат
контейнера API, записи сессий в Redis живут не дольше абсолютного срока и удаляются сами.

## Open Questions

- Политика сессий, лимитов, источника и Redis зафиксирована решением тимлида 2026-11-23:
  одна активная сессия, 24 часа неактивности, 7 суток абсолютно, лимиты 5/5 минут и
  20/5 минут с блокировкой 60 секунд, 10 запросов с IP за 10 минут; числа стартовые и
  настраиваемые.
  Комментарий тимлида фиксирует выбор политики, но не является окончательным согласованием
  всей спецификации и не разрешает реализацию до согласования этапов. Имя cookie, состав
  тела ошибки и справочник кодов и сообщений — подтвердить отдельно.
- Источник IP клиента для ключей счётчиков: за балансировщиком требуется решение о
  доверии прокси и заголовке `X-Forwarded-For`. Без него ключи счётчиков и ответы `429`
  зависят от того, как API определит адрес клиента.
- Тексты сообщений и перефразирование Web для кодов, которые сервер реально возвращает в
  интерфейс: `INVALID_CREDENTIALS`, `TOO_MANY_ATTEMPTS`, `EMAIL_RATE_LIMITED`,
  `REGISTRATION_RATE_LIMITED`, `CSRF_REJECTED`, `UNAUTHENTICATED`, `EMAIL_ALREADY_TAKEN`,
  `VALIDATION_FAILED`, `INVALID_REQUEST` и коды нарушений полей (`REQUIRED`,
  `EMAIL_INVALID`, `PASSWORD_TOO_SHORT`, `PASSWORD_TOO_LONG`, `PASSWORD_WEAK`,
  `NAME_TOO_SHORT`, `NAME_TOO_LONG`) — согласовать с Таней в рамках F4 и обновления
  спецификации формы в PR #34.
- Детали реализации, не входящие в этот change: окна и блокировки (B9), конкурентная
  регистрация (B6), Unicode и проверка без изменения данных (B3), гонки сессий и формат
  идентификатора (B4), перефразирование текстов (F4). Их закрывают до реализации
  соответствующей части.
- Правила источника (пустой `TRUSTED_ORIGINS`, отсутствие `Origin`/`Referer`,
  недоверенный preflight, стандартный порт) зафиксированы в решении 7a и не являются
  открытым вопросом.
- Клиентская проверка правил до отправки выносится в отдельную задачу: спецификация
  формы сейчас проверяет только обязательность и формат почты, а проверка пароля по
  общим Zod-схемам ещё не описана. В форме входа клиент проверяет полные правила email,
  сложность пароля — только в форме регистрации.
- Регистрация раскрывает занятость адреса — подтвердить у Юры и Таней, что такой
  уровень раскрытия приемлем для продукта.
- Форма регистрации в Web ещё не существует: нужен ли для неё отдельный текст ошибки,
  отличный от текста входа, — определить вместе с формой регистрации.
- Нативные клиенты: без `Origin` и `Referer` они получают `403`; для них понадобится
  отдельная схема аутентификации — определить вместе с задачей мобильного клиента.
