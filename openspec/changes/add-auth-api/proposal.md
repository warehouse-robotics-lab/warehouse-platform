# Proposal

## Why

Форма входа в Web уже сверстана (PR #31), а её поведение — проверка полей, ошибки,
состояние ожидания — описано в Draft PR #34 (`docs/login-form-behavior`). В API есть
готовое Prisma-хранилище пользователя (PR #29) и принятая спецификация данных
`user-account`, но нет ни одного HTTP-эндпоинта аутентификации и нет описания сессии.
Без согласованного внешнего контракта Web не может подключить форму, а команда не может
начать реализацию API авторизации.

Задача — [issue #39](https://github.com/warehouse-robotics-lab/warehouse-platform/issues/39).
Это change spec-first: он фиксирует поведение HTTP-контракта и сессии, а реализация
разбивается на небольшие сценарии в связанной задаче.

## What Changes

- Появляется внешний HTTP-контракт API авторизации:
  - регистрация пользователя;
  - вход по email и паролю;
  - выход из сессии;
  - получение текущего пользователя.
- Вводится способ сессии: серверная сессия в Redis, браузер получает непрозрачную
  httpOnly-cookie. Срок жизни — 7 суток с момента создания, продление при
  активности в пределах этого срока.
- Описывается поведение неавторизованного запроса: единый ответ с кодом ошибки,
  без различения существующей и несуществующей почты при входе.
- Хеширование и проверка пароля описываются отдельно от сохранения готового хеша
  (`user-account`): алгоритм argon2id, требования к паролю, отсутствие открытого
  пароля и хеша в ответах и журналах.
- Фиксируются ограничения полей: длина и сложность пароля, длина email и имени.
- Разная степень раскрытия при отказе: вход отвечает едино (один статус, код и текст, без
  указания поля), регистрация раскрывает проблемное поле и код нарушения — чтобы по
  ответу нельзя было перебирать зарегистрированные адреса при входе.
- Фиксируются защита от перебора пароля на входе и единый формат ошибок с кодами
  ошибок; поле `fields` используется для ошибок формата входных данных.
- Сроки жизни сессии и cookie, пороги защиты от перебора и параметры хеширования
  задаются переменными окружения со значениями по умолчанию.
- Описываются переиспользуемые механизмы API: единый слой ошибок и guard с
  декораторами для открытых и закрытых маршрутов.
- Общие схемы запросов, ответов и ошибок живут в `@warehouse/contracts` на Zod,
  документация контракта — Swagger и раздел в `apps/api/README.md`.
- Описано, что поведение формы в PR #34 нужно дополнить проверкой пароля и новыми
  кодами ошибок; расхождение зафиксировано, а не разрешено молча.

## Capabilities

### New Capabilities

- `auth-api`: внешний HTTP-контракт регистрации, входа, выхода и получения текущего
  пользователя — запросы, ответы, статусы, коды ошибок полей и общей ошибки, защита
  от перебора пароля.
- `user-session`: жизненный цикл сессии — создание, хранение, срок жизни и
  продление, завершение выходом, поведение запроса без действующей сессии.
- `user-credentials`: требования к учётным данным — правила пароля и email, хеширование
  и проверка исходного пароля, связь с сохранением готового хеша из `user-account`.

### Modified Capabilities

Нет. Требования `user-account` не меняются: правила полей, уникальности и нормализации
email уже описаны, а операция сохранения по-прежнему получает готовый хеш.

## Impact

- **`apps/api`:** новые модули аутентификации и сессий, клиент Redis, хеширование
  пароля, защита от перебора, единый слой ошибок и guard авторизации, Swagger.
  Требуются зависимости: клиент Redis, `argon2`, `@nestjs/swagger` (Swagger входит в
  стек проекта, контрактная библиотека ts-rest/tRPC не вводится — решение не принято).
- **`packages/contracts`:** пакет оживает: Zod-схемы запросов, ответов и ошибок.
  Выбор ts-rest/tRPC остаётся открытым и в этом change не решается.
- **`apps/web`:** код приложения в этом change не меняется. Требуется синхронизация
  со спецификацией `login-form` из PR #34: правила пароля и новые коды ошибок.
- **Переменные окружения API:** адрес Redis, сроки жизни сессии и cookie, пороги
  защиты от перебора, параметры хеширования, доверенные источники CORS. Значения по
  умолчанию и обязательность — в `apps/api/README.md`.
- **Документация:** раздел про HTTP-контракт авторизации в `apps/api/README.md`,
  Swagger как живая документация контракта.
- **Хранилище пользователя, CI, Simulation:** не затрагиваются. Связь с Simulation —
  следующий этап.
