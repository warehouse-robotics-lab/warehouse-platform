# Spec Delta

## Purpose

Требования к учётным данным пользователя на границе API: правила проверки email, пароля
и имени, хеширование исходного пароля и его проверка. Операция сохранения пользователя
остаётся в `user-account` и по-прежнему получает готовый хеш.

## ADDED Requirements

### Requirement: Требования к паролю

Пароль MUST содержать от 8 до 36 символов включительно. Пароль MUST содержать хотя бы
одну цифру, одну заглавную букву, одну строчную букву и один специальный символ.
Специальным символом считается любой символ, не являющийся буквой или цифрой, кроме
пробела. Пароль MUST NOT изменяться: регистр, пробелы и крайние пробелы сохраняются.
Нарушение правила MUST определяться проверкой однозначно и MUST сопровождаться кодом
нарушения: `PASSWORD_TOO_SHORT`, `PASSWORD_TOO_LONG` или `PASSWORD_WEAK`.

#### Scenario: Пароль короче минимума

- **WHEN** пользователь передаёт пароль длиной 7 символов, удовлетворяющий остальным правилам
- **THEN** проверка определяет нарушение длины с кодом `PASSWORD_TOO_SHORT`

#### Scenario: Пароль длиннее максимума

- **WHEN** пользователь передаёт пароль длиной 37 символов, удовлетворяющий остальным правилам
- **THEN** проверка определяет нарушение длины с кодом `PASSWORD_TOO_LONG`

#### Scenario: Пароль без цифры

- **WHEN** пользователь передаёт пароль без цифр
- **THEN** проверка определяет нарушение состава с кодом `PASSWORD_WEAK`

#### Scenario: Пароль без заглавной буквы

- **WHEN** пользователь передаёт пароль без заглавных букв
- **THEN** проверка определяет нарушение состава с кодом `PASSWORD_WEAK`

#### Scenario: Пароль без строчной буквы

- **WHEN** пользователь передаёт пароль без строчных букв
- **THEN** проверка определяет нарушение состава с кодом `PASSWORD_WEAK`

#### Scenario: Пароль без специального символа

- **WHEN** пользователь передаёт пароль только из букв и цифр
- **THEN** проверка определяет нарушение состава с кодом `PASSWORD_WEAK`

#### Scenario: Пробелы в пароле сохраняются

- **WHEN** пользователь передаёт пароль `"  Ab1!def  "` длиной от 8 до 36 символов
- **THEN** система принимает пароль и сохраняет его без изменений, включая пробелы

### Requirement: Требования к email

Email MUST содержать символ `@`, непустую локальную часть и непустой домен, MUST NOT
содержать пробелов и MUST быть не длиннее 254 символов после нормализации.
Перед проверкой и сохранением значение MUST быть нормализовано по правилам `user-account`:
крайние пробелы удаляются, регистр приводится к нижнему. Нарушение правил формата или
длины MUST определяться проверкой с кодом `EMAIL_INVALID`.

#### Scenario: Email без символа @

- **WHEN** пользователь передаёт email `userexample.com`
- **THEN** проверка определяет нарушение формата с кодом `EMAIL_INVALID`

#### Scenario: Email с пробелами

- **WHEN** пользователь передаёт email `"  user@example.com  "`
- **THEN** система нормализует значение до `user@example.com` и проверяет его дальше

#### Scenario: Слишком длинный email

- **WHEN** пользователь передаёт email длиннее 254 символов
- **THEN** проверка определяет нарушение длины с кодом `EMAIL_INVALID`

### Requirement: Требования к имени

Имя MUST содержать от 2 до 64 символов включительно после удаления крайних пробелов.
Пробелы между словами MUST сохраняться. Пустое после обрезки имя MUST считаться
отсутствующим. Нарушение правил MUST определяться проверкой с кодом `NAME_TOO_SHORT` или
`NAME_TOO_LONG`.

#### Scenario: Имя короче минимума

- **WHEN** пользователь передаёт имя `Я` или пустое имя
- **THEN** проверка определяет нарушение длины с кодом `NAME_TOO_SHORT`

#### Scenario: Имя длиннее максимума

- **WHEN** пользователь передаёт имя длиннее 64 символов
- **THEN** проверка определяет нарушение длины с кодом `NAME_TOO_LONG`

#### Scenario: Имя с крайними пробелами

- **WHEN** пользователь передаёт имя `"  Иван Петров  "`
- **THEN** система сохраняет имя `Иван Петров`

### Requirement: Коды нарушений правил

Коды нарушений правил MUST быть одинаковыми у Web и API, чтобы клиент мог проверять
значение до отправки. При отказе регистрации код нарушения MUST передаваться в ответе
в `fields` для поля, к которому нарушение относится. Коды нарушений MUST NOT
использоваться для ошибок аутентификации.

#### Scenario: Клиентская и серверная проверки совпадают

- **WHEN** Web проверяет значение по тем же правилам, что и API
- **THEN** код нарушения совпадает с кодом, который определила бы серверная проверка

#### Scenario: Ответ регистрации содержит код нарушения

- **WHEN** регистрация отклонена из-за нарушения правил поля
- **THEN** в `fields` для этого поля указан код конкретного нарушения

#### Scenario: Ошибка аутентификации без кодов нарушений

- **WHEN** вход отклонён
- **THEN** тело ответа содержит единый код `INVALID_CREDENTIALS` и не содержит `fields`
