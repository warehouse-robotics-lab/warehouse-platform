# Spec Delta

## Purpose

Внешний HTTP-контракт API авторизации: регистрация, вход, выход и получение текущего
пользователя, единый формат ошибок, статусы ответов, лимиты попыток входа и регистрации,
защита изменяющих запросов от CSRF и поведение при недоступности Redis.

## ADDED Requirements

### Requirement: Тело ошибки

Система MUST отвечать на ошибку единым телом вида `{ "code", "message", "fields"? }`.
`code` MUST быть стабильным машинным кодом, `message` — согласованной по коду
формулировкой (см. «Тексты ошибок»), `fields` — соответствием имён полей и массивов
кодов нарушений этих полей. HTTP-статус MUST передаваться статусом ответа и MUST NOT
дублироваться в теле. Формат MUST применяться ко всем ошибкам API.

#### Scenario: Ошибка без привязки к полю

- **WHEN** запрос отклонён по причине, не связанной с конкретным полем
- **THEN** тело ответа содержит `code` и `message`
- **AND** объект `fields` отсутствует

#### Scenario: Ошибка с привязкой к полю

- **WHEN** запрос отклонён из-за нарушения правил поля
- **THEN** тело ответа содержит `code`, `message` и `fields`
- **AND** в `fields` значение поля — массив кодов нарушений

### Requirement: Маршрут и метод

Неизвестный маршрут MUST давать ответ `404` с кодом ошибки `ROUTE_NOT_FOUND`, а известный
маршрут, вызванный неподдерживаемым методом, — ответ `405` с кодом ошибки
`METHOD_NOT_ALLOWED` и заголовком `Allow` с перечислением поддерживаемых методов. Оба
ответа MUST иметь единый формат ошибки. Предварительный запрос `OPTIONS` обработке
методом не подпадает (см. «CORS и preflight»).

#### Scenario: Неизвестный маршрут

- **WHEN** клиент обращается к неизвестному маршруту
- **THEN** система отвечает `404` с кодом ошибки `ROUTE_NOT_FOUND` в едином формате ошибки

#### Scenario: Неподдерживаемый метод

- **WHEN** клиент вызывает известный маршрут неподдерживаемым методом
- **THEN** система отвечает `405` с кодом ошибки `METHOD_NOT_ALLOWED` в едином формате ошибки
- **AND** в ответе присутствует заголовок `Allow` с перечислением поддерживаемых методов

### Requirement: Тексты ошибок

Каждому коду ошибки верхнего уровня MUST соответствовать ровно одно сообщение,
перечисленное в справочнике кодов и сообщений (`../../design.md`). Сообщение MUST быть
кратким и MUST NOT содержать технических подробностей. Один код MUST давать один и тот
же текст во всех ответах. Клиент MAY показывать собственную формулировку, опираясь на
код. Коды нарушений полей используются только в `fields` и отдельных сообщений не имеют:
текст для них выбирает клиент.

#### Scenario: Одинаковый текст для одного кода

- **WHEN** система отвечает двумя ошибками с одинаковым кодом
- **THEN** сообщения в обоих ответах совпадают

#### Scenario: Сообщение соответствует справочнику

- **WHEN** система отвечает ошибкой с кодом верхнего уровня
- **THEN** сообщение совпадает с текстом этого кода в справочнике

### Requirement: Коды нарушений полей

Коды нарушений полей, передаваемые в `fields`, MUST быть из перечня: `REQUIRED`,
`EMAIL_INVALID`, `EMAIL_ALREADY_TAKEN`, `PASSWORD_TOO_SHORT`, `PASSWORD_TOO_LONG`,
`PASSWORD_WEAK`, `NAME_TOO_SHORT`, `NAME_TOO_LONG`. Коды в `fields` MUST быть
упорядочены: сначала `REQUIRED`, затем коды длины, затем коды состава, затем код
конфликта занятости адреса. Поле с пустым значением MUST кодироваться только кодом
`REQUIRED`.

#### Scenario: Код нарушения поля известен клиенту

- **WHEN** клиент получает ошибку правил поля
- **THEN** код нарушения в `fields` входит в перечень кодов нарушений полей

#### Scenario: Порядок кодов в поле

- **WHEN** одно поле нарушает несколько правил
- **THEN** коды в `fields` для этого поля перечислены в установленном порядке

### Requirement: Ошибки правил полей

Если значения полей запроса не проходят проверки `user-credentials`, система MUST
отвечать `400 VALIDATION_FAILED` и перечислять в `fields` коды нарушений всех неверных
полей. Отсутствующее или пустое поле MUST кодироваться `REQUIRED`; если поле нарушает
несколько правил, MUST перечисляться все коды. При регистрации нарушение правил MUST NOT
создавать пользователя.

#### Scenario: Неверный формат email

- **WHEN** клиент отправляет email без символа `@`
- **THEN** система отвечает `400` с кодом ошибки `VALIDATION_FAILED`
- **AND** в `fields` для поля `email` указан код `EMAIL_INVALID`

#### Scenario: Отсутствующее обязательное поле

- **WHEN** клиент отправляет запрос без поля `email`
- **THEN** система отвечает `400` с кодом ошибки `VALIDATION_FAILED`
- **AND** в `fields` для поля `email` указан код `REQUIRED`

#### Scenario: Пустое значение поля

- **WHEN** клиент отправляет пустое значение поля
- **THEN** система отвечает `400` с кодом ошибки `VALIDATION_FAILED`
- **AND** в `fields` для этого поля указан код `REQUIRED`

#### Scenario: Пароль нарушает несколько правил

- **WHEN** клиент отправляет пароль короче минимума и без требуемых символов
- **THEN** система отвечает `400` с кодом ошибки `VALIDATION_FAILED`
- **AND** в `fields` для поля `password` указаны коды `PASSWORD_TOO_SHORT` и `PASSWORD_WEAK`

#### Scenario: Несколько неверных полей

- **WHEN** клиент отправляет неверные email, пароль и имя одновременно
- **THEN** система отвечает `400` с кодом ошибки `VALIDATION_FAILED`
- **AND** в `fields` перечислены коды нарушений всех трёх полей
- **AND** тело ответа имеет вид `{"code":"VALIDATION_FAILED","message":"Проверьте поля формы","fields":{"email":["EMAIL_INVALID"],"password":["PASSWORD_TOO_SHORT","PASSWORD_WEAK"],"name":["NAME_TOO_SHORT"]}}`

#### Scenario: Слабый пароль не создаёт пользователя

- **WHEN** клиент отправляет регистрацию с паролем, не удовлетворяющим правилам
- **THEN** система отвечает `400` с кодом ошибки `VALIDATION_FAILED`
- **AND** пользователь не создаётся

### Requirement: Ошибки тела запроса

Если тело запроса не является JSON-объектом, содержит лишние поля или поля неверных
типов, система MUST отвечать `400` с кодом ошибки `INVALID_REQUEST` и MUST NOT
заполнять `fields`. Тип содержимого MUST приниматься при основном типе
`application/json`, параметры вроде `charset` допускаются; иной тип MUST отклоняться
тем же ответом. Пустое тело рассматривается отдельно (см. «Пустое тело и адреса без
тела»).

#### Scenario: Тело не является объектом

- **WHEN** клиент отправляет тело, которое не является JSON-объектом
- **THEN** система отвечает `400` с кодом ошибки `INVALID_REQUEST`

#### Scenario: Неверный тип поля

- **WHEN** клиент отправляет `email` не строкой
- **THEN** система отвечает `400` с кодом ошибки `INVALID_REQUEST`
- **AND** `fields` не заполняется

#### Scenario: Лишнее поле в теле

- **WHEN** клиент отправляет поле, которого нет в контракте адреса
- **THEN** система отвечает `400` с кодом ошибки `INVALID_REQUEST`

#### Scenario: Тип содержимого с параметрами

- **WHEN** клиент отправляет тело с типом содержимого `application/json; charset=utf-8`
- **THEN** система принимает тело и обрабатывает запрос по правилам адреса

#### Scenario: Иной тип содержимого

- **WHEN** клиент отправляет тело с типом содержимого, отличным от `application/json`
- **THEN** система отвечает `400` с кодом ошибки `INVALID_REQUEST`

### Requirement: Пустое тело и адреса без тела

Пустое тело MUST считаться отсутствием всех обязательных полей и отклоняться как
нарушение правил полей с кодом `VALIDATION_FAILED` и кодами `REQUIRED` в `fields`.
Адреса, тело которых не требуется, MUST NOT проверяться на состав и тип.

#### Scenario: Пустое тело

- **WHEN** клиент отправляет пустое тело
- **THEN** система отвечает `400` с кодом ошибки `VALIDATION_FAILED`
- **AND** в `fields` указаны коды `REQUIRED` для отсутствующих полей

#### Scenario: Адрес без тела

- **WHEN** клиент вызывает адрес, тело которого не требуется
- **THEN** система не проверяет тело и обрабатывает запрос по правилам адреса

### Requirement: Состав объекта пользователя в ответе

Объект пользователя в ответах MUST содержать `uuid` в формате uuid, `email`, `name` и
`createdAt` в формате ISO 8601 в UTC. Объект MUST NOT содержать `password` и хеш пароля.

#### Scenario: Состав объекта пользователя

- **WHEN** система возвращает пользователя клиенту
- **THEN** объект содержит `uuid`, `email`, `name` и `createdAt`
- **AND** `createdAt` задан в формате ISO 8601 в UTC

#### Scenario: Пароль в объекте отсутствует

- **WHEN** система возвращает пользователя клиенту
- **THEN** объект не содержит поля `password` и значения хеша пароля

### Requirement: Регистрация пользователя

Система MUST предоставлять регистрацию по адресу `POST /auth/register`. Тело запроса
MUST содержать `email`, `password` и `name` строкового типа. При успехе система MUST
отвечать `201` с телом `{"user":{"uuid":"…","email":"…","name":"…","createdAt":"…"}}`
и MUST устанавливать cookie сессии с признаком `HttpOnly` и с признаками, заданными
конфигурацией. Проверки MUST выполняться в порядке: лимит регистраций с IP, затем
правила полей, затем занятость адреса.

#### Scenario: Успешная регистрация

- **WHEN** клиент отправляет `{"email":"user@example.com","password":"Ab1!defg","name":"Иван"}`
- **THEN** система отвечает `201` с телом `{"user":{"uuid":"…","email":"user@example.com","name":"Иван","createdAt":"…"}}`
- **AND** устанавливает cookie сессии

#### Scenario: Нарушение правил проверяется раньше занятости

- **GIVEN** адрес уже занят
- **WHEN** клиент отправляет регистрацию с неверным паролем
- **THEN** система отвечает `400` с кодом ошибки `VALIDATION_FAILED`

### Requirement: Занятый email при регистрации

Если email уже сохранён у другого пользователя, система MUST отвечать `409` с кодом
ошибки `EMAIL_ALREADY_TAKEN` и MUST указывать этот код в `fields` для поля `email`.
Сравнение email MUST выполняться по нормализованному значению. Данные существующего
пользователя MUST NOT изменяться, новый пользователь MUST NOT создаваться.

#### Scenario: Email уже занят

- **GIVEN** существует пользователь с email `user@example.com`
- **WHEN** клиент регистрируется с email `USER@example.com`
- **THEN** система отвечает `409` с телом `{"code":"EMAIL_ALREADY_TAKEN","message":"Адрес уже зарегистрирован","fields":{"email":["EMAIL_ALREADY_TAKEN"]}}`
- **AND** данные существующего пользователя не изменяются

### Requirement: Проверки полей при входе

При входе система MUST проверять наличие, тип и непустоту полей `email` и `password`, а
также применять к `email` полные правила `user-credentials`: формат адреса, отсутствие
пробелов и длину не более 254 символов после нормализации. Правила длины и состава
пароля при входе MUST NOT применяться: пароль, созданный по прежним правилам, MUST
приниматься и сравниваться с хешем как есть.

#### Scenario: Пустой пароль

- **WHEN** клиент отправляет пустой `password`
- **THEN** система отвечает `400` с кодом ошибки `VALIDATION_FAILED`
- **AND** в `fields` для поля `password` указан код `REQUIRED`

#### Scenario: Неверный формат email при входе

- **WHEN** клиент отправляет email без символа `@`
- **THEN** система отвечает `400` с кодом ошибки `VALIDATION_FAILED`
- **AND** в `fields` для поля `email` указан код `EMAIL_INVALID`

#### Scenario: Слишком длинный email при входе

- **WHEN** клиент отправляет email длиннее 254 символов
- **THEN** система отвечает `400` с кодом ошибки `VALIDATION_FAILED`
- **AND** в `fields` для поля `email` указан код `EMAIL_INVALID`

#### Scenario: Пароль по прежним правилам принимается

- **GIVEN** пользователь зарегистрирован с паролем, не удовлетворяющим текущим правилам сложности
- **WHEN** он входит с этим паролем
- **THEN** система не отклоняет пароль по правилам сложности и проверяет его по хешу

### Requirement: Вход пользователя

Система MUST предоставлять вход по адресу `POST /auth/login`. Тело запроса MUST
содержать `email` и `password` строкового типа. При успехе система MUST отвечать `200`
с телом `{"user":{"uuid":"…","email":"…","name":"…","createdAt":"…"}}` и MUST устанавливать
cookie сессии с признаком `HttpOnly` и с признаками, заданными конфигурацией.

#### Scenario: Успешный вход

- **WHEN** клиент отправляет `{"email":"user@example.com","password":"Ab1!defg"}`
- **THEN** система отвечает `200` с телом `{"user":{"uuid":"…","email":"user@example.com","name":"Иван","createdAt":"…"}}`
- **AND** устанавливает cookie сессии

### Requirement: Результаты входа

Каждый запрос входа MUST завершаться ровно одним из ответов: `200` при успехе,
`400 INVALID_REQUEST`, `400 VALIDATION_FAILED`, `401 INVALID_CREDENTIALS`,
`429 TOO_MANY_ATTEMPTS`, `429 EMAIL_RATE_LIMITED` или `503 SERVICE_UNAVAILABLE`.
`403 CSRF_REJECTED` и `500 INTERNAL_ERROR` применяются по правилам соответствующих
требований. `429` не является `INVALID_CREDENTIALS`, а `401` не является `429`.

#### Scenario: Успешный вход

- **GIVEN** верные учётные данные
- **WHEN** клиент выполняет вход
- **THEN** система отвечает `200` и устанавливает cookie сессии

#### Scenario: Неверные учётные данные

- **WHEN** клиент отправляет существующий `email` и неверный `password`
- **THEN** система отвечает `401` с кодом ошибки `INVALID_CREDENTIALS`
- **AND** другой статус входа не возвращается

#### Scenario: Отказ до проверки учётных данных

- **WHEN** запрос отклонён по правилам полей или по лимиту
- **THEN** система отвечает `400 VALIDATION_FAILED` или `429` соответственно
- **AND** код `INVALID_CREDENTIALS` не возвращается

### Requirement: Единый ответ при отказе аутентификации

При неверных учётных данных система MUST отвечать `401` с кодом ошибки
`INVALID_CREDENTIALS` и сообщением «Неверная почта или пароль». Ответ MUST NOT
содержать `fields` и MUST NOT указывать, что именно не совпало. Несуществующий email и
неверный пароль MUST давать одинаковый ответ.

#### Scenario: Неверный пароль

- **WHEN** клиент отправляет существующий `email` и неверный `password`
- **THEN** система отвечает `401` с телом `{"code":"INVALID_CREDENTIALS","message":"Неверная почта или пароль"}`
- **AND** cookie сессии не устанавливается

#### Scenario: Несуществующий email

- **WHEN** клиент отправляет несуществующий `email` и любой пароль
- **THEN** система отвечает `401` с телом `{"code":"INVALID_CREDENTIALS","message":"Неверная почта или пароль"}`

#### Scenario: Отказ не различает причины

- **GIVEN** клиент получил отказ аутентификации
- **WHEN** тело ответа отказа сравнивается с отказом по другой причине
- **THEN** код ошибки, сообщение и HTTP-статус совпадают

### Requirement: Что считается неудачной попыткой

Неудачной попыткой входа MUST считаться только отказ аутентификации (`401`); ошибки
формата и тела (`400`) и отказ по лимиту (`429`) MUST NOT учитываться. Ошибка чтения
счётчика или записи неудачной попытки MUST давать `503`; при сбое записи пароль уже
проверен, но сессия MUST NOT создаваться. Сбой сброса после успешного входа MUST NOT
отменять успех; ошибка MUST попадать в журнал.

#### Scenario: Ошибка формата не считается попыткой

- **WHEN** клиент отправляет запрос с некорректным форматом email
- **THEN** система отвечает `400`
- **AND** счётчики неудачных попыток не увеличиваются

#### Scenario: Отказ аутентификации считается попыткой

- **WHEN** клиент отправляет неверные учётные данные
- **THEN** система отвечает `401`
- **AND** счётчик неудачных попыток увеличивается

#### Scenario: Сбой записи после отказа

- **GIVEN** учётные данные неверны, а запись неудачной попытки не удаётся
- **WHEN** система обрабатывает попытку входа
- **THEN** система отвечает `503` с кодом ошибки `SERVICE_UNAVAILABLE`
- **AND** пароль уже проверен, но сессия не создаётся

#### Scenario: Отказ по лимиту не считается попыткой

- **WHEN** клиент получает отказ `429`
- **THEN** счётчики неудачных попыток не увеличиваются

#### Scenario: Успешный вход пытается сбросить счётчики

- **GIVEN** для пары `email` и IP были неудачные попытки
- **WHEN** пользователь входит с верными учётными данными
- **THEN** система пытается сбросить счётчики этой пары и этого адреса

#### Scenario: Отказ сброса не ломает вход

- **GIVEN** пользователь входит с верными учётными данными, а сброс счётчиков не удаётся
- **WHEN** система сбрасывает счётчики
- **THEN** вход завершается успешно, а ошибка сброса попадает в журнал

### Requirement: Учёт неудачных попыток для пары email и IP

Система MUST считать неудачные попытки входа отдельно для каждой пары `email` и IP
адреса клиента. Ключ счёта MUST строиться по нормализованному email. Порог — 5 неудачных
попыток за 5 минут, блокировка — 60 секунд; числа MUST задаваться конфигурацией. Повторные
запросы во время блокировки MUST NOT продлевать её; после окончания блокировки бюджет
попыток MUST обновляться. Механика окна и источник IP — детали B1 и B9.

#### Scenario: Счётчик ведётся по паре

- **WHEN** один пользователь неудачно входит с одного IP
- **THEN** счётчик этой пары увеличивается, а счётчики других пар не меняются

#### Scenario: Счётчик по нормализованному email

- **GIVEN** для пары `user@example.com` и IP была неудачная попытка
- **WHEN** та же пара приходит в другом регистре
- **THEN** система учитывает попытку в том же счётчике

### Requirement: Порядок применения лимитов

Система MUST проверять ограничения в порядке: проверка входных данных, затем блокировка
пары `email` и IP, затем лимит попыток по адресу почты, и только после этого — учётные
данные. При превышении любого лимита учётные данные MUST NOT проверяться и сессия MUST
NOT создаваться. При одновременном превышении блокировки пары и лимита по адресу MUST
применяться код блокировки пары `TOO_MANY_ATTEMPTS`.

#### Scenario: Превышен лимит пары

- **GIVEN** для пары `email` и IP действует блокировка
- **WHEN** клиент выполняет попытку входа
- **THEN** система отвечает `429` с кодом ошибки `TOO_MANY_ATTEMPTS`
- **AND** учётные данные не проверяются

#### Scenario: Превышен только лимит по адресу

- **GIVEN** блокировки пары нет, но исчерпан лимит попыток по адресу
- **WHEN** клиент выполняет попытку входа
- **THEN** система отвечает `429` с кодом ошибки `EMAIL_RATE_LIMITED`
- **AND** учётные данные не проверяются

#### Scenario: Превышены оба лимита

- **GIVEN** действуют блокировка пары и лимит по адресу
- **WHEN** клиент выполняет попытку входа
- **THEN** система отвечает `429` с кодом ошибки `TOO_MANY_ATTEMPTS`

### Requirement: Заголовок Retry-After

Любой ответ `429` MUST содержать заголовок `Retry-After` с числом секунд до следующей
допустимой попытки. Для обоих лимитов входа это остаток блокировки; для регистрации —
остаток окна. Значение MUST быть числом секунд, а не датой.

#### Scenario: Ответ 429 содержит Retry-After

- **WHEN** система отвечает `429` на вход или регистрацию
- **THEN** ответ содержит `Retry-After` с числом секунд

### Requirement: Блокировка входа для пары email и IP

Попытка, превышающая порог неудачных попыток, MUST отклоняться ответом `429` с кодом
ошибки `TOO_MANY_ATTEMPTS` и заголовком `Retry-After`. Блокировка MUST NOT завершать
действующие сессии. Порог 5, окно 5 минут и длительность блокировки 60 секунд MUST
задаваться конфигурацией. Механика отсчёта и непродления блокировки — детали B9.

#### Scenario: Превышен порог попыток

- **GIVEN** для пары `email` и IP за окно уже было 5 неудачных попыток
- **WHEN** клиент выполняет шестую попытку входа
- **THEN** система отвечает `429` с телом `{"code":"TOO_MANY_ATTEMPTS","message":"Слишком много попыток. Повторите позже."}`
- **AND** ответ содержит `Retry-After` с числом секунд до конца блокировки
- **AND** учётные данные не проверяются и сессия не создаётся

### Requirement: Лимит попыток для адреса почты

Система MUST считать неудачные попытки входа отдельно для каждого нормализованного
email без учёта IP. Порог — 20 неудачных попыток за 5 минут, блокировка — 60 секунд;
числа MUST задаваться конфигурацией. Повторные запросы во время блокировки MUST NOT
продлевать её; после окончания блокировки бюджет MUST обновляться. Превышение порога MUST
отклоняться `429 EMAIL_RATE_LIMITED` с `Retry-After` — остатком блокировки. Механика — B9.

#### Scenario: Превышен лимит по адресу

- **GIVEN** для нормализованного email за окно исчерпан порог неудачных попыток
- **WHEN** клиент выполняет попытку входа
- **THEN** система отвечает `429` с телом `{"code":"EMAIL_RATE_LIMITED","message":"Слишком много попыток. Повторите позже."}`
- **AND** ответ содержит `Retry-After` с числом секунд до конца блокировки

#### Scenario: Блокировка email не продлевается

- **GIVEN** для нормализованного email действует блокировка
- **WHEN** клиент повторяет попытку до её окончания
- **THEN** система отвечает `429` с кодом ошибки `EMAIL_RATE_LIMITED`
- **AND** срок блокировки не увеличивается

#### Scenario: После блокировки бюджет обновляется

- **GIVEN** срок блокировки email истёк
- **WHEN** клиент выполняет вход с верными учётными данными
- **THEN** система проверяет учётные данные и создаёт сессию

#### Scenario: Лимит не связан с IP

- **GIVEN** лимит по адресу исчерпан для одного email
- **WHEN** другой клиент входит с тем же email с другого IP
- **THEN** система отклоняет вход по лимиту этого адреса

### Requirement: Лимит регистраций с IP

Система MUST считать все запросы регистрации отдельно для каждого IP клиента, включая
запросы с нарушением правил полей. Порог — 10 запросов за 10 минут; числа MUST задаваться
конфигурацией. Превышение порога MUST отклоняться `429 REGISTRATION_RATE_LIMITED` с
заголовком `Retry-After`; этот ответ MUST иметь приоритет над ошибками тела и полей.
Механика окна — B9.

#### Scenario: Превышен лимит регистраций

- **GIVEN** для IP за окно исчерпан порог запросов регистрации
- **WHEN** клиент выполняет ещё одну попытку регистрации
- **THEN** система отвечает `429` с телом `{"code":"REGISTRATION_RATE_LIMITED","message":"Слишком много попыток. Повторите позже."}`
- **AND** ответ содержит `Retry-After` с числом секунд до конца окна
- **AND** пользователь не создаётся

#### Scenario: Неверные данные учитываются

- **GIVEN** лимит регистраций для IP не исчерпан
- **WHEN** клиент отправляет регистрацию с неверными данными
- **THEN** система отвечает `400`
- **AND** запрос учитывается в счётчике IP

### Requirement: Защита изменяющих запросов от CSRF

Система MUST проверять источник изменяющих запросов (`POST`, `PUT`, `PATCH`, `DELETE`),
включая регистрацию и вход. Источник MUST определяться по `Origin`, при его отсутствии —
по `Referer`, и сверяться со списком доверенных источников точным сравнением схемы, хоста
и порта; стандартный порт схемы равен отсутствию порта. Несовпадение, `Origin: null` или
отсутствие обоих заголовков MUST давать `403 CSRF_REJECTED`. Проверка включена всегда.

#### Scenario: Чужой источник

- **WHEN** клиент отправляет изменяющий запрос с заголовком `Origin` из недоверенного источника
- **THEN** система отвечает `403` с телом `{"code":"CSRF_REJECTED","message":"Источник запроса недопустим"}`
- **AND** состояние не меняется и сессия не создаётся

#### Scenario: Источник null

- **WHEN** клиент отправляет изменяющий запрос с заголовком `Origin: null`
- **THEN** система отвечает `403` с кодом ошибки `CSRF_REJECTED`

#### Scenario: Доверенный источник

- **GIVEN** источник запроса входит в список доверенных
- **WHEN** клиент отправляет изменяющий запрос
- **THEN** система обрабатывает запрос по правилам адреса

#### Scenario: Стандартный порт источника

- **GIVEN** в `TRUSTED_ORIGINS` указан `https://app.example.com`
- **WHEN** запрос приходит с `Origin: https://app.example.com:443`
- **THEN** источник считается доверенным

#### Scenario: Нестандартный порт источника

- **GIVEN** в `TRUSTED_ORIGINS` указан `https://app.example.com`
- **WHEN** запрос приходит с `Origin: https://app.example.com:8443`
- **THEN** система отвечает `403` с кодом ошибки `CSRF_REJECTED`

#### Scenario: Источник не определяется

- **WHEN** изменяющий запрос приходит без заголовков `Origin` и `Referer`
- **THEN** система отвечает `403` с кодом ошибки `CSRF_REJECTED`

### Requirement: Порядок проверки источника и сессии

Маршрут и метод запроса MUST определяться первыми: неизвестный маршрут MUST давать
`404 ROUTE_NOT_FOUND`. Для распознанного маршрута проверка источника изменяющего
запроса MUST выполняться раньше проверки входных данных, лимитов и сессии. Недоверенный
источник MUST давать ответ `403 CSRF_REJECTED` независимо от состояния тела, счётчиков и
наличия сессии. Предварительный запрос `OPTIONS` проверяется по тому же списку
источников (см. «CORS и preflight»).

#### Scenario: Недоверенный источник без сессии

- **GIVEN** клиент не имеет действующей сессии
- **WHEN** клиент отправляет изменяющий запрос с заголовком `Origin` из недоверенного источника
- **THEN** система отвечает `403` с кодом ошибки `CSRF_REJECTED`
- **AND** проверка сессии не выполняется

#### Scenario: Недоверенный источник с некорректным телом

- **WHEN** клиент отправляет изменяющий запрос с недоверенным источником и некорректным телом
- **THEN** система отвечает `403` с кодом ошибки `CSRF_REJECTED`

#### Scenario: Неизвестный маршрут с недоверенным источником

- **WHEN** клиент отправляет изменяющий запрос с недоверенным источником на неизвестный маршрут
- **THEN** система отвечает `404` с кодом ошибки `ROUTE_NOT_FOUND`

### Requirement: Публичные адреса

Адреса `GET /health`, `POST /auth/register`, `POST /auth/login` и `POST /auth/logout`
MUST быть доступны без сессии. Остальные адреса API MUST требовать действующей сессии по
умолчанию, и каждый такой адрес MUST быть помечен как закрытый явно. Ответ `GET /health`
MUST содержать тело `{"status":"ok","service":"api"}`.

#### Scenario: Проверка состояния без сессии

- **WHEN** клиент вызывает `GET /health` без cookie
- **THEN** система отвечает `200` с телом `{"status":"ok","service":"api"}`

#### Scenario: Закрытый адрес без сессии

- **WHEN** клиент вызывает закрытый адрес без cookie
- **THEN** система отвечает `401` с кодом ошибки `UNAUTHENTICATED`

### Requirement: CORS и preflight

API MUST отвечать на запросы с доверенного источника заголовками
`Access-Control-Allow-Origin` и `Access-Control-Allow-Credentials: true`. Список
источников MUST задаваться конфигурацией и проверяться при запуске: пустой список MUST
останавливать запуск. `OPTIONS` MUST обрабатываться без cookie: доверенный источник —
`204` с разрешающими заголовками; недоверенный, `Origin: null` или без `Origin` — `403
CSRF_REJECTED`; неизвестный адрес — `404`.

#### Scenario: Ответ с доверенного источника

- **WHEN** клиент отправляет запрос с заголовком `Origin` доверенного источника
- **THEN** ответ содержит `Access-Control-Allow-Origin` с этим источником
- **AND** ответ содержит `Access-Control-Allow-Credentials` со значением `true`

#### Scenario: Предварительный запрос

- **WHEN** браузер отправляет предварительный запрос `OPTIONS` известному адресу с доверенного источника
- **THEN** система отвечает `204` без тела
- **AND** ответ содержит заголовки, разрешающие методы и заголовки запроса

#### Scenario: Предварительный запрос с недоверенного источника

- **WHEN** браузер отправляет предварительный запрос `OPTIONS` известному адресу с недоверенного источника
- **THEN** система отвечает `403` с кодом ошибки `CSRF_REJECTED`

#### Scenario: Предварительный запрос без источника

- **WHEN** предварительный запрос `OPTIONS` к известному адресу приходит без `Origin`
- **THEN** система отвечает `403` с кодом ошибки `CSRF_REJECTED`

#### Scenario: Предварительный запрос к неизвестному адресу

- **WHEN** браузер отправляет предварительный запрос `OPTIONS` неизвестному адресу
- **THEN** система отвечает `404` с кодом ошибки `ROUTE_NOT_FOUND`

### Requirement: Недоступность Redis при работе с сессией

Если сессию нельзя создать, проверить или удалить из-за недоступности Redis, система
MUST отвечать `503 SERVICE_UNAVAILABLE` без технических подробностей. `503` MUST означать
возможный неизвестный исход: операция могла выполниться, а подтверждение — потеряться.
Повторная операция MUST быть безопасной: вход не ставит cookie, регистрация не
гарантирует откат (повтор может дать `409` → вход), выход не сбрасывает cookie,
идемпотентен и не утверждает, что сессия осталась активной.

#### Scenario: Вход при недоступном Redis

- **WHEN** клиент входит с верными учётными данными, а Redis недоступен
- **THEN** система отвечает `503` с телом `{"code":"SERVICE_UNAVAILABLE","message":"Сервис временно недоступен. Повторите позже."}`
- **AND** cookie сессии не устанавливается

#### Scenario: Регистрация при недоступном Redis

- **WHEN** клиент регистрируется, а Redis недоступен
- **THEN** система отвечает `503` с кодом ошибки `SERVICE_UNAVAILABLE`
- **AND** система не гарантирует откат уже созданной записи
- **AND** повторная регистрация того же адреса может дать `409 EMAIL_ALREADY_TAKEN`

#### Scenario: Запрос к закрытому ресурсу при недоступном Redis

- **WHEN** клиент выполняет запрос к закрытому ресурсу, а Redis недоступен
- **THEN** система отвечает `503` с кодом ошибки `SERVICE_UNAVAILABLE`

#### Scenario: Выход при недоступном Redis

- **WHEN** авторизованный клиент выходит, а Redis недоступен
- **THEN** система отвечает `503` с кодом ошибки `SERVICE_UNAVAILABLE`
- **AND** cookie не сбрасывается
- **AND** система не утверждает, что сессия осталась активной
- **AND** повторный выход безопасен, даже если сессия уже удалена

### Requirement: Недоступность Redis при работе со счётчиками лимитов

Ошибка чтения счётчика лимита или записи в счётчик MUST давать `503 SERVICE_UNAVAILABLE`.
Для входа при сбое записи неудачной попытки пароль уже проверен, но сессия MUST NOT
создаваться. Сбой сброса счётчиков после успешного входа MUST NOT отменять успех; ошибка
MUST попадать в журнал.

#### Scenario: Счётчик лимита недоступен

- **GIVEN** клиент выполняет попытку входа, а счётчик лимита не удаётся прочитать
- **WHEN** система проверяет ограничения
- **THEN** система отвечает `503` с кодом ошибки `SERVICE_UNAVAILABLE`
- **AND** учётные данные не проверяются

### Requirement: Непредвиденная ошибка

При непредвиденной ошибке система MUST отвечать `500` с кодом ошибки `INTERNAL_ERROR` и
MUST NOT раскрывать технические подробности в ответе. Подробности MUST попадать в
журнал.

#### Scenario: Непредвиденная ошибка

- **WHEN** обработка запроса завершается непредвиденной ошибкой
- **THEN** система отвечает `500` с телом `{"code":"INTERNAL_ERROR","message":"Внутренняя ошибка сервера"}`

### Requirement: Выход из сессии

Система MUST предоставлять выход по адресу `POST /auth/logout`. Тело не требуется и
игнорируется. При успехе система MUST отвечать `204` и сбрасывать cookie пустым значением
с `Max-Age=0`. Выход без cookie MUST завершаться `204` без обращения к хранилищу. Выход с
действующей сессией MUST удалять сессию. При `503` cookie MUST NOT сбрасываться, система
MUST NOT утверждать, что сессия осталась активной, а повтор MUST быть безопасен.

#### Scenario: Выход авторизованного пользователя

- **WHEN** авторизованный клиент вызывает `POST /auth/logout`
- **THEN** система отвечает `204` без тела
- **AND** сессия завершена, cookie сброшена пустым значением с `Max-Age=0`

#### Scenario: Выход без сессии

- **WHEN** клиент вызывает `POST /auth/logout` без cookie
- **THEN** система отвечает `204` без тела

### Requirement: Получение текущего пользователя

Система MUST предоставлять адрес `GET /users/current`. Авторизация MUST приниматься
только по cookie сессии, другие способы передачи учётных данных MUST NOT поддерживаться.
При действующей сессии система MUST отвечать `200` с телом
`{"user":{"uuid":"…","email":"…","name":"…","createdAt":"…"}}` без поля `password`.
Без действующей сессии система MUST отвечать `401` с кодом ошибки `UNAUTHENTICATED`.

#### Scenario: Текущий пользователь

- **GIVEN** пользователь вошёл в сессию
- **WHEN** клиент вызывает `GET /users/current`
- **THEN** система отвечает `200` с объектом пользователя
- **AND** объект не содержит поле `password`

#### Scenario: Без сессии

- **WHEN** клиент вызывает `GET /users/current` без cookie
- **THEN** система отвечает `401` с кодом ошибки `UNAUTHENTICATED`

### Requirement: Запрет кэширования ответов аутентификации

Все ответы адресов `POST /auth/register`, `POST /auth/login`, `POST /auth/logout` и
`GET /users/current` MUST содержать заголовок `Cache-Control: no-store`, включая ответы
с ошибками: промежуточный кэш не должен отдавать ответ с cookie другому клиенту.

#### Scenario: Успешный ответ не кэшируется

- **WHEN** система отвечает на успешный вход или регистрацию
- **THEN** в ответе присутствует заголовок `Cache-Control: no-store`

#### Scenario: Отказ не кэшируется

- **WHEN** система отвечает отказом на любом из адресов аутентификации
- **THEN** в ответе присутствует заголовок `Cache-Control: no-store`

#### Scenario: Текущий пользователь не кэшируется

- **WHEN** система отвечает на `GET /users/current`
- **THEN** в ответе присутствует заголовок `Cache-Control: no-store`
