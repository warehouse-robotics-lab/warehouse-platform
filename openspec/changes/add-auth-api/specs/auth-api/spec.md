# Spec Delta

## Purpose

Внешний HTTP-контракт API авторизации: регистрация, вход, выход и получение текущего
пользователя, единый формат ошибок, статусы ответов и защита входа от перебора пароля.

## ADDED Requirements

### Requirement: Тело ошибки

Система MUST отвечать на ошибку единым телом вида `{ "code", "message", "fields"? }`.
`code` MUST быть стабильным машинным кодом, `message` — кратким человекочитаемым текстом
без технических подробностей, `fields` — необязательным соответствием имён полей и кодов
ошибок этих полей. HTTP-статус MUST передаваться статусом ответа и MUST NOT
дублироваться в теле. Формат MUST применяться ко всем ошибкам API, включая неизвестный
маршрут и неподдерживаемый метод.

#### Scenario: Ошибка без привязки к полю

- **WHEN** запрос отклонён по причине, не связанной с конкретным полем
- **THEN** тело ответа содержит `code` и `message`
- **AND** объект `fields` отсутствует

#### Scenario: Неизвестный маршрут

- **WHEN** клиент обращается к неизвестному маршруту
- **THEN** система отвечает `404` в едином формате ошибки

#### Scenario: Неподдерживаемый метод

- **WHEN** клиент вызывает известный маршрут неподдерживаемым методом
- **THEN** система отвечает `405` в едином формате ошибки

### Requirement: Поле fields для ошибок формата

Поле `fields` MUST использоваться для ошибок формата и правил входных данных: оно
указывает, какое поле нарушило какое правило. Поле `fields` MUST NOT использоваться для
ошибок аутентификации: при отказе аутентификации тело ответа MUST NOT содержать `fields`,
поскольку неизвестно, какое поле «виновато», и это скрывается намеренно.

#### Scenario: Ошибка формата входных данных

- **WHEN** клиент отправляет email неверного формата
- **THEN** система отвечает `400`
- **AND** в `fields` для поля `email` указан код `EMAIL_INVALID`

#### Scenario: Ошибка аутентификации без fields

- **WHEN** вход отклонён
- **THEN** тело ответа содержит `code` и `message`
- **AND** объект `fields` отсутствует

### Requirement: Регистрация пользователя

Система MUST предоставлять регистрацию по адресу `POST /auth/register` с телом, содержащим
`email`, `password` и `name`. При успехе система MUST отвечать `201` с объектом
пользователя и MUST устанавливать cookie сессии. Объект пользователя в ответе MUST
содержать `uuid`, `email`, `name` и `createdAt` и MUST NOT содержать `password`.

#### Scenario: Успешная регистрация

- **WHEN** клиент отправляет корректные `email`, `password` и `name`
- **THEN** система отвечает `201` с объектом пользователя
- **AND** устанавливает cookie сессии

#### Scenario: Тело запроса некорректно

- **WHEN** тело запроса не является объектом с ожидаемыми полями
- **THEN** система отвечает `400` с кодом ошибки `INVALID_REQUEST`

### Requirement: Занятый email при регистрации

Если email уже сохранён у другого пользователя, система MUST отвечать `409` с кодом
ошибки `EMAIL_ALREADY_TAKEN` и MUST указывать этот код в `fields` для поля `email`.
Сравнение email MUST выполняться по нормализованному значению. Данные существующего
пользователя MUST NOT изменяться, новый пользователь MUST NOT создаваться.

#### Scenario: Email уже занят

- **GIVEN** существует пользователь с email `user@example.com`
- **WHEN** клиент регистрируется с тем же email в другом регистре
- **THEN** система отвечает `409` с кодом ошибки `EMAIL_ALREADY_TAKEN`
- **AND** в `fields` для поля `email` указан код `EMAIL_ALREADY_TAKEN`
- **AND** данные существующего пользователя не изменяются

#### Scenario: Email занят с пробелами и другим регистром

- **WHEN** клиент регистрируется с email `"  USER@Example.com  "`, а такой адрес уже сохранён
- **THEN** система отвечает `409` с кодом ошибки `EMAIL_ALREADY_TAKEN`

### Requirement: Некорректные данные регистрации

Если данные регистрации не проходят проверки `user-credentials`, система MUST отвечать
`400` и MUST перечислять в `fields` коды нарушений всех неверных полей. Пользователь в
этом случае MUST NOT создаваться.

#### Scenario: Слабый пароль

- **WHEN** клиент отправляет пароль, не удовлетворяющий требованиям
- **THEN** система отвечает `400`
- **AND** в `fields` для поля `password` указан код нарушения правил пароля

#### Scenario: Неверный формат email

- **WHEN** клиент отправляет email без символа `@`
- **THEN** система отвечает `400`
- **AND** в `fields` для поля `email` указан код `EMAIL_INVALID`

#### Scenario: Несколько неверных полей

- **WHEN** клиент отправляет неверные email, пароль и имя одновременно
- **THEN** система отвечает `400` и перечисляет в `fields` коды нарушений всех трёх полей

### Requirement: Единый ответ при отказе аутентификации

При отказе аутентификации система MUST отвечать `401` с кодом ошибки
`INVALID_CREDENTIALS` и сообщением «Неверная почта или пароль». Ответ MUST NOT
содержать `fields` и MUST NOT указывать, что именно не совпало. Несуществующий email,
неверный пароль и временная блокировка входа MUST давать одинаковый ответ.

#### Scenario: Неверный пароль

- **WHEN** клиент отправляет существующий `email` и неверный `password`
- **THEN** система отвечает `401` с кодом ошибки `INVALID_CREDENTIALS`
- **AND** cookie сессии не устанавливается

#### Scenario: Несуществующий email

- **WHEN** клиент отправляет несуществующий `email` и любой пароль
- **THEN** система отвечает `401` с кодом ошибки `INVALID_CREDENTIALS`

#### Scenario: Отказ не различает причины

- **GIVEN** клиент получил отказ аутентификации
- **WHEN** тело ответа отказа сравнивается с отказом по другой причине
- **THEN** код ошибки, сообщение и HTTP-статус совпадают

#### Scenario: Временная блокировка входа

- **WHEN** вход отклонён из-за превышения числа попыток
- **THEN** система отвечает `429` с кодом ошибки `TOO_MANY_ATTEMPTS`
- **AND** ответ не раскрывает, зарегистрирован ли email

### Requirement: Выход из сессии

Система MUST предоставлять выход по адресу `POST /auth/logout`. При успехе система MUST
отвечать `204` без тела. Выход без действующей сессии MUST завершаться тем же успешным
ответом.

#### Scenario: Выход авторизованного пользователя

- **WHEN** авторизованный клиент вызывает `POST /auth/logout`
- **THEN** система отвечает `204` без тела
- **AND** сессия завершена, cookie сброшена

#### Scenario: Выход без сессии

- **WHEN** клиент вызывает `POST /auth/logout` без cookie
- **THEN** система отвечает `204` без тела

### Requirement: Получение текущего пользователя

Система MUST предоставлять адрес `GET /users/current`. При действующей сессии система
MUST отвечать `200` с объектом пользователя без поля `password`. Без действующей сессии
система MUST отвечать `401` с кодом ошибки `UNAUTHENTICATED`.

#### Scenario: Текущий пользователь

- **GIVEN** пользователь вошёл в сессию
- **WHEN** клиент вызывает `GET /users/current`
- **THEN** система отвечает `200` с объектом пользователя
- **AND** объект не содержит поле `password`

#### Scenario: Без сессии

- **WHEN** клиент вызывает `GET /users/current` без cookie
- **THEN** система отвечает `401` с кодом ошибки `UNAUTHENTICATED`

### Requirement: Учёт неудачных попыток входа

Система MUST считать неудачные попытки входа отдельно для каждой пары `email` и IP
адреса клиента. Порог числа попыток и окно подсчёта MUST задаваться конфигурацией
(по умолчанию 5 попыток за 15 минут). Успешный вход MUST сбрасывать счётчик неудачных
попыток этой пары.

#### Scenario: Счётчик ведётся по паре email и IP

- **WHEN** один пользователь неудачно входит с одного IP
- **THEN** счётчик этой пары увеличивается, а счётчики других пар не меняются

#### Scenario: Сброс счётчика после успешного входа

- **GIVEN** для пары `email` и IP были неудачные попытки входа
- **WHEN** пользователь входит с верными учётными данными
- **THEN** счётчик неудачных попыток этой пары сбрасывается

### Requirement: Блокировка входа при превышении порога

Когда число неудачных попыток за заданное окно превышает заданный порог, система MUST
отклонять следующий вход ответом `429` с кодом ошибки `TOO_MANY_ATTEMPTS`. Срок
блокировки MUST задаваться конфигурацией (по умолчанию 15 минут) и MUST отсчитываться
с момента блокировки.

#### Scenario: Превышен порог попыток

- **GIVEN** для пары `email` и IP число неудачных попыток входа за заданное окно превысило заданный порог
- **WHEN** клиент выполняет ещё одну попытку входа
- **THEN** система отвечает `429` с кодом ошибки `TOO_MANY_ATTEMPTS`
- **AND** вход не проверяется и сессия не создаётся

#### Scenario: Блокировка действует заданный срок

- **GIVEN** вход отклонён из-за превышения порога
- **WHEN** клиент повторяет попытку до истечения заданного срока блокировки
- **THEN** система отвечает `429` с кодом ошибки `TOO_MANY_ATTEMPTS`

#### Scenario: Срок блокировки истёк

- **GIVEN** срок блокировки истёк
- **WHEN** клиент повторяет попытку входа
- **THEN** система проверяет учётные данные и при верных данных создаёт сессию

#### Scenario: Лимит не распространяется на другие пары

- **GIVEN** порог исчерпан для одной пары `email` и IP
- **WHEN** другой клиент входит с другой почтой с того же IP
- **THEN** система не отклоняет вход по лимиту этой пары
