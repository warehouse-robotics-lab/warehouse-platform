# Spec Delta

## Purpose

Хранение данных учётной записи пользователя: состав полей и их назначение, обязательность значений, уникальность и правила сравнения email, правила хранения пароля при входе по email и паролю. Операция сохранения получает готовый хеш пароля; хеширование исходного пароля — вне этой спецификации (см. design change `add-user-model`).

## ADDED Requirements

### Requirement: Состав данных пользователя

Система SHALL хранить запись пользователя с полями: `uuid` — постоянный уникальный идентификатор; `email` — почта для входа и связи с пользователем; `password` — готовый хеш пароля (см. «Хранение пароля»); `name` — отображаемое имя в интерфейсе; `createdAt`, `updatedAt` — время создания и изменения записи. Идентификатор и метки времени система MUST присваивать автоматически; их не задаёт вызывающая сторона.

#### Scenario: Создание пользователя со всеми полями

- **WHEN** создаётся пользователь с email, готовым хешем пароля и отображаемым именем
- **THEN** система сохраняет запись с полями `uuid`, `email`, `password`, `name`, `createdAt`, `updatedAt`
- **AND** `uuid` и метки времени заполнены системой автоматически

### Requirement: Обязательные значения

Поля `email`, `password` и `name` MUST быть заполнены непустыми значениями; под значением `password` понимается готовый хеш пароля. Система MUST отклонять запись пользователя, в которой хотя бы одно из них отсутствует или пусто.

#### Scenario: Создание без email

- **WHEN** создаётся пользователь без адреса почты или с пустым адресом
- **THEN** система отклоняет запись и не сохраняет пользователя

#### Scenario: Создание без пароля

- **WHEN** создаётся пользователь без готового хеша пароля в поле `password` или с пустым значением
- **THEN** система отклоняет запись и не сохраняет пользователя

#### Scenario: Создание без имени

- **WHEN** создаётся пользователь без отображаемого имени или с пустым именем
- **THEN** система отклоняет запись и не сохраняет пользователя

### Requirement: Формат email

Поле `email` MUST содержать адрес в формате электронной почты (локальная часть, символ `@`, домен). Система MUST отклонять значение, не соответствующее формату.

#### Scenario: Некорректный email

- **WHEN** создаётся пользователь с email без символа `@` или без домена, например `userexample.com`
- **THEN** система отклоняет запись с ошибкой формата и не сохраняет пользователя

### Requirement: Уникальность и сравнение email

Email MUST быть уникальным среди всех пользователей. Сравнение email система MUST выполнять без учёта регистра после удаления крайних пробелов: перед сохранением значение нормализуется (усечение пробелов и приведение к нижнему регистру), и сравнение идёт по нормализованному значению.

#### Scenario: Повторная регистрация с занятой почтой

- **WHEN** создаётся пользователь с email, который уже сохранён у другого пользователя
- **THEN** система отклоняет новую запись ошибкой уникальности
- **AND** данные существующего пользователя не изменяются

#### Scenario: Повторная почта в другом регистре

- **WHEN** существует пользователь с email `user@example.com`
- **AND** создаётся пользователь с email `USER@EXAMPLE.COM` или `User@Example.com`
- **THEN** система распознаёт адрес как занятый и отклоняет запись ошибкой уникальности

#### Scenario: Почта с крайними пробелами

- **WHEN** создаётся пользователь с email `"  user@example.com  "`
- **THEN** система сохраняет адрес в нормализованном виде `user@example.com`

### Requirement: Хранение пароля

Система MUST хранить пароль только в виде хеша и MUST NOT сохранять исходный (открытый) пароль ни в одном поле записи пользователя. Операция сохранения пользователя MUST принимать готовый хеш и сохранять значение поля `password` без изменений и повторного хеширования; исходный пароль в операцию сохранения не передаётся.

#### Scenario: Пароль сохраняется только как хеш

- **WHEN** создаётся пользователь с готовым хешем пароля
- **THEN** в сохранённой записи поле `password` содержит переданный хеш без изменений
- **AND** значение поля не вычисляется повторно (повторное хеширование не выполняется)
