# Design

## Context

Согласованный контракт уже находится в основных спецификациях:

- `openspec/specs/auth-api/spec.md` — адреса, статусы, тела, ошибки, заголовки и карта
  ответов;
- `openspec/specs/user-credentials/spec.md` — правила email, пароля и имени,
  нормализация и скрытие пароля;
- `openspec/specs/user-session/spec.md` — cookie сессии, которая документируется в
  ответах, но реализуется в B4/B5.

Обоснования взяты из `openspec/changes/archive/2026-11-27-add-auth-api/design.md`:
решение 3 (Zod-схемы в `@warehouse/contracts` + Swagger), решение 4 (формат ошибки и
справочник), решение 6 (пароль и нормализация) и решение 14 (карта контракта).

Текущее состояние: `packages/contracts` содержит только README; `apps/api` использует
Zod для окружения, но не имеет Swagger и контрактных схем; `apps/web` не зависит от
пакета. Реализация Change 1 не добавляет HTTP-обработчиков.

Порядок работы — ADR-002: спецификация согласована в PR #61; тесты передаются на
человеческое ревью; реализация начинается только после согласования тестов.

## Goals / Non-Goals

**Goals:**

- Один набор Zod-схем, типов и правил для API и Web.
- Различать ошибку структуры тела (`INVALID_REQUEST`) и ошибку правил полей
  (`VALIDATION_FAILED` с `fields`).
- Сохранить согласованные правила: email, пароль, имя, нормализация, кодовые точки,
  исходный пароль без изменений, разные правила `login` и `register`.
- Генерировать OpenAPI из тех же схем и публиковать его в API без фиктивных endpoint-ов.
- Сделать публичные экспорты пригодными для будущих F1/F2 без подключения форм сейчас.

**Non-Goals:**

- Redis, конфигурация B1, CORS/preflight, сессии, guard, CSRF, хеширование, лимиты,
  HTTP-обработчики.
- Клиентская валидация форм и транспорт Web → API.
- Выбор ts-rest/tRPC и топология развёртывания.
- Изменение согласованных требований и текстов сообщений.

## Decisions

### 1. Границы пакета и публичный API

`@warehouse/contracts` — приватный workspace-пакет с единственной точкой входа
`src/index.ts`. Публичные экспорты:

- `userSchema`, `userResponseSchema`, `User`, `UserResponse`;
- `registerRequestSchema`, `loginRequestSchema`, `RegisterRequest`, `LoginRequest`;
- `errorCodeSchema`, `fieldCodeSchema`, `fieldViolationsSchema`, `errorResponseSchema`,
  `errorResponseByCode`, `ErrorCode`, `FieldCode`, `FieldViolations`, `ErrorResponse`;
- `ERROR_MESSAGES`, `FIELD_CODE_ORDER`, `EMAIL_MAX_LENGTH`, `PASSWORD_MIN_LENGTH`,
  `PASSWORD_MAX_LENGTH`, `NAME_MIN_LENGTH`, `NAME_MAX_LENGTH`;
- `normalizeEmail`, `normalizeName`, `orderFieldCodes`, `createErrorResponse`;
- `validateRegisterRequest`, `validateLoginRequest`, `ValidationResult`.

Пакет не знает про NestJS, Redis, cookie и HTTP. Он описывает данные и правила,
которые одинаково нужны API и Web.

### 2. Две стадии проверки тела

Один Zod-схемой нельзя корректно различить «поле отсутствует» (`VALIDATION_FAILED` и
`REQUIRED`) и «поле неверного типа» (`INVALID_REQUEST`), поэтому валидатор выполняет две
стадии:

1. **Структура.** Тело приводится к JSON-объекту; `undefined` (пустое тело) заменяется
   на `{}`. Схема `z.object({...}).strict()` отклоняет не-объект, лишние поля и неверные
   типы. Любая такая ошибка даёт `INVALID_REQUEST` без `fields`.
2. **Правила полей.** Для строковых значений проверяются обязательность, нормализация
   email, длина в кодовых точках и состав. Нарушения собираются в `fields` как
   «поле → массив кодов»; сообщение — `VALIDATION_FAILED`.

Пустое тело (`undefined`) и `{}` дают `VALIDATION_FAILED` с `REQUIRED` для всех
обязательных полей. Пустая строка даёт только `REQUIRED` и не добавляет коды длины или
состава. `null` и не-объекты дают `INVALID_REQUEST`. Проверка `Content-Type` и разбор
JSON остаются в B2: контракт принимает уже разобранное значение.

### 3. Правила полей и нормализация

Правила соответствуют `user-credentials`:

- **Email:** нормализация — удаление крайних пробелов и приведение к нижнему регистру.
  После нормализации: непустая локальная часть, ровно один символ `@`, непустой домен,
  отсутствие пробелов, длина не более 254 кодовых точек. Точка в домене не требуется.
  Ошибка — `EMAIL_INVALID`, пустое значение — `REQUIRED`.
- **Пароль при регистрации:** от 8 до 36 кодовых точек, хотя бы одна цифра (`\p{Nd}`),
  одна заглавная и одна строчная буква (`\p{L}`), один специальный символ — любой
  символ, кроме буквы, цифры и `U+0020`. Пробел — обычный символ, но не специальный.
  Ошибки — `PASSWORD_TOO_SHORT`, `PASSWORD_TOO_LONG`, `PASSWORD_WEAK`.
- **Пароль при входе:** проверяются только наличие и непустота. Длина и состав не
  применяются, чтобы пароль, созданный по прежним правилам, продолжал работать.
  Пустое значение — `REQUIRED`.
- **Имя:** удаляются крайние пробелы, внутренние пробелы сохраняются. После обрезки —
  от 2 до 64 кодовых точек. Пустое значение — `REQUIRED`, иначе `NAME_TOO_SHORT` или
  `NAME_TOO_LONG`.
- **Сохранение значений:** нормализованные email и имя возвращаются в `data`; исходный
  пароль не обрезается, не приводится к регистру и не заменяется — он возвращается как
  есть. Хеширование и проверка хеша — B3.

Длина считается через `Array.from(value).length` (кодовые точки), а не через
`String.length`. Это защищает кириллицу и символы вне BMP от ложных ограничений.

Для объекта пользователя `createdAt` принимается только в канонической ISO 8601
UTC-записи с `Z`; смещение `+00:00` не принимается.

Порядок кодов в `fields` фиксирован: `REQUIRED`, затем коды длины, затем коды состава,
затем `EMAIL_ALREADY_TAKEN`. Валидатор добавляет коды в этом порядке; дополнительно
экспортируется `orderFieldCodes` для сборки ошибок из внешних источников.

### 4. Ошибки и справочник сообщений

`ERROR_MESSAGES` — единственный источник текстов, ровно по одному на код верхнего
уровня:

| Код | Статус | Сообщение |
| --- | --- | --- |
| `INVALID_REQUEST` | 400 | Некорректный запрос |
| `VALIDATION_FAILED` | 400 | Проверьте поля формы |
| `EMAIL_ALREADY_TAKEN` | 409 | Адрес уже зарегистрирован |
| `INVALID_CREDENTIALS` | 401 | Неверная почта или пароль |
| `UNAUTHENTICATED` | 401 | Требуется вход |
| `CSRF_REJECTED` | 403 | Источник запроса недопустим |
| `TOO_MANY_ATTEMPTS` | 429 | Слишком много попыток. Повторите позже. |
| `EMAIL_RATE_LIMITED` | 429 | Слишком много попыток. Повторите позже. |
| `REGISTRATION_RATE_LIMITED` | 429 | Слишком много попыток. Повторите позже. |
| `ROUTE_NOT_FOUND` | 404 | Маршрут не найден |
| `METHOD_NOT_ALLOWED` | 405 | Метод не поддерживается |
| `SERVICE_UNAVAILABLE` | 503 | Сервис временно недоступен. Повторите позже. |
| `INTERNAL_ERROR` | 500 | Внутренняя ошибка сервера |

Тело ошибки — `{ code, message, fields? }`; HTTP-статус в теле не дублируется.
`fields` допускается только у `VALIDATION_FAILED` (обязателен) и
`EMAIL_ALREADY_TAKEN` (обязателен, `{ email: ["EMAIL_ALREADY_TAKEN"] }`). У остальных
кодов `fields` отсутствует. `errorResponseByCode` содержит отдельную схему для каждого
кода, `errorResponseSchema` — их объединение. `createErrorResponse` подставляет текст из
справочника и сортирует коды.

Коды нарушений полей отдельного сообщения не имеют: текст для них выбирает клиент.

### 5. OpenAPI из тех же схем

Документ OpenAPI собирается в `apps/api/src/openapi/auth-openapi.ts` из экспортов
пакета, а не из ручных DTO. Успешные ответы берут `userResponseSchema`, ошибки —
`errorResponseByCode`; отдельных DTO-классов нет. Для схем используется
`z.toJSONSchema(schema, { target: "openapi-3.0", io: "input", unrepresentable: "any" })`.
Ограничения длины добавляются в JSON Schema через `.meta({ minLength, maxLength })`:
они описывают кодовые точки так же, как JSON Schema, и не влияют на runtime-проверку.

Документ содержит ровно четыре адреса и статусы из карты контракта:

- `POST /auth/register`: `201`, `400` (`INVALID_REQUEST`, `VALIDATION_FAILED`),
  `409 EMAIL_ALREADY_TAKEN`, `403 CSRF_REJECTED`, `429 REGISTRATION_RATE_LIMITED`,
  `503`, `500`, `404`, `405`;
- `POST /auth/login`: `200`, `400`, `401 INVALID_CREDENTIALS`, `403`,
  `429 TOO_MANY_ATTEMPTS`/`EMAIL_RATE_LIMITED`, `503`, `500`, `404`, `405`;
- `POST /auth/logout`: `204`, `403`, `503`, `500`, `404`, `405`;
- `GET /users/current`: `200`, `401 UNAUTHENTICATED`, `503`, `500`, `404`, `405`.

Статусы документируются по карте контракта; их поведение реализуется в B1–B9, а не в
Change 1. Заголовки ответов: `Cache-Control: no-store` у всех ответов; `Retry-After` у
`429`; `Allow` у `405`; `Set-Cookie` у успешных `201`/`200`. Их установка также
принадлежит B2/B4/B8/B9; Change 1 только документирует контракт. CORS/preflight,
`TRUSTED_ORIGINS` и CORS-заголовки относятся к B1 и в Change 1 не документируются и не
реализуются.
Тело `204` отсутствует. Запрос `POST /auth/logout` тела не требует и не описывает его.

Каждая операция получает `x-implementation-status: "not-implemented"` и описание, что
это контракт, а обработчик появится в B6–B8. Документация не выдаётся за работающие
endpoint-ы.

`apps/api/src/main.ts` публикует документ через `SwaggerModule.setup("docs", app,
document, { jsonDocumentUrl: "docs-json" })`. `SwaggerModule.createDocument` не
используется, потому что контроллеров авторизации ещё нет; фиктивные контроллеры не
создаются.

### 6. Сборка и подключение потребителей

- `packages/contracts` компилируется `tsc` в `dist` (CommonJS + `.d.ts`), потому что
  `apps/api` работает в CommonJS, а `apps/web` (Next.js) импортирует CommonJS без
  дополнительной настройки. `package.json` указывает `main`, `types` и `exports` на
  `dist`.
- `packages/contracts` получает скрипты `build`, `lint`, `typecheck`, `test` и
  собственный `tsconfig`/ESLint-конфиг по образцу API.
- `apps/api` и `apps/web` добавляют `"@warehouse/contracts": "workspace:*"`.
- В `turbo.json` задачи `dev`, `typecheck`, `test` и `build` учитывают сборку
  workspace-зависимостей (`^build`), чтобы `dist` пакета существовал до запуска
  потребителей. Это изменение конфигурации, а не поведения авторизации.
- `apps/web` получает тонкий модуль-реэкспорт публичных типов и схем. Формы его пока не
  используют; это проверяет, что Web импортирует публичный экспорт, и не тянет
  авторизацию в UI.
- README пакета, API и Web описывают назначение, команды, `/docs`, `/docs-json` и то,
  что формы к API не подключены.
- Версии TypeScript, ESLint и Zod берутся из проекта. `@nestjs/swagger` — новая
  зависимость; выбирается версия, совместимая с Nest 11, и фиксируется в общем
  `pnpm-lock.yaml`. Других версий и инструментов не добавляется.

## Testing Strategy

- **`packages/contracts`:** тесты на `node:test` + `node:assert/strict`, собранные
  `tsc` в отдельный каталог и запущенные `node --test`. Так пакет не получает нового
  тестового фреймворка; используется только TypeScript и Node.
- **`apps/api`:** тест генерации OpenAPI на существующем Jest. Он не поднимает Nest и
  проверяет документ как данные: пути, методы, схемы, статусы, заголовки и пометку
  «контракт без реализации». Поведение Redis, сессий, лимитов и обработчиков этот тест
  не проверяет — оно принадлежит B1–B9.
- **Потребители:** `typecheck` и `build` API и Web подтверждают импорт публичных
  экспортов. Отдельного теста Web нет, потому что тестовый скрипт у Web пока не
  объявлен; это ограничение фиксируется в PR.
- **Матрица «Scenario → тест»:** `openspec/changes/add-auth-contracts/test-matrix.md`.
  Она состоит из трёх частей: тесты схем и правил Change 1, тесты документации OpenAPI и
  раздел «Вне Change 1» с владельцами B1–B9/F1–F7 без тестов.

## Risks / Trade-offs

- [`z.toJSONSchema` для `openapi-3.0` не выражает часть проверок] → ограничения длины
  вынесены в `.meta`, остальные правила описаны текстом; поведение проверяется тестами
  валидаторов, а не только JSON Schema.
- [Строгая схема отклоняет лишние поля] → это согласованное решение из `auth-api`;
  новая версия клиента и API обновляются вместе.
- [CommonJS-сборка пакета] → соответствует текущему API; если Web или будущий пакет
  потребует ESM, экспорты можно расширить без изменения схем.
- [Swagger без контроллеров] → документ собирается из контракта, поэтому не отражает
  будущие изменения Nest автоматически; тест OpenAPI удерживает карту контракта.
- [Порядок сборки в dev] → `^build` добавляет шаг сборки контрактов; это осознанная
  плата за отсутствие дублирования схем.
- [Тесты контракта не проверяют HTTP-поведение] → это граница Change 1; статусы,
  cookie, Redis, CSRF и лимиты проверяются в B1–B9.

## Open Questions

Открытых вопросов нет. Зафиксировано:

- email содержит ровно один `@`; несколько `@` дают `EMAIL_INVALID`;
- `createdAt` принимается только в канонической ISO 8601 UTC-записи с `Z`; `+00:00`
  не принимается.

Если при реализации обнаружится расхождение согласованных требований, оно оформляется
коротким вопросом Стасу, а зависимая часть останавливается.
