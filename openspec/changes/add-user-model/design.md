# Design

## Context

Этот change — spec-only: готовится и согласовывается спецификация данных пользователя, реализация будет отдельным будущим change. Способ входа согласован при подготовке change: **email + пароль**; подтверждение фиксируется на ревью спецификации. Продуктовые требования (`docs/product-requirements.md`) задают стек будущего бэкенда (NestJS, PostgreSQL, `prisma / typeorm`), но выбор инструмента и подключение — за реализацией. Порядок согласования — [ADR-002](../../../docs/adr/002-ai-development-workflow.md) (Accepted).

Требования к поведению — в `specs/user-account/spec.md`; здесь зафиксированы только решения по самим данным, чтобы после согласования было «понятно, какую модель создать в Prisma и какие ограничения проверить».

## Goals / Non-Goals

**Goals:**

- Зафиксировать решения по данным пользователя, достаточные для будущей реализации модели: состав полей, назначение, обязательность, правила email.
- Оставить решение, которое не блокирует добавление OAuth и Telegram позже.

**Non-Goals:**

- Подключение Prisma, базы данных, миграции, тестов и инфраструктуры — всё это реализация в следующем change.
- Выбор алгоритма хеширования пароля — приходит вместе с задачей регистрации/входа; модель хранит готовый хеш.
- Эндпоинты, сессии, JWT, роли, приглашения.

## Decisions

### 1. Поля пользователя

`uuid` (уникальный идентификатор, генерируется системой), `email` (вход и связь), `password` (данные пароля для входа; хранится только хеш — см. решение 4), `name` (отображаемое имя), `createdAt`, `updatedAt` (метки времени, заполняются системой). Набор минимален для входа по email и паролю и не мешает расширению: OAuth добавляется отдельной таблицей провайдеров, Telegram — опциональными полями или отдельной таблицей привязок, без изменения уже согласованных правил.

### 2. Идентификатор: поле `uuid`

Поле идентификатора называется `uuid` и имеет формат uuid, генерируется системой (`uuid String @id @default(uuid())` в эскизе ниже). Формат выбран при обсуждении change (2026-11-12): стандарт, генерируемый где угодно без координации; альтернатива cuid короче и приближённо упорядочена по времени создания, но в масштабе проекта разница несущественна. Имя поля `uuid` вместо конвенционального `id` — решение владельца продукта (2026-11-12) вопреки рекомендации: имя поля привязано к формату значения, и при гипотетической смене формата на не-uuid поле пришлось бы переименовывать. Внутри uuid возможен переход на uuid v7 без смены имени и формата поля, если индексная локальность станет важна.

### 3. Правила email: нормализация + уникальность

- Обязательное поле, формат почты.
- Уникальность среди всех пользователей.
- Сравнение без учёта регистра после усечения крайних пробелов; сохранение в нормализованном виде (нижний регистр, без крайних пробелов).

Правило «одно место нормализации при записи + проверка уникальности» фиксируется в спецификации; конкретный механизм (нормализация в коде, `citext`, функциональный индекс) — решение реализации.

### 4. Хранение пароля и имя поля

Только хеш, пароль в открытом виде не хранится нигде. Поле называется `password` — решение принято при обсуждении change (2026-11-12) вопреки рекомендации `passwordHash`: имя перестаёт сообщать о содержимом само по себе, поэтому инвариант «только хеш» держится текстом спецификации (`user-account`), обязательной проверкой в сервисном слое при записи и вниманием ревьюеров (см. риски). В пользу `password` было учтено пожелание владельца продукта о простом имени; имя не привязано к алгоритму хеширования, его смена модель не меняет.

### 5. Эскиз модели для следующего change (справочно)

Чтобы после согласования было понятно, что создавать, зафиксирован ожидаемый вид модели в Prisma:

```prisma
model User {
  uuid      String   @id @default(uuid())
  email     String   @unique
  password  String
  name      String
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}
```

Эскиз не является реализацией и может уточняться в change-реализации (типы длин, способ нормализации) без пересогласования этой спецификации, если требования `user-account` не меняются.

## Risks / Trade-offs

- [Спецификация описывает данные без реализации] → до первого change-реализации правила проверяются только ревью, не тестами. Митигация: сценарии спецификации сформулированы как будущие тест-кейсы.
- [Поле `password` хранит только хеш, но имя об этом не сообщает] → риск записи открытого пароля при поспешной реализации. Митигация: инвариант зафиксирован в требовании «Хранение пароля» спецификации, сценарий «Пароль сохраняется только как хеш» становится тест-кейсом, а сервисный слой записи обязан принимать пароль и хешировать его сам, не доверяя вызывающей стороне.
- [Решения по данным принимаются до появления смежных модулей (склады, роли)] → возможна корректировка при последующих спецификациях. Митигация: сущности складов и ролей будут отдельными capability; `User` хранит только собственные данные учётной записи.

## Open Questions

- Требуется ли продуктовое ограничение длины `name` и максимальной длины email, или достаточно валидации формата — можно решить на ревью или в change-реализации, на правила спецификации не влияет.
