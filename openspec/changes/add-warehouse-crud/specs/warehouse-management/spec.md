# Spec Delta

## Purpose

Пользователь управляет только собственными складами через защищённый HTTP API,
а данные склада сохраняются в PostgreSQL между перезапусками API.

## ADDED Requirements

### Requirement: Примеры HTTP-контракта

API SHALL поддерживать следующие примеры HTTP-контракта. Во всех ошибках тело
MUST соответствовать единому формату из согласованного auth-контракта.

#### Scenario: Примеры успешных ответов и ошибок

- **WHEN** клиент отправляет запрос из таблицы в указанном состоянии
- **THEN** API возвращает указанные статус и тело ответа

| Ситуация | Запрос | Ответ |
| --- | --- | --- |
| Создание | `POST /warehouses` с `{"name":"Основной склад"}` | `201` и `{"uuid":"7d7cc15c-4260-4dcb-94c5-58aa5b364ed6","name":"Основной склад","createdAt":"2026-11-21T10:00:00.000Z","updatedAt":"2026-11-21T10:00:00.000Z"}` |
| Список | `GET /warehouses` | `200` и массив представлений складов |
| Получение | `GET /warehouses/7d7cc15c-4260-4dcb-94c5-58aa5b364ed6` | `200` и представление склада |
| Переименование | `PATCH /warehouses/7d7cc15c-4260-4dcb-94c5-58aa5b364ed6` с `{"name":"Склад № 1"}` | `200` и представление с новым именем |
| Удаление | `DELETE /warehouses/7d7cc15c-4260-4dcb-94c5-58aa5b364ed6` | `204` без тела |
| Пустое имя | `POST /warehouses` с `{"name":"   "}` | `400` и `{"code":"VALIDATION_FAILED","message":"Проверьте поля формы","fields":{"name":["REQUIRED"]}}` |
| Лишний владелец | `POST /warehouses` с `{"name":"Основной склад","ownerUuid":"…"}` | `400` и `{"code":"INVALID_REQUEST","message":"Некорректный запрос"}` |
| Отсутствующий или чужой склад | `GET /warehouses/7d7cc15c-4260-4dcb-94c5-58aa5b364ed6` для отсутствующего либо чужого склада | `404` и `{"code":"WAREHOUSE_NOT_FOUND","message":"Склад не найден"}` |

#### Scenario: Пример чужого склада не раскрывает его существование

- **GIVEN** UUID принадлежит другому пользователю либо не существует
- **WHEN** клиент получает склад по этому UUID
- **THEN** API возвращает одинаковые статус `404` и тело ошибки

### Requirement: Представление склада

Система SHALL хранить склад с системным UUID, именем, владельцем-пользователем
и метками `createdAt` и `updatedAt`. В HTTP-ответе склада MUST быть только
`uuid`, `name`, `createdAt` и `updatedAt`; UUID владельца не раскрывается.

#### Scenario: Создание возвращает представление склада

- **WHEN** аутентифицированный пользователь создаёт склад с допустимым именем
- **THEN** API возвращает `201` с UUID, именем и метками времени в ISO 8601
- **AND** UUID и метки времени назначены сервером

#### Scenario: Склад сохраняется после перезапуска API

- **WHEN** пользователь создаёт склад, а API перезапускается
- **THEN** последующее получение этого склада тем же пользователем возвращает
  сохранённые UUID и имя

### Requirement: Валидация имени и входного тела

Создание и переименование MUST принимать строго объект только с полем `name`.
Система SHALL удалить крайние пробелы, а итоговое имя MUST содержать от 1 до
100 символов. Неверное тело, невалидный UUID пути и лишние поля MUST
возвращать `400` в согласованной с авторизацией оболочке ошибки.

#### Scenario: Имя нормализуется перед сохранением

- **WHEN** пользователь создаёт или переименовывает склад с именем
  `  Основной склад  `
- **THEN** API сохраняет и возвращает имя `Основной склад`

#### Scenario: Пустое или слишком длинное имя отклоняется

- **WHEN** пользователь передаёт имя из пробелов или длиной более 100 символов
- **THEN** API возвращает `400`
- **AND** создание или изменение склада не происходит

#### Scenario: Клиент пытается передать владельца

- **WHEN** пользователь передаёт `ownerUuid` или другое поле помимо `name`
- **THEN** API возвращает `400`
- **AND** переданное значение не влияет на владельца или данные склада

### Requirement: Аутентификация и владение

Все операции со складами MUST использовать согласованный механизм
аутентификации из #39/#40. Владельцем при создании SHALL становиться текущий
аутентифицированный пользователь; клиент MUST NOT назначать владельца.

#### Scenario: Неаутентифицированный запрос

- **WHEN** запрос к любому маршруту складов не содержит действительной
  аутентификации
- **THEN** API возвращает согласованный `401`

#### Scenario: Чужой склад не раскрывается

- **GIVEN** склад принадлежит пользователю A
- **WHEN** пользователь B получает, изменяет или удаляет UUID этого склада
- **THEN** API возвращает `404`
- **AND** склад пользователя A не изменяется

### Requirement: Порядок проверки источника и сессии

Для распознанного маршрута `POST`, `PATCH` или `DELETE` система MUST проверить
`Origin` либо `Referer` раньше тела, UUID и сессии. Недоверенный источник MUST
давать `403 CSRF_REJECTED`; при доверенном или отсутствующем источнике отсутствие
сессии MUST давать `401 UNAUTHENTICATED`, а недоступность проверки сессии —
`503 SERVICE_UNAVAILABLE`.

#### Scenario: Изменение с недоверенным источником без сессии

- **WHEN** клиент без сессии отправляет `PATCH /warehouses/:uuid` с
  недоверенным `Origin`
- **THEN** API возвращает `403` с кодом `CSRF_REJECTED`
- **AND** проверка сессии, UUID и тела не выполняется

#### Scenario: Изменение без сессии после допустимой проверки источника

- **WHEN** клиент отправляет `PATCH /warehouses/:uuid` без сессии и с
  доверенным `Origin` либо без `Origin` и `Referer`
- **THEN** API возвращает `401` с телом
  `{"code":"UNAUTHENTICATED","message":"Требуется вход"}`

#### Scenario: Сессию невозможно проверить

- **WHEN** клиент с допустимым источником обращается к защищённому складу, а
  Redis недоступен при проверке сессии
- **THEN** API возвращает `503` с телом
  `{"code":"SERVICE_UNAVAILABLE","message":"Сервис временно недоступен. Повторите позже."}`

### Requirement: Создание и список собственных складов

`POST /warehouses` SHALL создавать склад текущего пользователя. `GET
/warehouses` SHALL возвращать `200` с полным массивом только его складов без
пагинации, отсортированным по `createdAt` от новых к старым.

#### Scenario: Пустой список

- **WHEN** пользователь без складов запрашивает `GET /warehouses`
- **THEN** API возвращает `200` и пустой массив

#### Scenario: Список изолирован и отсортирован

- **GIVEN** у пользователя A есть два склада, созданные последовательно, а у
  пользователя B есть один склад
- **WHEN** пользователь A запрашивает `GET /warehouses`
- **THEN** API возвращает только два склада пользователя A, начиная с нового

### Requirement: Получение и переименование своего склада

`GET /warehouses/:uuid` SHALL возвращать собственный склад с `200`. `PATCH
/warehouses/:uuid` SHALL заменять его имя допустимым значением и возвращать
обновлённое представление с `200`.

#### Scenario: Пользователь получает свой склад

- **WHEN** пользователь запрашивает UUID принадлежащего ему склада
- **THEN** API возвращает `200` и его представление

#### Scenario: Пользователь переименовывает свой склад

- **WHEN** пользователь отправляет допустимое новое имя в
  `PATCH /warehouses/:uuid` своего склада
- **THEN** API возвращает `200` с новым именем и обновлённой меткой `updatedAt`

### Requirement: Удаление и отсутствие склада

`DELETE /warehouses/:uuid` SHALL удалять собственный склад и возвращать `204`
без тела. Валидный UUID отсутствующего, чужого или уже удалённого склада MUST
возвращать единый `404`; это поведение не раскрывает существование чужих данных.

#### Scenario: Удаление своего склада

- **WHEN** пользователь удаляет принадлежащий ему склад
- **THEN** API возвращает `204` без тела
- **AND** последующий список пользователя не содержит этот склад

#### Scenario: Повторное удаление

- **WHEN** пользователь повторно удаляет UUID уже удалённого склада
- **THEN** API возвращает `404`

#### Scenario: Невалидный UUID

- **WHEN** пользователь передаёт UUID пути в неверном формате
- **THEN** API возвращает `400`
