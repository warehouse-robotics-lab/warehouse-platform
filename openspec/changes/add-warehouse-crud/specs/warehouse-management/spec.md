# Spec Delta

## Purpose

Пользователь управляет только собственными складами через защищённый HTTP API,
а данные склада сохраняются в PostgreSQL между перезапусками API.

## ADDED Requirements

### Requirement: Примеры HTTP-контракта

API SHALL поддерживать следующие примеры HTTP-контракта. Во всех ошибках тело
MUST соответствовать единому формату из согласованного auth-контракта.

#### Scenario: Примеры успешных ответов и ошибок

- **WHEN** клиент отправляет запрос из таблицы в указанном состоянии
- **THEN** API возвращает указанные статус и тело ответа

| Ситуация | Запрос | Ответ |
| --- | --- | --- |
| Создание | `POST /warehouses` с `{"name":"Основной склад"}` | `201` и `{"warehouse":{"uuid":"7d7cc15c-4260-4dcb-94c5-58aa5b364ed6","name":"Основной склад","createdAt":"2026-11-21T10:00:00.000Z","updatedAt":"2026-11-21T10:00:00.000Z"}}` |
| Повторяющееся имя | `POST /warehouses` с `{"name":"Основной склад"}`, когда у пользователя уже есть склад с тем же именем | `201` и `{"warehouse":{"uuid":"f714dfe6-7625-4beb-9d7e-b8f04d6d3615","name":"Основной склад","createdAt":"2026-11-21T11:00:00.000Z","updatedAt":"2026-11-21T11:00:00.000Z"}}` |
| Пустой список | `GET /warehouses` | `200` и `{"warehouses":[]}` |
| Список | `GET /warehouses` | `200` и `{"warehouses":[{"uuid":"f714dfe6-7625-4beb-9d7e-b8f04d6d3615","name":"Новый склад","createdAt":"2026-11-21T11:00:00.000Z","updatedAt":"2026-11-21T11:00:00.000Z"},{"uuid":"7d7cc15c-4260-4dcb-94c5-58aa5b364ed6","name":"Основной склад","createdAt":"2026-11-21T10:00:00.000Z","updatedAt":"2026-11-21T10:00:00.000Z"}]}` |
| Получение | `GET /warehouses/7d7cc15c-4260-4dcb-94c5-58aa5b364ed6` | `200` и `{"warehouse":{"uuid":"7d7cc15c-4260-4dcb-94c5-58aa5b364ed6","name":"Основной склад","createdAt":"2026-11-21T10:00:00.000Z","updatedAt":"2026-11-21T10:00:00.000Z"}}` |
| Переименование | `PATCH /warehouses/7d7cc15c-4260-4dcb-94c5-58aa5b364ed6` с `{"name":"Склад № 1"}` | `200` и `{"warehouse":{"uuid":"7d7cc15c-4260-4dcb-94c5-58aa5b364ed6","name":"Склад № 1","createdAt":"2026-11-21T10:00:00.000Z","updatedAt":"2026-11-21T11:30:00.000Z"}}` |
| Удаление | `DELETE /warehouses/7d7cc15c-4260-4dcb-94c5-58aa5b364ed6` | `204` без тела |
| Отсутствующее или пустое имя | `POST /warehouses` с `{}`, `PATCH /warehouses/:uuid` без тела либо `POST /warehouses` с `{"name":"   "}` | `400` и `{"code":"VALIDATION_FAILED","message":"Проверьте поля формы","fields":{"name":["REQUIRED"]}}` |
| Слишком длинное имя | `POST /warehouses` с `name` длиной более 100 Unicode code points после `String.prototype.trim()` | `400` и `{"code":"VALIDATION_FAILED","message":"Проверьте поля формы","fields":{"name":["NAME_TOO_LONG"]}}` |
| Неверная структура тела | `POST /warehouses` с `{"name":123}`, `{"name":null}`, массивом либо `null` | `400` и `{"code":"INVALID_REQUEST","message":"Некорректный запрос"}` |
| Лишний владелец | `POST /warehouses` с `{"name":"Основной склад","ownerUuid":"…"}` | `400` и `{"code":"INVALID_REQUEST","message":"Некорректный запрос"}` |
| Неверный UUID | `GET /warehouses/abc` | `400` и `{"code":"INVALID_REQUEST","message":"Некорректный запрос"}` |
| Отсутствующий или чужой склад | `GET /warehouses/7d7cc15c-4260-4dcb-94c5-58aa5b364ed6` для отсутствующего либо чужого склада | `404` и `{"code":"WAREHOUSE_NOT_FOUND","message":"Склад не найден"}` |

#### Scenario: Пример чужого склада не раскрывает его существование

- **GIVEN** UUID принадлежит другому пользователю либо не существует
- **WHEN** клиент получает склад по этому UUID
- **THEN** API возвращает одинаковые статус `404` и тело ошибки

### Requirement: Представление склада

Система SHALL хранить склад с системным UUID, именем, владельцем-пользователем
и метками `createdAt` и `updatedAt`. В HTTP-ответе одиночный склад MUST быть
вложен в поле `warehouse`, а список — в поле `warehouses`. Представление склада
MUST содержать только `uuid`, `name`, `createdAt` и `updatedAt`; UUID владельца
не раскрывается.

#### Scenario: Создание возвращает представление склада

- **WHEN** аутентифицированный пользователь создаёт склад с допустимым именем
- **THEN** API возвращает `201` с UUID, именем и метками времени в ISO 8601
  в поле `warehouse`
- **AND** UUID и метки времени назначены сервером

#### Scenario: Склад сохраняется после перезапуска API

- **WHEN** пользователь создаёт склад, а API перезапускается
- **THEN** последующее получение этого склада тем же пользователем возвращает
  сохранённые UUID и имя

### Requirement: Нормализация и длина имени

Перед проверкой и сохранением система SHALL нормализовать `name` методом
ECMAScript `String.prototype.trim()`. Итоговое имя MUST содержать от 1 до 100
Unicode code points; длина MUST NOT считаться в UTF-16 units или grapheme
clusters. Отсутствующее, пустое после нормализации или слишком длинное имя MUST
давать `400 VALIDATION_FAILED` с кодом в `fields.name`.

#### Scenario: Имя нормализуется перед сохранением

- **WHEN** пользователь создаёт или переименовывает склад с именем
  `\tОсновной склад\u00A0\n`
- **THEN** API сохраняет и возвращает имя `Основной склад`
- **AND** `String.prototype.trim()` удаляет начальные и конечные `WhiteSpace`
  и `LineTerminator` code points, включая `U+0020`, `U+0009`, `U+000A`,
  `U+000D` и `U+00A0`

#### Scenario: Внутренние whitespace code points сохраняются

- **WHEN** пользователь создаёт склад с именем `Основной\tсклад`
- **THEN** API сохраняет и возвращает `Основной\tсклад` без замены табуляции

#### Scenario: 100 Unicode code points допустимы

- **WHEN** пользователь передаёт имя из 100 символов `😀` после нормализации
- **THEN** API принимает имя, хотя в UTF-16 оно занимает 200 units

#### Scenario: Более 100 Unicode code points отклоняются

- **WHEN** пользователь передаёт имя из 101 символа `😀` после нормализации
- **THEN** API возвращает `400 VALIDATION_FAILED` с
  `{"name":["NAME_TOO_LONG"]}` в `fields`

#### Scenario: Отсутствующее или пустое имя отклоняется

- **WHEN** пользователь не передаёт `name`, отправляет пустое тело либо имя из
  пробелов
- **THEN** API возвращает `400 VALIDATION_FAILED` с
  `{"name":["REQUIRED"]}` в `fields`
- **AND** создание или изменение склада не происходит

#### Scenario: Слишком длинное имя отклоняется

- **WHEN** пользователь передаёт имя длиной более 100 символов после trim
- **THEN** API возвращает `400 VALIDATION_FAILED` с
  `{"name":["NAME_TOO_LONG"]}` в `fields`
- **AND** создание или изменение склада не происходит

### Requirement: Структура тела и UUID пути

Создание и переименование MUST принимать строго объект только с полем `name`.
Не-объектное тело, нестроковое `name`, лишние поля и невалидный UUID пути MUST
давать `400 INVALID_REQUEST` без `fields`.

#### Scenario: Некорректная структура тела отклоняется

- **WHEN** пользователь передаёт не-объектное тело, нестроковое `name` или
  лишнее поле
- **THEN** API возвращает `400 INVALID_REQUEST` без `fields`
- **AND** создание или изменение склада не происходит

#### Scenario: Клиент пытается передать владельца

- **WHEN** пользователь передаёт `ownerUuid` или другое поле помимо `name`
- **THEN** API возвращает `400 INVALID_REQUEST` без `fields`
- **AND** переданное значение не влияет на владельца или данные склада

### Requirement: Аутентификация и владение

Все операции со складами MUST использовать согласованный механизм
аутентификации из #39/#40. Владельцем при создании SHALL становиться текущий
аутентифицированный пользователь; клиент MUST NOT назначать владельца. Для
распознанного маршрута складов проверка сессии MUST завершиться до проверки
UUID, тела и области владения.

#### Scenario: Неаутентифицированный запрос

- **WHEN** запрос к распознанному маршруту складов не содержит сессии
- **THEN** API возвращает `401 UNAUTHENTICATED` до проверки UUID, тела и
  существования склада

#### Scenario: Чужой склад не раскрывается

- **GIVEN** склад принадлежит пользователю A
- **WHEN** пользователь B получает, изменяет или удаляет UUID этого склада
- **THEN** API возвращает `404`
- **AND** склад пользователя A не изменяется

### Requirement: Порядок маршрута, метода и источника

Система MUST сначала распознать маршрут и метод. Неизвестный маршрут и
неподдерживаемый метод MUST вернуть ответы общего auth-контракта до проверки
источника и сессии. Для распознанного `POST`, `PATCH` или `DELETE` система MUST
затем проверить `Origin` либо при его отсутствии `Referer`. Недоверенный
источник MUST дать `403 CSRF_REJECTED` до сессии, UUID и тела.

#### Scenario: Изменение с недоверенным источником без сессии

- **WHEN** клиент без сессии отправляет `PATCH /warehouses/:uuid` с
  недоверенным `Origin`
- **THEN** API возвращает `403` с кодом `CSRF_REJECTED`
- **AND** проверка сессии, UUID и тела не выполняется

#### Scenario: Неизвестный маршрут не проверяет источник

- **WHEN** клиент отправляет `POST /unknown` с недоверенным `Origin`
- **THEN** API возвращает `404 ROUTE_NOT_FOUND`, а не `403 CSRF_REJECTED`

### Requirement: Порядок сессии и данных

Для `GET`, а также после доверенного или отсутствующего источника изменяющего
запроса, система MUST проверить сессию до UUID, тела и области владения.
Отсутствующая сессия MUST дать `401 UNAUTHENTICATED`; если предъявленную сессию
невозможно проверить из-за недоступности Redis, API MUST дать
`503 SERVICE_UNAVAILABLE`. Только после действительной сессии проверяются UUID
и тело (`400`), затем склад в области текущего владельца (`404`).

#### Scenario: Изменение без сессии после допустимой проверки источника

- **WHEN** клиент отправляет `PATCH /warehouses/:uuid` без сессии и с
  доверенным `Origin` либо без `Origin` и `Referer`
- **THEN** API возвращает `401` с телом
  `{"code":"UNAUTHENTICATED","message":"Требуется вход"}`
- **AND** проверка UUID, тела и склада не выполняется

#### Scenario: GET без сессии не раскрывает ошибку UUID

- **WHEN** клиент без сессии запрашивает `GET /warehouses/abc`
- **THEN** API возвращает `401 UNAUTHENTICATED`, а не `400 INVALID_REQUEST`

#### Scenario: Сессию невозможно проверить

- **WHEN** клиент предъявляет сессию при обращении к защищённому складу с
  допустимым источником, а Redis недоступен при её проверке
- **THEN** API возвращает `503` с телом
  `{"code":"SERVICE_UNAVAILABLE","message":"Сервис временно недоступен. Повторите позже."}`
- **AND** проверка UUID, тела и склада не выполняется

#### Scenario: Действительная сессия предшествует проверке данных

- **GIVEN** у клиента есть действительная сессия
- **WHEN** он запрашивает `GET /warehouses/abc`
- **THEN** API возвращает `400 INVALID_REQUEST`

### Requirement: Создание и список собственных складов

`POST /warehouses` SHALL создавать склад текущего пользователя. `GET
/warehouses` SHALL возвращать `200` с полным массивом только его складов в
поле `warehouses`, без пагинации, отсортированным по `createdAt` от новых к
старым.

#### Scenario: Пустой список

- **WHEN** пользователь без складов запрашивает `GET /warehouses`
- **THEN** API возвращает `200` и `{"warehouses":[]}`

#### Scenario: Список изолирован и отсортирован

- **GIVEN** у пользователя A есть два склада, созданные последовательно, а у
  пользователя B есть один склад
- **WHEN** пользователь A запрашивает `GET /warehouses`
- **THEN** API возвращает их в поле `warehouses`, начиная с нового

#### Scenario: Имена складов не уникальны

- **GIVEN** у пользователя уже есть склад с именем `Основной склад`
- **WHEN** он создаёт второй склад с тем же нормализованным именем или
  переименовывает в него другой свой склад
- **THEN** API создаёт или обновляет склад без `409`
- **AND** записи различаются UUID

### Requirement: Получение и переименование своего склада

`GET /warehouses/:uuid` SHALL возвращать собственный склад с `200` в поле
`warehouse`. `PATCH /warehouses/:uuid` SHALL заменять его имя допустимым
значением и возвращать обновлённое представление в поле `warehouse` с `200`.

#### Scenario: Пользователь получает свой склад

- **WHEN** пользователь запрашивает UUID принадлежащего ему склада
- **THEN** API возвращает `200` и его представление в поле `warehouse`

#### Scenario: Пользователь переименовывает свой склад

- **WHEN** пользователь отправляет допустимое новое имя в
  `PATCH /warehouses/:uuid` своего склада
- **THEN** API возвращает `200` в поле `warehouse` с новым именем и обновлённой
  меткой `updatedAt`

### Requirement: Удаление и отсутствие склада

`DELETE /warehouses/:uuid` SHALL удалять собственный склад и возвращать `204`
без тела. Валидный UUID отсутствующего, чужого или уже удалённого склада MUST
возвращать единый `404`; это поведение не раскрывает существование чужих данных.

#### Scenario: Удаление своего склада

- **WHEN** пользователь удаляет принадлежащий ему склад
- **THEN** API возвращает `204` без тела
- **AND** последующий список пользователя не содержит этот склад

#### Scenario: Повторное удаление

- **WHEN** пользователь повторно удаляет UUID уже удалённого склада
- **THEN** API возвращает `404`

#### Scenario: Невалидный UUID

- **WHEN** пользователь передаёт UUID пути в неверном формате
- **THEN** API возвращает `400 INVALID_REQUEST` без `fields`
