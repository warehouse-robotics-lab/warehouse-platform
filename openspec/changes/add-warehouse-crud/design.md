# Design

## Context

Мотивация изменения описана в [proposal.md](proposal.md). В API уже есть
`PrismaModule`, PostgreSQL и модель `User`, но нет модуля складов или
механизма текущего пользователя. `test:integration` безопасно использует
`TEST_DATABASE_URL`, тогда как текущий `test:e2e` запускается с прикладным
`DATABASE_URL`. Архитектурная граница соответствует [ADR-003](../../../docs/adr/003-module-interaction.md):
API хранит постоянные данные и проверяет права HTTP-запросов.

Авторизационный контракт сверяется с PR #61 на ревизии
`51139cd718a815d4640ec6cdc1b89a5cfc5c99e8`: он задаёт единое тело ошибки,
CSRF-проверку изменяющих запросов до проверки сессии и ответы `401`/`403`/`503`.
PR ещё не получил человеческого согласования, поэтому перед переходом к тестам
нужно повторить сверку с согласованной ревизией.

Порядок согласования задаёт [ADR-002](../../../docs/adr/002-ai-development-workflow.md):
для этого ограниченного модуля краткая спецификация и тесты получают
человеческое согласование до реализации.

## Goals / Non-Goals

**Goals:**

- Добавить минимальную постоянную сущность склада, принадлежащую одному
  пользователю.
- Предоставить Web стабильный защищённый HTTP CRUD без раскрытия чужих данных.
- Проверять модель и API на выделенной PostgreSQL-базе, безопасной для тестов.

**Non-Goals:**

- Реализовывать регистрацию, сессии, токены или альтернативный способ
  передачи UUID пользователя.
- Подключать Web, изменять его пустое состояние или менять capability
  `warehouses-page`.
- Добавлять карту, роли наблюдателя, приглашения, Simulation, Redis, очереди,
  Socket.IO или общий пакет контрактов.

## Decisions

### 1. Одна сущность `Warehouse` с владельцем

Миграция Prisma добавит `Warehouse` с `uuid`, `name`, `ownerUuid`,
`createdAt`, `updatedAt` и обязательной связью с `User`; у пользователя будет
обратная связь со складами. Индекс по владельцу и времени создания поддержит
список пользователя. Ограничение базы не позволит сохранить пустое после trim
или имя длиннее 100 символов.

Это минимальная модель для создания, переименования и удаления из продуктовых
требований. Карта и совместный доступ намеренно не сериализуются в этом change:
они потребуют иной модели прав и отдельного согласования.

### 2. Выделенный модуль API и строгий DTO-контракт

CRUD будет размещён в отдельном NestJS-модуле складов, использующем существующий
`PrismaModule`. Для тела `POST` и `PATCH` применяется строгая Zod-проверка из
уже установленной зависимости: неизвестные поля, включая `ownerUuid`,
отклоняются. Модуль возвращает только публичное представление склада и не
добавляет новую библиотеку в workspace.

Строгая проверка предпочтительнее молчаливого игнорирования `ownerUuid`: клиент
сразу получает понятный `400` и не может ошибочно считать, что сменил владельца.

### 3. Доступ всегда ограничен текущим владельцем

Контроллер будет получать UUID текущего пользователя только из согласованного
auth-механизма #39/#40. Сервис передаёт этот UUID в каждый запрос чтения,
изменения и удаления; отсутствие записи в такой области видимости превращается
в единый `404`. Таким образом не различаются отсутствующий и чужой UUID.

Конкретные имена guard, decorator и transport сессии не выбираются этим
change: он использует публичный интерфейс авторизации после её реализации.
Реализация складов не начинается до готовности этого интерфейса и тестового
способа аутентифицировать двух пользователей.

### 4. HTTP-ответы следуют общему контракту авторизации

Успешные операции используют предложенные в спецификации статусы `201`, `200`
и `204`. Невалидные путь или тело дают `400`, а неаутентифицированный запрос —
согласованный `401`. Оболочка ошибок и field-errors не вводятся отдельно:
они должны совпасть с итоговым контрактом #39, чтобы Web не обрабатывал два
формата ошибок.

Для отсутствующего и чужого склада добавляется код `WAREHOUSE_NOT_FOUND` со
статусом `404` и одинаковым сообщением «Склад не найден». Для `POST`, `PATCH`
и `DELETE` источник проверяется раньше тела, UUID и сессии: недоверенный Origin
даёт `403 CSRF_REJECTED`; только после допустимой проверки источника отсутствие
сессии даёт `401 UNAUTHENTICATED`, а недоступность Redis при её проверке —
`503 SERVICE_UNAVAILABLE`.

### 5. e2e изолируется так же, как integration

Конфигурация e2e переиспользует выделенную `TEST_DATABASE_URL` и безопасный
reset непубличной схемы из integration setup. Защита setup учитывает таблицы
`User` и `Warehouse` в `public`, а README отражает это поведение.

Переиспользование существующего механизма вместо второй тестовой инфраструктуры
гарантирует, что миграция, Prisma runtime и защищённые HTTP-сценарии обращаются
к одной тестовой схеме, не стирая прикладные данные.

До первого e2e-прогона `jest-e2e.json` подключает
`integration.global-setup.ts` и `integration.setup.ts`. Global setup читает
`TEST_DATABASE_URL`, проверяет отдельную БД и схему, затем запускает Prisma CLI
с временно установленным `DATABASE_URL`, равным этой test URL. Setup для Jest
устанавливает тот же URL для Prisma runtime. Bare-команда `prisma:migrate:deploy`
не используется для тестовой миграции: она читает обычный `DATABASE_URL` и
предназначена для целевой БД.

## Risks / Trade-offs

- [Авторизация #39/#40 ещё не готова] → изменение остаётся на стадии
  спецификации и тестов; защищённый CRUD не реализуется до появления её
  согласованного публичного интерфейса.
- [PR #61 ещё не согласован] → перед тестами повторно сверить error envelope,
  порядок Origin/сессии и коды с одобренной ревизией; при изменении поведения
  обновить этот change и получить повторное согласование.
- [Ошибка в настройке e2e может затронуть прикладную БД] → setup требует
  отдельную базу с суффиксом `_test` и непубличную схему до очистки.
- [Единый `404` осложняет диагностику клиента] → он предотвращает раскрытие
  существования чужого склада; API не предоставляет альтернативный статус.
- [Пока нет пагинации] → первый Web-сценарий получает полный список; при
  росте объёма пагинация станет отдельным изменением контракта.

## Migration Plan

1. Создать Prisma migration после согласования тестов; она добавляет таблицу
   и внешний ключ без изменения существующих пользователей.
2. Проверить migration через `test:integration` и изолированный `test:e2e`:
   их global setup пересоздаёт test schema и передаёт Prisma CLI
   `DATABASE_URL`, равный `TEST_DATABASE_URL`.
3. Применить bare `prisma:migrate:deploy` только к целевой БД по обычному
   процессу команды; эта команда не проверяет тестовую БД самостоятельно.
4. При необходимости отката создать отдельную проверенную компенсирующую
   migration; автоматически удалять склады и таблицу rollback-скриптом нельзя.
