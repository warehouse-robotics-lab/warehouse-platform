# Design

## Context

Мотивация изменения описана в [proposal.md](proposal.md). В API уже есть
`PrismaModule`, PostgreSQL и модель `User`, но нет модуля складов или
механизма текущего пользователя. `test:integration` безопасно использует
`TEST_DATABASE_URL`, тогда как текущий `test:e2e` запускается с прикладным
`DATABASE_URL`. Архитектурная граница соответствует [ADR-003](../../../docs/adr/003-module-interaction.md):
API хранит постоянные данные и проверяет права HTTP-запросов.

Авторизационный контракт сверяется с PR #61 на ревизии
`e870a35dad1fd93a22e9fb49f860696b9984e47f`: он задаёт единое тело ошибки,
CSRF-проверку изменяющих запросов до проверки сессии и ответы `401`/`403`/`503`.
Отсутствующие одновременно `Origin` и `Referer` для изменяющего запроса также
дают `403 CSRF_REJECTED`. PR ещё не получил человеческого согласования, поэтому
перед переходом к тестам нужно повторить сверку с согласованной ревизией.

Порядок согласования задаёт [ADR-002](../../../docs/adr/002-ai-development-workflow.md):
для этого ограниченного модуля краткая спецификация и тесты получают
человеческое согласование до реализации.

## Goals / Non-Goals

**Goals:**

- Добавить минимальную постоянную сущность склада, принадлежащую одному
  пользователю.
- Предоставить Web стабильный защищённый HTTP CRUD без раскрытия чужих данных.
- Проверять модель и API на выделенной PostgreSQL-базе, безопасной для тестов.

**Non-Goals:**

- Реализовывать регистрацию, сессии, токены или альтернативный способ
  передачи UUID пользователя.
- Подключать Web, изменять его пустое состояние или менять capability
  `warehouses-page`.
- Добавлять карту, роли наблюдателя, приглашения, Simulation, Redis, очереди,
  Socket.IO или общий пакет контрактов.

## Decisions

### 1. Одна сущность `Warehouse` с владельцем

Миграция Prisma добавит `Warehouse` с `uuid`, `name`, `ownerUuid`,
`createdAt`, `updatedAt` и обязательной связью с `User`; у пользователя будет
обратная связь со складами. У внешнего ключа явно задаётся `onDelete: Restrict`:
будущая операция удаления пользователя не может молча каскадно удалить его
склады. Составной индекс `(ownerUuid, createdAt DESC, uuid DESC)` поддержит
стабильный список пользователя. Ограничение базы проверит, что уже
нормализованное имя содержит от 1 до 100 Unicode code points; уникального
ограничения на пару `ownerUuid` и `name` не будет, поэтому одинаковые имена
разрешены. `createdAt` и `updatedAt` задаются сервером независимо; равенство
этих значений при создании не является инвариантом API.

Это минимальная модель для создания, переименования и удаления из продуктовых
требований. Карта и совместный доступ намеренно не сериализуются в этом change:
они потребуют иной модели прав и отдельного согласования.

### 2. Выделенный модуль API и строгий DTO-контракт

CRUD будет размещён в отдельном NestJS-модуле складов, использующем существующий
`PrismaModule`. Для тела `POST` и `PATCH` применяется строгая Zod-проверка из
уже установленной зависимости: неизвестные поля, включая `ownerUuid`,
отклоняются. Модуль возвращает только публичное представление склада и не
добавляет новую библиотеку в workspace.

Строгая проверка предпочтительнее молчаливого игнорирования `ownerUuid`: клиент
сразу получает понятный `400` и не может ошибочно считать, что сменил владельца.
Перед проверкой Zod нормализует `name` методом `String.prototype.trim()` и
считает длину Unicode code points, а не UTF-16 units. Поэтому внешние пробелы,
табы, переводы строк и неразрывные пробелы удаляются, а внутренние символы не
изменяются. Одинаковое нормализованное имя не является конфликтом и не даёт
`409`.
Отсутствующее, пустое после trim или слишком длинное `name` возвращает
`400 VALIDATION_FAILED` с `fields.name` (`REQUIRED` или `NAME_TOO_LONG`);
`U+0000` в `name`, не-объектное тело, нестроковое `name`, лишнее поле и
некорректный UUID — `400 INVALID_REQUEST` без `fields`. Нулевой символ
отклоняется до обращения к PostgreSQL, поскольку его нельзя сохранить в `text`.
`WAREHOUSE_NOT_FOUND` остаётся только для валидного UUID, не найденного в
области текущего владельца.

### 3. Доступ всегда ограничен текущим владельцем

Контроллер будет получать UUID текущего пользователя только из согласованного
auth-механизма #39/#40. Сервис передаёт этот UUID в каждый запрос чтения,
изменения и удаления; отсутствие записи в такой области видимости превращается
в единый `404`. Таким образом не различаются отсутствующий и чужой UUID.

Изменение и удаление используют одну owner-scoped мутацию, а не цепочку
`findFirst` с последующим `update` или `delete`. Нулевое число изменённых строк
и Prisma `P2025` преобразуются в `WAREHOUSE_NOT_FOUND`. Это делает конкуренцию
с параллельным удалением наблюдаемой как `404`, а не как `500`; `PATCH` может
вернуть запись только из той же успешной атомарной мутации.

Конкретные имена guard, decorator и transport сессии не выбираются этим
change: он использует публичный интерфейс авторизации после её реализации.
Реализация складов не начинается до готовности этого интерфейса и тестового
способа аутентифицировать двух пользователей.

### 4. HTTP-ответы следуют общему контракту авторизации

Успешные операции используют предложенные в спецификации статусы `201`, `200`
и `204`. Одиночный склад в ответе `POST`, `GET /:uuid` и `PATCH` вложен в
`warehouse`, а список — в `warehouses`; это соответствует форме ответа
пользователя из auth и позволяет позже добавить метаданные пагинации без смены
типа поля списка. Невалидные путь или тело дают `400`, а неаутентифицированный
запрос — согласованный `401`. Оболочка ошибок и field-errors не вводятся
отдельно: они должны совпасть с итоговым контрактом #39, чтобы Web не
обрабатывал два формата ошибок.

Для отсутствующего и чужого склада добавляется код `WAREHOUSE_NOT_FOUND` со
статусом `404` и одинаковым сообщением «Склад не найден». Для `POST`, `PATCH`
и `DELETE` порядок обработки таков: маршрут и метод → `Origin`/`Referer` →
сессия → UUID → тело → область текущего владельца. Для `GET` этап проверки
источника пропускается. Недоверенный источник или отсутствие одновременно
`Origin` и `Referer` дают `403 CSRF_REJECTED`; только после доверенной проверки
источника отсутствие сессии даёт `401 UNAUTHENTICATED`. Если предъявленную
сессию нельзя проверить из-за недоступности Redis, возвращается
`503 SERVICE_UNAVAILABLE`; ошибка UUID, тела или существования склада в этом
случае не раскрывается. Лишь действительная сессия допускает сначала `400` для
UUID, затем проверку тела и последующий `404` в owner scope.

После проверки формата UUID он приводится к нижнему регистру до owner-scoped
запроса, поэтому представления одного UUID в верхнем и нижнем регистре имеют
одинаковую семантику. Все ответы распознанных маршрутов складов, в том числе
ошибки и `204`, получают `Cache-Control: no-store`, как приватные ответы auth,
зависящие от cookie.

CORS-конфигурация из auth применяется ко всем маршрутам складов: фактический
запрос с доверенного `Origin` получает точный `Access-Control-Allow-Origin` и
`Access-Control-Allow-Credentials: true`. `OPTIONS` к известному маршруту —
особый preflight-этап после распознавания маршрута и до cookie, сессии, UUID и
тела; доверенный источник получает `204` с разрешающими заголовками и
`Cache-Control: no-store`, недоверенный, `null` или отсутствующий `Origin` —
`403 CSRF_REJECTED`, а неизвестный маршрут — `404 ROUTE_NOT_FOUND`.

После слияния #61 этот change переносит общий справочник ошибок из auth-спеки в
`docs/api/error-codes.md`, обновляет ссылку auth-спеки на него и добавляет
`WAREHOUSE_NOT_FOUND` (`404`, «Склад не найден»). До слияния #61 код склада не
добавляется в ветку auth.

### 5. Тестовый план разделяет существующий зелёный набор и новые red-тесты

До добавления warehouse-тестов отдельно запускаются существующие unit-тесты
`pnpm --filter @warehouse/api test --runInBand` и integration-тест
`pnpm --filter @warehouse/api test:integration test/prisma.integration-spec.ts`.
После изоляции e2e (решение 6) отдельно запускается существующий smoke-тест
`pnpm --filter @warehouse/api test:e2e test/app.e2e-spec.ts`.

Новые тесты запускаются изолированно командами
`pnpm --filter @warehouse/api test -- warehouses --runInBand`,
`pnpm --filter @warehouse/api test:integration test/warehouses.integration-spec.ts`
и `pnpm --filter @warehouse/api test:e2e test/warehouses.e2e-spec.ts`.
До появления модели `Warehouse` integration red-тест не обращается к
`prisma.warehouse`: он через raw SQL проверяет метаданные схемы и намеренно
падает на assertion об отсутствующей таблице. Это отличает ожидаемый red от
`TypeError` из-за отсутствующего delegate Prisma. E2E red-тест до маршрута
намеренно получает `404`; unit red-тест принимается только при падении
наблюдаемого правила валидации или владения, а не импорта.

Проверка сортировки использует в integration/e2e-fixtures явно заданные разные
и одинаковые `createdAt`: она проверяет сначала время по убыванию, затем UUID
по убыванию. Тесты меток времени проверяют ISO-представление и серверное
обновление, но не предполагают равенство `createdAt` и `updatedAt` при
создании.

### 6. e2e изолируется так же, как integration

Конфигурация e2e переиспользует выделенную `TEST_DATABASE_URL` и безопасный
reset непубличной схемы из integration setup. Защита setup учитывает таблицы
`User` и `Warehouse` в `public`, а README отражает это поведение.

Переиспользование существующего механизма вместо второй тестовой инфраструктуры
гарантирует, что миграция, Prisma runtime и защищённые HTTP-сценарии обращаются
к одной тестовой схеме, не стирая прикладные данные.

До первого e2e-прогона `jest-e2e.json` подключает
`integration.global-setup.ts` и `integration.setup.ts`. Global setup читает
`TEST_DATABASE_URL`, проверяет отдельную БД и схему, затем запускает Prisma CLI
с временно установленным `DATABASE_URL`, равным этой test URL. Setup для Jest
устанавливает тот же URL для Prisma runtime. Bare-команда `prisma:migrate:deploy`
не используется для тестовой миграции: она читает обычный `DATABASE_URL` и
предназначена для целевой БД.

## Risks / Trade-offs

- [Авторизация #39/#40 ещё не готова] → изменение остаётся на стадии
  спецификации и тестов; защищённый CRUD не реализуется до появления её
  согласованного публичного интерфейса.
- [PR #61 ещё не согласован] → перед тестами повторно сверить error envelope,
  порядок Origin/сессии и коды с одобренной ревизией; при изменении поведения
  обновить этот change и получить повторное согласование.
- [Ошибка в настройке e2e может затронуть прикладную БД] → setup требует
  отдельную базу с суффиксом `_test` и непубличную схему до очистки.
- [Единый `404` осложняет диагностику клиента] → он предотвращает раскрытие
  существования чужого склада; API не предоставляет альтернативный статус.
- [Пока нет пагинации] → первый Web-сценарий получает полный список; при
  росте объёма пагинация станет отдельным изменением контракта.

## Migration Plan

1. Создать Prisma migration после согласования тестов; она добавляет таблицу,
   составной индекс списка и внешний ключ `onDelete: Restrict` без изменения
   существующих пользователей.
2. Проверить migration через `test:integration` и изолированный `test:e2e`:
   их global setup пересоздаёт test schema и передаёт Prisma CLI
   `DATABASE_URL`, равный `TEST_DATABASE_URL`.
3. Применить bare `prisma:migrate:deploy` только к целевой БД по обычному
   процессу команды; эта команда не проверяет тестовую БД самостоятельно.
4. При необходимости отката создать отдельную проверенную компенсирующую
   migration; автоматически удалять склады и таблицу rollback-скриптом нельзя.
