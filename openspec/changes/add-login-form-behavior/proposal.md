# Proposal

## Why

Базовая вёрстка страницы входа подготовлена в PR №31.
Второй этап задачи №18 — проверка полей, сообщения об ошибках
и состояние ожидания отправки.

Поведение и проверки перед реализацией согласуются с командой
по ADR-002.

## What Changes

- Проверка обязательности почты и пароля, проверка формата почты.
- Сообщения об ошибках под соответствующими полями.
- Общее сообщение об ошибке входа перед кнопкой.
- Состояние ожидания с блокировкой кнопки и повторной отправки.
- Локальный тестовый обработчик для воспроизведения успеха,
  неверных учётных данных и технической ошибки без API
  и настоящих учётных данных.
- Автоматические тесты основного поведения формы.

Точные правила проверки, обработки значений и отображения
состояний описываются в спецификации текущего изменения.
Результат успешной тестовой отправки, включая необходимость
и адрес перехода, согласуется до реализации.

## Capabilities

### New Capabilities

- `login-form`: проверка полей, отображение ошибок и состояния
  ожидания, обработка результатов локальной тестовой отправки.

### Modified Capabilities

Нет. Требования к хранению учётной записи в `user-account`
не изменяются.

## Impact

- Приложение apps/web: форма входа и её тесты.
- Для полей и кнопки используются существующие компоненты
  Input и Button из shadcn.
- Для формы используются React Hook Form и Zod согласно ТЗ проекта.
- Для тестов используются Vitest и React Testing Library
  согласно ТЗ проекта. Необходимая настройка тестов входит
  в этот этап.
- Структура кода соответствует принятому в проекте FSD.

Спецификация openspec/specs/user-account/spec.md учитывается
в части правил почты. Она описывает хранение учётной записи
и не заменяет спецификацию формы входа.

Реализация продолжит работу из PR №31 после его слияния.
API, база данных и существующие правила хранения пользователей
не изменяются.

## Workflow

1. Подготовить краткую спецификацию поведения и сценарии проверок.
2. Согласовать с командой объём задачи и порядок ревью по ADR-002.
3. Подготовить и согласовать тесты до реализации поведения.
4. Реализовать согласованное поведение и выполнить проверки.

Для небольшого изменения спецификация и тесты могут проходить
совместное ревью согласно ADR-002. Сценарии проверок не заменяют
автоматические тесты.

План работы будет описан в tasks.md. После получения согласования
в нём фиксируются участник, ссылка на ревью и проверенная ревизия.

## Out of Scope

- Подключение к настоящему API авторизации.
- Создание сессии, хранение токенов и защита маршрутов.
- Регистрация, смена и восстановление пароля.
- Определение требований к сложности пароля:
  правила согласуются с командой отдельно.
- Замена LoginHeader на общий компонент из задачи №17.

## Open Questions

- Какой результат показывать после успешной локальной
  тестовой отправки: выполнять переход или передавать
  результат внешнему обработчику?
- Если требуется переход, какой маршрут использовать?
- Подтверждаются ли правила общей ошибки:
  сохранять сообщение после завершения ожидания
  и очищать при начале новой корректной отправки?
- Какой текст использовать для пустых полей:
  «Обязательное поле» по предложению Полины
  или отдельные сообщения из макета?
- Как выбирать результат локального тестового обработчика
  при ручной проверке: через настройку в коде или отдельный
  инструмент разработки, не входящий в пользовательскую форму?
