# Proposal

## Why

Базовая вёрстка страницы входа подготовлена в PR №31.
Второй этап задачи №18 — проверка полей, сообщения об ошибках
и состояние ожидания отправки.

Поведение и проверки перед реализацией согласуются с командой
по ADR-002.

## What Changes

- Проверка обязательности почты и пароля, проверка формата почты.
- Сообщения об ошибках под соответствующими полями.
- Общее сообщение об ошибке входа перед кнопкой.
- Состояние ожидания с блокировкой кнопки и повторной отправки.
- Локальный тестовый обработчик для воспроизведения успеха,
  неверных учётных данных и технической ошибки без API
  и настоящих учётных данных.
- Автоматические тесты основного поведения формы.

Точные правила проверки, обработки значений и отображения
состояний описываются в спецификации текущего изменения.
Результат успешной тестовой отправки, включая необходимость
и адрес перехода, согласуется до реализации.

## Capabilities

### New Capabilities

- `login-form`: проверка полей, отображение ошибок и состояния
  ожидания, обработка результатов локальной тестовой отправки.

### Modified Capabilities

Нет. Требования к хранению учётной записи в `user-account`
не изменяются.

## Impact

- Приложение apps/web: форма входа и её тесты.
- Для полей и кнопки используются существующие компоненты
  Input и Button из shadcn.
- Для формы используются React Hook Form и Zod согласно ТЗ проекта.
- Для тестов используются Vitest и React Testing Library
  согласно ТЗ проекта. Необходимая настройка тестов входит
  в этот этап.
- Структура кода соответствует принятому в проекте FSD.

Спецификация openspec/specs/user-account/spec.md учитывается
в части правил почты. Она описывает хранение учётной записи
и не заменяет спецификацию формы входа.

Реализация продолжит работу из PR №31 после его слияния.
API, база данных и существующие правила хранения пользователей
не изменяются.

## Workflow

1. Подготовить краткую спецификацию поведения и сценарии проверок.
2. Согласовать с командой объём задачи и порядок ревью по ADR-002.
3. Подготовить и согласовать тесты до реализации поведения.
4. Реализовать согласованное поведение и выполнить проверки.

Для небольшого изменения спецификация и тесты могут проходить
совместное ревью согласно ADR-002. Сценарии проверок не заменяют
автоматические тесты.

План работы будет описан в tasks.md. После получения согласования
в нём фиксируются участник, ссылка на ревью и проверенная ревизия.

## Out of Scope

- Подключение к настоящему API авторизации.
- Создание сессии, хранение токенов и защита маршрутов.
- Регистрация, смена и восстановление пароля.
- Определение требований к сложности пароля:
  правила согласуются с командой отдельно.
- Замена LoginHeader на общий компонент из задачи №17.

## Решения по замечаниям ревью

- После первой попытки отправки каждое поле проверяется
  при каждом изменении значения.
- При успехе вызывается внешний обработчик без перехода
  и создания сессии.
- Для пустых полей используется «Обязательное поле».
- Общая ошибка сохраняется при редактировании и невалидной
  отправке, очищается при новой корректной отправке.
- Тестовый результат выбирается вне пользовательской формы.

## Уточнение настроек по ревью

Стас подтвердил способ настройки тестового обработчика через
NEXT_PUBLIC_LOGIN_MOCK_RESULT и NEXT_PUBLIC_LOGIN_MOCK_DELAY_MS.

Значения по умолчанию применяются отдельно к каждой отсутствующей
переменной. Пустые и некорректные значения вызывают явную ошибку
конфигурации без тестовой отправки и вызова обработчика успеха.

Способ отображения ошибки и дополнительные сценарии описаны
в spec.md и ожидают повторного согласования.

## Ручная проверка тестового обработчика

Предлагаемый способ проверки в режиме разработки:

1. В apps/web/.env.local установить:
   NEXT_PUBLIC_LOGIN_MOCK_RESULT=success
   NEXT_PUBLIC_LOGIN_MOCK_DELAY_MS=1500
2. Перезапустить сервер разработки и открыть /login.
3. Ввести вымышленные корректные данные и отправить форму.
4. Во время задержки проверить индикатор загрузки,
   блокировку кнопки, неизменность полей и запрет
   повторной отправки.
5. После ответа проверить однократный вызов внешнего
   обработчика успеха, отсутствие перехода и создания сессии.
   Способ наблюдения вызова будет описан при подготовке тестов
   и технического решения без вывода пароля в журнал.
6. Повторить проверку с результатом invalid-credentials:
   должно появиться «Неверная почта или пароль».
7. Повторить проверку с результатом technical-error:
   должно появиться «Не удалось войти. Попробуйте ещё раз.».
8. Указать неизвестный результат succes, перезапустить сервер
   и открыть /login. Проверить сообщение об ошибке настройки
   и отсутствие вызова обработчика успеха.
9. Повторить проверку с задержками -1, 10001, 1.5 и abc,
   затем с пустым значением каждой настройки.
   Каждый случай должен показывать ошибку конфигурации.
10. Оставить только результат technical-error:
    проверить техническую ошибку после стандартной задержки 1500 мс.
11. Оставить только задержку 3000:
    проверить успешный результат после 3000 мс.
12. Удалить обе настройки:
    проверить успешный результат после стандартных 1500 мс.

После каждого изменения настроек сервер разработки
перезапускается. Локальный файл .env.local не коммитится.
Настройки тестового обработчика не содержат секретов.

перечисленные проверки ещё не выполнялись.
