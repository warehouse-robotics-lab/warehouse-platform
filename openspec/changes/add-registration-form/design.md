# Design

## Context

Мотивация и объём — в `proposal.md`, требования — в `specs/registration-form/spec.md`.

Текущее состояние `apps/web` на `main`:

- Next.js 16 (App Router), React 19, Tailwind CSS 4, shadcn/ui в стиле `base-nova`
  на `@base-ui/react` 1.9. Структура по FSD: маршруты в `src/app`, страницы в `src/_pages`,
  виджеты в `src/widgets`, UI-kit в `src/shared/ui` (`apps/web/README.md`).
- В `src/shared/ui` есть `button`, `input`, `tooltip` и компоненты каркаса кабинета.
- Страница входа на `main` — только разметка. Поведение входа, React Hook Form, Zod,
  `@hookform/resolvers`, Vitest и Testing Library приходят с PR #66 (ещё не слит, стек
  на спецификации входа PR #34). Ошибки входа в #66 выводятся без резервирования места
  и без значков, общая ошибка — текстом без рамки.
- Шапка 56px с «Warehouse Platform» уже есть как виджет `src/widgets/app-header`.
  Вход использует свою копию `LoginHeader` внутри `_pages/login`.

Правила полей — PR #61, ревизия `7380d19`. Стас подтвердил, что #61 берётся за основу,
но ещё не согласован окончательно.

Макет: `design/warehouse-platform.pen` из PR #70, ревизия `067bbb3` (на `main` —
`95542cc`). Фреймы `hNtZe` (1440px) и `x0lXB` (390px) и состояния: исходное, пустые
обязательные поля, неверный формат почты, отправка, общий сбой, пароль показан (только
1440px). Кадров подсказки к паролю и занятой почты нет: их поведение описано в
спецификации без макета.

Порядок работы — [ADR-002](../../../docs/adr/002-ai-development-workflow.md), полный:
спецификация, тесты, реализация (см. `tasks.md`).

## Goals / Non-Goals

**Goals:**

- Общие элементы форм в `shared/ui`, на которые форма входа перейдёт без изменения
  внешнего вида регистрации.
- Правила полей, которые выдают коды нарушений из #61, чтобы при подключении API (F2, F7)
  заменить источник правил, а не тексты и разметку.
- Поведение, проверяемое автотестами в jsdom. Раскладку, наведение и сравнение
  с макетом проверяет человек в браузере.

**Non-Goals:**

- Перевод формы входа на общие компоненты и общий разбор настроек тестового обработчика.
- Общий клиент API, TanStack Query и обработка кодов ответов API.
- Настройка линтера правил FSD.

## Decisions

### 1. Структура по FSD

```text
src/app/register/page.tsx              # подключает RegisterPage
src/_pages/register/
  ui/register-page.tsx                 # шапка, карточка, выбор обработчика, переход после успеха
  ui/register-form.tsx                 # форма
  ui/password-hint.tsx                 # значок «ⓘ» и текст требований
  model/registration-schema.ts         # правила полей → коды нарушений #61, нормализация
  model/field-error-texts.ts           # код нарушения → текст под полем
  model/mock-config.ts                 # разбор NEXT_PUBLIC_REGISTRATION_MOCK_*
  api/mock-submit-registration.ts      # тестовый обработчик
src/shared/ui/
  form-field.tsx                       # подпись, место для значка у подписи, поле, строка ошибки
  form-alert.tsx                       # общая ошибка в рамке, зарезервированная область
  submit-button.tsx                    # кнопка с индикатором отправки
  password-input.tsx                   # поле пароля с кнопкой показа
  popover.tsx                          # из реестра shadcn
```

- **Маршрут вне группы `(cabinet)`,** как `/login`: каркас кабинета на странице не нужен.
- **Шапка — виджет `app-header`.** Он совпадает с шапкой макета: 56px, отступы 16/24px.
  Страница может импортировать виджет. `LoginHeader` из `_pages/login` импортировать
  нельзя: FSD запрещает импорт между слайсами одного слоя.
- **Имена:** маршрут и слайс — `register`, как `login`. Capability и переменные
  окружения — `registration`, как договорено в #41.
- **`onSuccess` и переход — в странице, а не в форме.** Форма вызывает `onSuccess()`
  без аргументов, как во входе. Страница вызывает `router.replace("/warehouses")`:
  замена записи в истории не даёт вернуться на форму кнопкой «Назад». Так форма
  не зависит от маршрутизации, а тест страницы проверяет вызов `replace`.

### 2. Общие компоненты форм в `shared/ui`

- **Состав по ответу Тани в #41:** поле с подписью и строкой ошибки, общая ошибка,
  кнопка с индикатором отправки. Кнопка показа пароля тоже вынесена: это элемент UI
  без логики регистрации, и вход сможет взять её без переноса кода.
- **`FormField`** рендерит `<label>`, место для дополнения справа от подписи с отступом 4px (значок «ⓘ»),
  поле (`children`) и строку ошибки высотой 20px с отступом 4px сверху. Строка есть
  всегда, пустая — без текста и значка. Идентификатор сообщения строится от `id` поля,
  компонент отдаёт `aria-invalid` и `aria-describedby` для поля.
- **`FormAlert`** — область `aria-live="polite"` фиксированной высоты (64px по макету).
  С сообщением — рамка и значок «!» в круге, без сообщения — пустое место.
- **`SubmitButton`** — `Button` с `aria-busy`, спиннером и подписью в `sr-only`
  во время ожидания: размер и доступное имя не меняются. Тот же приём, что в #66.
- **`PasswordInput`** — `Input` и кнопка `type="button"` справа внутри поля, значки
  `Eye`/`EyeOff` из `lucide-react`. Доступное имя кнопки меняется: «Показать пароль» /
  «Скрыть пароль». `aria-pressed` не ставится, чтобы не озвучивать состояние дважды.
  У поля отступ справа под кнопку, без атрибута `maxLength`.
- **Альтернатива — компонент `field` из реестра shadcn.** Отклонена: `FieldError`
  в текущем реестре `base-nova` имеет `role="alert"` и не рендерится без ошибки. После
  первой отправки ошибки пересчитываются при каждом вводе, и `role="alert"` озвучивал бы
  каждое изменение. Резервирования места тоже нет. Подгонка потребовала бы правки
  сгенерированного файла, что противоречит принятому в #17 правилу.
- **Значки ошибок** — «!» в круге, как в макете: `CircleAlert` из `lucide-react`, `aria-hidden="true"`.
- **Отступы по макету #70:** подпись, 8px, поле 44px, строка ошибки 4/20px, 12px
  до следующей подписи. Перед общей ошибкой 8px, после — 12px. От поля пароля до кнопки
  108px. Размеры карточки и заголовка сверяются с PNG-экспортом при реализации.

### 3. Логика формы: React Hook Form и Zod

- **`useForm` с `zodResolver`, `mode: "onSubmit"`, `reValidateMode: "onChange"`.** Это
  ровно требование спецификации: до первой отправки ошибок нет, после неё изменённое поле
  проверяется при каждом вводе. Стек формы — из ТЗ (`docs/product-requirements.md`).
- **Схема выдаёт коды нарушений #61,** а тексты берутся из таблицы в
  `field-error-texts.ts`. При подключении API (F2) локальная схема заменяется общей
  из `@warehouse/contracts` с теми же кодами, а тексты и разметка остаются.
- **Одно нарушение на поле.** Проверка поля в `superRefine` останавливается на первом
  нарушении в порядке #61: `REQUIRED`, длина, состав. Порядок не зависит от того,
  в каком порядке Zod собирает проблемы.
- **Нормализация в схеме.** Имя — `trim()`, почта — `trim().toLowerCase()`, пароль
  не меняется. `handleSubmit` передаёт обработчику уже нормализованные значения.
- **Символы.** Длина — число кодовых точек (`Array.from(value).length`). Заглавная —
  `\p{Lu}`, строчная — `\p{Ll}`, цифра — `\p{Nd}`, специальный символ — `[^\p{L}\p{Nd} ]`
  (флаг `u`). #61 не уточняет категории заглавной и строчной букв, поэтому выбраны
  `Lu`/`Ll`. В F2 правило заменяется общей схемой.
- **Почта:** `^\S+@[^\s@]+$` и не больше 254 кодовых точек. Разделитель — последний «@»,
  точка в домене не требуется. Вход (#66) использует `z.email()`, который требует точку
  в домене. Выравнивание правил входа — F2 (см. риски).
- **Занятая почта:** `setError("email", { type: "server", message: "EMAIL_ALREADY_TAKEN" })`
  и `setFocus("email")`. При вводе в поле почты повторная проверка схемой заменяет эту
  ошибку результатом обычных правил.
- **Общая ошибка** хранится в состоянии формы отдельно от ошибок полей и очищается
  только в начале корректной отправки, как во входе.
- **Альтернатива — ручное состояние ошибок поверх `useForm`, как в #66.** Не выбрана:
  `reValidateMode` уже даёт нужное поведение, а ручной пересчёт дублирует resolver.
  Единый подход для обеих форм обсуждается при переводе входа на общие компоненты.

### 4. Ожидание, успех и уход со страницы

- **Ожидание** — локальный флаг формы. Поля `readOnly`, кнопка `disabled`, повторный
  `submit` игнорируется по флагу, а не только по `disabled` (Enter в поле).
- **После успеха флаг не сбрасывается:** страница уходит на `/warehouses`, а до этого
  повторная отправка невозможна. При подключении API (F7) вторая отправка дала бы `409`
  на только что созданный адрес.
- **Уход со страницы.** Форма помечает размонтирование, и результат обработчика после
  него не обрабатывается: ни `onSuccess`, ни `setError`, ни общая ошибка.
- **Готовность к работе.** Как в #66, поля и кнопка `disabled`, пока клиентский код
  не готов (`useSyncExternalStore` с серверным снимком `false`). Иначе обычная отправка
  `<form>` до гидратации ушла бы GET-запросом с паролем в адресе. Форма — `noValidate`.
- **Начальный фокус — эффектом после готовности, а не атрибутом `autoFocus`.** Во время
  гидратации поле ещё `disabled`, и фокус от `autoFocus` при монтировании не встанет.
  Поэтому после готовности форма вызывает `setFocus("name")`, если
  `matchMedia("(min-width: 48rem)")` совпадает и фокус ещё на `body`. Ширина
  проверяется один раз при открытии, изменение размера окна фокус не переносит.
- **Порог 768px — брейкпоинт `md`,** как у раскладок кабинета (#17) и хука `use-mobile`.
  На макете фокус в «Имя» есть только на кадре 1440px, на кадре 390px его нет.
  На телефоне автофокус открыл бы экранную клавиатуру поверх формы.
- **Во входе автофокуса нет:** на макете входа фокус не показан ни на одном кадре.
  Расхождение осознанное, решение автора задачи (BentonFraizer, 2026-11-26).

### 5. Подсказка к паролю — Popover, а не Tooltip

- **`popover` из реестра shadcn** (`pnpm --filter @warehouse/web exec shadcn add popover`),
  сгенерированный файл не правится.
- **`Popover.Trigger` с `openOnHover`** открывает подсказку наведением, а нажатие,
  Enter и пробел работают как у обычной кнопки-переключателя. Base UI закрывает
  подсказку по Escape и нажатию вне неё. Для перехода указателя со значка на подсказку
  при необходимости задаётся небольшой `closeDelay`.
- **Tooltip отклонён:** подсказка Base UI Tooltip не открывается нажатием на сенсорном
  экране и по Enter/пробелу, а это требование Стаса.
- **`initialFocus={false}`:** фокус остаётся на значке, поэтому повторный Enter или
  пробел закрывает подсказку, а Escape оставляет фокус на значке. В подсказке нет
  интерактивных элементов, переносить в неё фокус не нужно.
- **`side="top"`** — над значком, поле пароля под подписью не перекрывается. Ширина
  ограничена окном с отступами 16px, чтобы на 390px текст не обрезался.
- **Текст для `aria-describedby`.** Содержимое Popover рендерится в портале только
  в открытом состоянии. Поэтому рядом с полем лежит тот же текст в `sr-only`, и поле
  пароля ссылается на него постоянно, а при ошибке — ещё и на строку ошибки.
- **Значок «ⓘ»** — `Info` из `lucide-react`, 16px, в кнопке с областью нажатия 24×24.
  Отрицательные отступы сохраняют высоту строки подписи 20px, чтобы форма не отличалась
  от макета. Значок «ⓘ» вместо «?» из комментария Стаса — по договорённости со Стасом
  (см. журнал в `tasks.md`). «!» не используется: он обозначает ошибки.

### 6. Тексты

Тексты пустых полей, ошибки формата почты и общей ошибки взяты из макета. Остальные
предложены в этом изменении и отдаются на ревью Тане (ответ в #41).

| Поле | Код #61 | Текст |
| --- | --- | --- |
| Имя | `REQUIRED` | Укажите имя |
| Имя | `NAME_TOO_SHORT` | Минимум 2 символа |
| Имя | `NAME_TOO_LONG` | Максимум 64 символа |
| Почта | `REQUIRED` | Укажите почту |
| Почта | `EMAIL_INVALID` | Проверьте формат почты |
| Почта | `EMAIL_ALREADY_TAKEN` | Эта почта уже зарегистрирована |
| Пароль | `REQUIRED` | Укажите пароль |
| Пароль | `PASSWORD_TOO_SHORT` | Минимум 8 символов |
| Пароль | `PASSWORD_TOO_LONG` | Максимум 36 символов |
| Пароль | `PASSWORD_WEAK` | Пароль не соответствует требованиям |

- Строка ошибки в макете — одна строка 20px. На 390px под текст остаётся около 300px
  (поле 326px минус значок и отступ), поэтому тексты короткие, а полный список
  требований — в подсказке «ⓘ».
- Подсказка: «Пароль должен содержать: от 8 до 36 символов; заглавную и строчную буквы;
  цифру; спецсимвол, например ! # - _ (пробел не считается)». Список — `<ul>`.
- Общая ошибка: «Не удалось создать аккаунт. Попробуйте ещё раз.» Ошибка настройки —
  текст входа: «Ошибка настройки тестового обработчика. Проверьте настройки разработки.»

### 7. Тестовый обработчик и его настройки

- **Тот же подход, что во входе (#66):** `createMockSubmitRegistration({ result, delayMs })`
  возвращает функцию, которая через `setTimeout` отдаёт результат
  `"success" | "email-taken" | "technical-error"`. Страница передаёт её в форму.
- **Разбор настроек** — `parseRegistrationMockConfig`: значение по умолчанию только
  для `undefined`, пустая строка — ошибка, задержка — `^\d+$` и не больше 10000.
  `NEXT_PUBLIC_*` подставляются при сборке, поэтому нужен перезапуск сервера разработки.
- **Код разбора дублирует вход.** Общий разборщик в `shared/lib` потребовал бы правки
  кода входа. Его выделение — в задаче перевода входа на общие компоненты.
- Переменные описываются в `apps/web/.env.example` и README.

### 8. Тесты (этап 2, после слияния #66)

- **Vitest и Testing Library с настройкой из #66,** новых пакетов нет.
- **Модульные тесты:** схема (коды и нормализация по сценариям правил полей, граничные
  длины, кодовые точки), разбор настроек, таблица текстов.
- **Тесты формы:** состояния, ожидание, повторная отправка, занятая почта, общая
  ошибка, уход со страницы, показ пароля, подсказка (Enter, пробел, Escape, нажатие),
  связи `aria-*`. Обработчик — управляемый `Promise` вместо таймера.
- **Тест страницы:** `next/navigation` подменяется, проверяется `replace("/warehouses")`
  и отсутствие `push`.
- **Вручную в браузере:** наведение, раскладка 390/1440, отсутствие сдвигов,
  положение подсказки, кольца фокуса, «Назад» после регистрации, сравнение с макетом.
  jsdom не считает раскладку.
- Каждый тест проверяется на способность обнаружить нарушение: временная поломка
  поведения должна давать падение.

## Risks / Trade-offs

- [#66 не слит: нет зависимостей и настройки тестов] → тесты и реализация начинаются
  после слияния. Ветка перед этим обновляется от `main`, конфликты в `pnpm-lock.yaml`
  не ожидаются, так как пакеты не добавляются.
- [#61 не согласован окончательно] → правила и коды могут измениться. Тогда обновляются
  спецификация, тесты и схема, существенные изменения повторно идут на ревью.
- [До перевода входа формы выглядят по-разному: у входа нет резервирования, значков
  и рамки] → это временно, перевод входа согласован с Таней отдельной правкой после #66.
- [Правила почты входа (`z.email()`) строже правил регистрации] → адрес вида
  `user@localhost` пройдёт регистрацию, но не пройдёт клиентскую проверку входа. Пока
  обработчики тестовые, последствий нет. Выравнивание — F2.
- [Если над значком «ⓘ» нет места в окне (страница прокручена), Base UI переворачивает
  подсказку вниз, и она перекрывает поле пароля] → проверка 390px выполняется на
  непрокрученной странице, как в сценарии. Перекрытие при прокрутке принимается.
- [На устройствах с мышью и сенсорным экраном наведение и нажатие могут сработать
  вместе] → поведение Base UI принимается и проверяется вручную на телефоне
  и на компьютере.
- [Состояние ожидания после успеха держится до смены страницы] → если переход
  не произойдёт, форма останется заблокированной. Для тестового обработчика это
  приемлемо, при подключении API (F7) решение пересматривается.
