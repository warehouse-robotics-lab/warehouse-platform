# user-credentials Specification

## Purpose
Требования к учётным данным пользователя на границе API: правила проверки email, пароля
и имени, хеширование исходного пароля и его проверка. Операция сохранения пользователя
остаётся в `user-account` и по-прежнему получает готовый хеш.

## Requirements

### Requirement: Длина пароля

Пароль MUST содержать от 8 до 36 символов включительно. Нарушение длины MUST
определяться проверкой с кодом `PASSWORD_TOO_SHORT` или `PASSWORD_TOO_LONG`.

#### Scenario: Пароль короче минимума

- **WHEN** пользователь передаёт пароль длиной 7 символов, удовлетворяющий остальным правилам
- **THEN** проверка определяет нарушение длины с кодом `PASSWORD_TOO_SHORT`

#### Scenario: Пароль длиннее максимума

- **WHEN** пользователь передаёт пароль длиной 37 символов, удовлетворяющий остальным правилам
- **THEN** проверка определяет нарушение длины с кодом `PASSWORD_TOO_LONG`

### Requirement: Состав пароля

Пароль MUST содержать хотя бы одну цифру, одну заглавную букву, одну строчную букву и
один специальный символ. Специальным символом MUST считаться любой символ, кроме буквы,
цифры и пробела. Нарушение состава MUST определяться проверкой с кодом `PASSWORD_WEAK`.

#### Scenario: Пароль без цифры

- **WHEN** пользователь передаёт пароль без цифр
- **THEN** проверка определяет нарушение состава с кодом `PASSWORD_WEAK`

#### Scenario: Пароль без заглавной буквы

- **WHEN** пользователь передаёт пароль без заглавных букв
- **THEN** проверка определяет нарушение состава с кодом `PASSWORD_WEAK`

#### Scenario: Пароль без строчной буквы

- **WHEN** пользователь передаёт пароль без строчных букв
- **THEN** проверка определяет нарушение состава с кодом `PASSWORD_WEAK`

#### Scenario: Пароль без специального символа

- **WHEN** пользователь передаёт пароль только из букв и цифр
- **THEN** проверка определяет нарушение состава с кодом `PASSWORD_WEAK`

### Requirement: Область применения правил email и имени

Правила email MUST применяться при входе, регистрации и любом другом обращении к
адресу. Правила имени MUST применяться там, где имя задаётся, то есть при
регистрации.

#### Scenario: Правила email действуют при входе

- **WHEN** пользователь входит с адресом, нарушающим правила email
- **THEN** проверка определяет нарушение и отклоняет вход до проверки учётных данных

#### Scenario: Правила имени действуют при регистрации

- **WHEN** пользователь регистрируется с именем, нарушающим правила
- **THEN** проверка определяет нарушение и отклоняет регистрацию

### Requirement: Область применения правил пароля

Правила длины и состава пароля MUST применяться при регистрации. При входе MUST
проверяться только наличие и непустота пароля: пароль, созданный по прежним правилам,
MUST приниматься при входе и сравниваться с хешем как есть. Пустой пароль MUST
кодироваться кодом `REQUIRED`, а не кодом нарушения длины.

#### Scenario: Старый пароль принимается при входе

- **GIVEN** пользователь зарегистрирован с паролем, не удовлетворяющим текущим правилам длины или состава
- **WHEN** он входит с этим паролем
- **THEN** система не отклоняет пароль по правилам длины или состава
- **AND** проверяет его по сохранённому хешу

#### Scenario: Правила действуют при регистрации

- **WHEN** пользователь регистрируется с паролем, не удовлетворяющим правилам
- **THEN** проверка определяет нарушение и отклоняет регистрацию

### Requirement: Пробелы и регистр пароля

Пароль MUST NOT изменяться: регистр, пробелы и крайние пробелы сохраняются. Пробел
MUST считаться обычным символом пароля, но специальным символом не считаться.

#### Scenario: Пробелы в пароле сохраняются

- **WHEN** пользователь передаёт пароль `"  Ab1!def  "` длиной от 8 до 36 символов
- **THEN** система принимает пароль и сохраняет его без изменений, включая пробелы

#### Scenario: Пробел не заменяет специальный символ

- **WHEN** пользователь передаёт пароль без специальных символов, но с пробелами
- **THEN** проверка определяет нарушение состава с кодом `PASSWORD_WEAK`

### Requirement: Требования к email

Email MUST содержать символ `@`, непустую локальную часть и непустой домен, MUST NOT
содержать пробелов после нормализации и MUST быть не длиннее 254 символов после
нормализации. Перед проверкой, поиском пользователя и сохранением значение
MUST быть нормализовано по правилам `user-account`. Нарушение правил формата или длины
MUST определяться проверкой с кодом `EMAIL_INVALID`, пустое значение — кодом
`REQUIRED`. Точка в домене MUST NOT требоваться.

#### Scenario: Email без символа @

- **WHEN** пользователь передаёт email `userexample.com`
- **THEN** проверка определяет нарушение формата с кодом `EMAIL_INVALID`

#### Scenario: Email с пробелами

- **WHEN** пользователь передаёт email `"  user@example.com  "`
- **THEN** система нормализует значение до `user@example.com` и проверяет его дальше

#### Scenario: Email с пробелом внутри

- **WHEN** пользователь передаёт email `us er@example.com`
- **THEN** проверка определяет нарушение формата с кодом `EMAIL_INVALID`
#### Scenario: Пустой email

- **WHEN** пользователь передаёт пустой email
- **THEN** проверка определяет отсутствие значения с кодом `REQUIRED`

#### Scenario: Слишком длинный email

- **WHEN** пользователь передаёт email длиннее 254 символов
- **THEN** проверка определяет нарушение длины с кодом `EMAIL_INVALID`

#### Scenario: Поиск по нормализованному адресу

- **GIVEN** существует пользователь с email `user@example.com`
- **WHEN** выполняется поиск по адресу `USER@Example.com`
- **THEN** поиск находит пользователя `user@example.com`

### Requirement: Требования к имени

Имя MUST содержать от 2 до 64 символов включительно после удаления крайних пробелов.
Пробелы между словами MUST сохраняться. Пустое после обрезки имя MUST считаться
отсутствующим и кодироваться кодом `REQUIRED`. Нарушение правил MUST
определяться проверкой с кодом `NAME_TOO_SHORT` или `NAME_TOO_LONG`. Правила MUST
применяться там, где имя задаётся, то есть при регистрации.

#### Scenario: Имя короче минимума

- **WHEN** пользователь передаёт имя `Я`
- **THEN** проверка определяет нарушение длины с кодом `NAME_TOO_SHORT`

#### Scenario: Пустое имя

- **WHEN** пользователь передаёт пустое имя или имя из одних пробелов
- **THEN** проверка определяет отсутствие значения с кодом `REQUIRED`

#### Scenario: Имя длиннее максимума

- **WHEN** пользователь передаёт имя длиннее 64 символов
- **THEN** проверка определяет нарушение длины с кодом `NAME_TOO_LONG`

#### Scenario: Имя с крайними пробелами

- **WHEN** пользователь передаёт имя `"  Иван Петров  "`
- **THEN** система сохраняет имя `Иван Петров`

### Requirement: Хеширование исходного пароля

Перед сохранением пользователя сервис аутентификации MUST хешировать исходный пароль
алгоритмом argon2id. Исходная строка MUST при этом не изменяться: преобразованию
подвергается только то, что попадает в хеш. Система MUST NOT хешировать хеш повторно
и MUST NOT сохранять исходный пароль ни в одном поле.

#### Scenario: Хеширование перед сохранением

- **WHEN** пользователь регистрируется с исходным паролем
- **THEN** система хеширует пароль алгоритмом argon2id
- **AND** в операцию сохранения передаётся только хеш

#### Scenario: Исходный пароль не сохраняется

- **WHEN** система сохраняет пользователя
- **THEN** исходный пароль не сохраняется ни в одном поле

#### Scenario: Повторное хеширование не выполняется

- **WHEN** система сохраняет уже готовый хеш пароля
- **THEN** значение поля `password` сохраняется без изменений и повторного хеширования

### Requirement: Проверка пароля

Система MUST проверять исходный пароль сравнением с сохранённым хешем. Исходная строка
MUST передаваться в проверку без преобразований: регистр, пробелы и крайние пробелы
участвуют в сравнении как есть. При несовпадении система MUST сообщить об отказе без
указания причины. Проверка сама по себе MUST NOT создавать и изменять данные
пользователя, включая хеш: замена хеша — отдельный шаг после успешной проверки (см.
«Перехеширование при смене параметров»).

#### Scenario: Верный пароль

- **WHEN** пользователь передаёт пароль, совпадающий с сохранённым хешем
- **THEN** проверка проходит и система продолжает обработку входа

#### Scenario: Неверный пароль

- **WHEN** пользователь передаёт пароль, не совпадающий с сохранённым хешем
- **THEN** проверка не проходит и система отклоняет вход без указания причины

#### Scenario: Проверка без преобразований

- **WHEN** пользователь передаёт пароль `"  Ab1!def  "`
- **THEN** проверка сравнивает именно эту строку с хешем
- **AND** строка с другими крайними пробелами даёт другой результат проверки

### Requirement: Фиктивная проверка пароля

При входе по адресу, для которого нет пользователя, система MUST выполнить проверку
хеша с текущими параметрами хеширования из конфигурации, чтобы время ответа не
отличалось от ответа при неверном пароле.

#### Scenario: Проверка при несуществующем адресе

- **WHEN** пользователь входит с адресом, для которого нет пользователя
- **THEN** система выполняет проверку хеша с текущими параметрами
- **AND** не сообщает, что пользователя не существует

### Requirement: Перехеширование при смене параметров

Параметры хеширования MUST задаваться конфигурацией. Если параметры сохранённого хеша
отличаются от текущих, проверка MUST проходить по сохранённым параметрам, а после
успешного входа система MUST отдельным шагом заменять хеш на новый, созданный с текущими
параметрами. Замена хеша MUST выполняться операцией обновления записи пользователя и
MUST NOT изменять требования `user-account`, где описано только создание записи.
Пароль пользователя при этом MUST NOT меняться.

#### Scenario: Вход со старым хешем

- **GIVEN** сохранённый хеш создан с параметрами, отличными от текущих
- **WHEN** пользователь входит с верным паролем
- **THEN** проверка проходит и вход выполняется

#### Scenario: Хеш обновляется после входа

- **GIVEN** сохранённый хеш создан с параметрами, отличными от текущих
- **WHEN** пользователь успешно входит
- **THEN** система сохраняет новый хеш, созданный с текущими параметрами

#### Scenario: Следующий вход использует новый хеш

- **GIVEN** хеш был заменён при предыдущем входе
- **WHEN** пользователь входит снова с тем же паролем
- **THEN** проверка проходит по новому хешу

### Requirement: Скрытие пароля и хеша

Система MUST NOT включать исходный пароль и хеш пароля в тела ответов, в данные,
передаваемые клиенту, и в журналы. Чтение данных пользователя MUST NOT возвращать поле
`password`.

#### Scenario: Ответ не содержит пароль

- **WHEN** система возвращает данные пользователя клиенту
- **THEN** в ответе отсутствуют исходный пароль и хеш пароля

#### Scenario: Журнал не содержит пароль

- **WHEN** система записывает в журнал результат входа или регистрации
- **THEN** в записи журнала отсутствуют исходный пароль и хеш пароля

### Requirement: Коды нарушений правил

Коды нарушений правил MUST быть одинаковыми у Web и API, чтобы клиент мог проверять
значение до отправки. При отказе регистрации код нарушения MUST передаваться в `fields`.
Коды нарушений MUST NOT использоваться для ошибок аутентификации. Отказы `400`, `429` и
`503` MUST NOT кодироваться как `INVALID_CREDENTIALS`: их коды и статусы задаёт `auth-api`.
Правила применяются на границе API; `user-account` получает проверенное значение и не
меняется.

#### Scenario: Клиентская и серверная проверки совпадают

- **WHEN** Web проверяет значение по тем же правилам, что и API
- **THEN** код нарушения совпадает с кодом, который определила бы серверная проверка

#### Scenario: Ответ регистрации содержит код нарушения

- **WHEN** регистрация отклонена из-за нарушения правил поля
- **THEN** в `fields` для этого поля указан код конкретного нарушения

#### Scenario: Неверные учётные данные без кодов нарушений

- **WHEN** вход отклонён из-за неверных учётных данных
- **THEN** тело ответа содержит единый код `INVALID_CREDENTIALS` и не содержит `fields`
