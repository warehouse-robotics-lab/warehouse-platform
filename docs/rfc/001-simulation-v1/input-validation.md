# Вход, валидация и начальное состояние

[К общему RFC](../001-simulation-v1.md) · [Сквозной пример](delivery-example.md)

Предложение уточняет запуск одного сценария для
[issue #35](https://github.com/warehouse-robotics-lab/warehouse-platform/issues/35).
Основания — [состояние и движение](state-and-movement.md),
[граница ядра и приложения](execution.md),
[ТЗ](../../product-requirements.md) и Accepted
[ADR-002](../../adr/002-ai-development-workflow.md)/[ADR-003](../../adr/003-module-interaction.md).
После обсуждения требования и ожидаемые результаты включаются в общий OpenSpec
`define-simulation-core-v1-behavior` из
[PR #59](https://github.com/warehouse-robotics-lab/warehouse-platform/pull/59).
Этот раздел не заменяет согласование спецификации по ADR-002.

## Вход сценария

`createInitialState(input)` получает доменные данные:

| Данные | Состав |
| --- | --- |
| Контекст | `warehouseId`, `runId` |
| Исходная карта | `mapId`, `mapVersion`, `width`, `height`, `obstacles`, `stations`, `initialRobot` |
| Препятствия | Массив клеток `{ x, y }`, каждая клетка полностью непроходима |
| Станции | Две станции с `id` и `position: { x, y }` |
| Начальный робот | Один `initialRobot` с `id` и `position: { x, y }` |
| Задание | Одно задание с `id`, `pickupStationId`, `deliveryStationId`, отдельно от карты |

Это состав данных, а не новый транспортный конверт. Названия и вложенность
экспортируемых типов согласуются в спецификации. Обязательность `name` станции
и ограничения ID/`mapVersion` остаются вопросом Q2 ниже.

Позиции — клетки, не пиксели: начало сверху слева, `x` вправо, `y` вниз.
Прямоугольное или составное препятствие передаётся набором занятых клеток.
Пустой список препятствий допустим. Задание определяет роли станций ссылками
на их ID; название станции не используется для выбора цели.

Статусы, назначение робота, груз, маршрут и `tick` создаёт ядро.
Исходная карта сохраняет начальную расстановку, текущая позиция принадлежит
отдельному состоянию исполнения. Права пользователя, активный запуск,
повторы команд и транспортные номера проверяются вне ядра.

## Проверки перед созданием состояния

| Область | Правило |
| --- | --- |
| Размеры | Числовые значения `width = 20`, `height = 20` |
| Количество объектов | Один робот, две станции, одно задание; отсутствие обязательного объекта или другое количество недопустимы |
| Координаты | У каждого препятствия, станции и робота обе координаты — конечные целые числа: `0 ≤ x < 20`, `0 ≤ y < 20` |
| Препятствия | Одна клетка встречается в `obstacles` не более одного раза |
| Станции | Различаются по ID и позиции; ни одна не находится на препятствии |
| Начальный робот | Не находится на препятствии или на любой станции |
| Ссылки задания | Обе ссылаются на существующие станции этой карты и различаются между собой |

Числовые строки, дроби, `NaN`, бесконечность и отсутствующая координата
не являются допустимыми координатами. Ядро не округляет их, не переносит
объекты и не удаляет дубли, чтобы сделать сценарий допустимым.

Начальные пересечения проверяются только при создании состояния. Во время
доставки робот может занимать клетку станции. Начальный валидатор не применяется
повторно к каждому состоянию движения; случай поиска «робот уже в цели»
не разрешает начальное размещение на станции.

Достижимость станций при создании состояния не проверяется. Структурно
корректная карта с перекрытым путём допускается к запуску; планирование
маршрута позже может завершить задание с `NO_PATH`.

## Результат проверки и ошибки

При допустимом входе ядро создаёт состояние из следующего раздела.
При нарушении правил возвращается `INVALID_SCENARIO` с указанием поля и причины;
рабочее состояние не создаётся. Входные объекты сохраняют прежние значения.
Ошибка запуска не превращается в `task.error: NO_PATH` и не создаёт событие
`task_failed`: доставка ещё не началась.

В таблице каждый случай независимо изменяет вход из
[сквозного примера](delivery-example.md); остальные данные корректны.
Поля и причины описаны по смыслу, точная форма ответа зависит от Q1.

| Изменение входа | Ожидаемый результат |
| --- | --- |
| `width: 19`, `height: 20` | `INVALID_SCENARIO`: ширина не соответствует размеру сценария |
| `width: "20"` | `INVALID_SCENARIO`: ширина не является числом |
| Нет робота, нет задания либо станций одна/три | `INVALID_SCENARIO`: отсутствует обязательный объект либо нарушено количество |
| Позиция робота `(-1,1)` или `(20,1)` | `INVALID_SCENARIO`: позиция за границей карты |
| Позиция станции `(4,20)` | `INVALID_SCENARIO`: позиция за границей карты |
| Координата препятствия `x: 2.5`, `x: "2"`, `NaN` или бесконечность | `INVALID_SCENARIO`: координата не является конечным целым числом |
| У клетки отсутствует `y` | `INVALID_SCENARIO`: отсутствует обязательная координата |
| Препятствие `(2,1)` добавлено повторно | `INVALID_SCENARIO`: повторяющаяся клетка препятствия |
| Робот перемещён в `(2,1)` | `INVALID_SCENARIO`: робот на препятствии |
| Станция получения перемещена в `(2,1)` | `INVALID_SCENARIO`: станция на препятствии |
| Обе станции размещены в `(4,1)` | `INVALID_SCENARIO`: совпадают позиции станций |
| Обе станции имеют `id: pickup-1`, обе ссылки задания равны `pickup-1` | `INVALID_SCENARIO`: повтор ID станций и одинаковые ссылки; выбор/порядок диагностик определяется Q1 |
| Робот размещён в `(4,1)` либо `(4,3)` | `INVALID_SCENARIO`: робот изначально на станции |
| Любая из ссылок задания заменена на `missing-station` | `INVALID_SCENARIO`: указанной станции нет на карте |
| Обе ссылки задания равны `pickup-1`, станции не изменены | `INVALID_SCENARIO`: получение и доставка ссылаются на одну станцию |
| Робот перемещён в свободную `(0,0)` либо `(19,19)` | Создаётся начальное состояние: крайние координаты допустимы |
| `obstacles: []` | Создаётся начальное состояние: препятствия необязательны |
| Препятствия заменены на `(3,1)`, `(5,1)`, `(4,0)`, `(4,2)` | Создаётся начальное состояние; недостижимость получения выявляется при планировании |
| Препятствия заменены на `(3,3)`, `(5,3)`, `(4,2)`, `(4,4)` | Создаётся начальное состояние; недостижимость назначения выявляется после получения груза |

Проверка сценария не ограничивает отдельную функцию BFS картами 20×20:
её более общий вход описан в [разделе поиска](state-and-movement.md).

## Начальное состояние

Для допустимого входа сквозного примера `createInitialState` создаёт:

| Часть | Ожидаемые значения |
| --- | --- |
| Контекст | `warehouseId: warehouse-1`, `runId: run-1` |
| Карта | `mapId: map-1`, `mapVersion: 1`, размеры и объекты из входа |
| Запуск | `status: running`, `tick: 0` |
| Робот | `id: robot-1`, `position: (0,1)`, `status: idle`, `carryingTaskId: null` |
| Задание | `id: task-1`, `pickupStationId: pickup-1`, `deliveryStationId: delivery-1` |
| Исполнение задания | `assignedRobotId: null`, `status: queued`, `phase: unassigned`, `error: null` |
| Маршрут | `route: []` |

Общее правило: идентификаторы, карта и ссылки задания сохраняются из входа,
текущая позиция робота совпадает с `initialRobot.position`. Остальные поля
инициализируются значениями таблицы. Ни один входной объект не изменяется.
Повторный вызов с теми же данными даёт равное по значениям состояние и не требует
часов, сети или памяти о предыдущих вызовах.

Создание состояния не назначает задание, не ищет путь и не формирует события
доставки. Пустой `route` здесь означает, что планирование ещё не выполнялось.
Первый `step` назначает робота и формирует `task_assigned` по существующей
таблице переходов. Хранение результата, ответ на команду запуска и публикация
снимка остаются в приложении по ADR-003.

## Вопросы для согласования

В design change из PR #59 уже выделены вопросы, которые этот раздел не закрывает:

- **Q1 — результат валидации.** Как различаются успех и ошибка создания;
  возвращается одна ошибка или список; как определяется порядок проверок,
  представляются путь `field` и значение `reason`.
- **Q2 — ID и метаданные.** Тип, допустимые значения и область уникальности
  идентификаторов, ограничения `mapVersion`, обязательность `name` станции.
- **Q3 — вход последующих операций.** Должны ли `step`/`applyControl` диагностировать
  произвольное некорректное состояние или получают только состояния допустимых
  операций ядра. Таблица начальных значений не решает этот вопрос.

Для ревью нужно проверить правила начальных пересечений, допустимые границы,
ссылки на станции, отделение недостижимости от ошибок входа и соответствие
начального состояния сквозному примеру. После согласования Q1–Q2 примеры ошибок
нужно выразить точными ожидаемыми результатами в OpenSpec. Полная модель
последующих состояний зависит также от Q3. Исполняемые тесты готовятся отдельно
после согласования спецификации по ADR-002.
