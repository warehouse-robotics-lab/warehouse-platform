# Сквозной пример доставки

[К общему RFC](../001-simulation-v1.md) · [Состояние и движение](state-and-movement.md)

Пример показывает входные данные, начальное состояние и результаты последовательных
шагов. Назначение, поиск и операция с грузом выполняются отдельными шагами;
маршрут к назначению строится после получения груза. Значения полей и данные событий
предлагаются для совместного согласования, а не описывают готовую реализацию.

## Входные данные

| Данные | Поля и значения |
| --- | --- |
| Склад | `warehouseId: warehouse-1` |
| Запуск | `runId: run-1` |
| Карта | `mapId: map-1`, `mapVersion: 1`, `width: 20`, `height: 20` |
| Препятствия | `obstacles`: клетки `(2,1)` и `(2,2)` |
| Станция получения | `id: pickup-1`, `name: Приёмка`, `position: (4,1)` |
| Станция назначения | `id: delivery-1`, `name: Выдача`, `position: (4,3)` |
| Начальная расстановка робота | `initialRobot`: `id: robot-1`, `position: (0,1)` |
| Задание | `id: task-1`, `pickupStationId: pickup-1`, `deliveryStationId: delivery-1` |

Препятствия, станции и начальная расстановка входят в исходную карту.
Ниже показан её фрагмент; остальные клетки карты 20×20 свободны:

```text
    0123456
0   .......
1   R.#.A..
2   ..#....
3   ....B..
4   .......
```

`R` — робот, `A` — получение, `B` — назначение, `#` — препятствия.
Исходная карта и `initialRobot` не меняются при движении.

При порядке соседей вправо, вниз, влево, вверх получаем следующие маршруты.
Текущая клетка в `route` не входит.

| Участок | Следующие клетки `route` | Перемещений |
| --- | --- | --- |
| К получению | `(1,1) → (1,0) → (2,0) → (3,0) → (4,0) → (4,1)` | 6 |
| К назначению | `(4,2) → (4,3)` | 2 |

Второй маршрут приведён для описания всей доставки; он рассчитывается только
после получения груза.

## Начальное состояние

После успешной проверки сценария ожидаются следующие значения:

| Часть состояния | Поля и значения |
| --- | --- |
| Склад, запуск и карта | Идентификаторы и карта из входных данных |
| Запуск | `status: running`, `tick: 0` |
| Робот | `id: robot-1`, `position: (0,1)`, `status: idle`, `carryingTaskId: null` |
| Задание | `id: task-1`, ссылки на станции из входных данных, `assignedRobotId: null` |
| Исполнение задания | `status: queued`, `phase: unassigned`, `error: null` |
| Маршрут | `route: []` |

Здесь `route` относится к единственному роботу. При нескольких роботах привязку
маршрутов нужно определить в общей модели состояния.

## Последовательные результаты шагов

Первый вызов `step` получает начальное состояние. Каждый следующий вызов получает
`nextState` предыдущего принятого шага. Это позволяет проверить последовательность
без запуска таймера, Nest, очередей или БД.

В таблице указаны все изменяемые данные каждого `nextState` и возвращаемые события:

- `tick` равен номеру шага.
- Карта, идентификаторы и ссылки на станции сохраняются из входных данных.
- Статус запуска остаётся `running`, ошибка задания — `error: null`.
- С первого шага `assignedRobotId: robot-1` сохраняется и после завершения задания.
- `—` в колонке груза означает `carryingTaskId: null`, иначе указан ID задания.
- `—` в колонке событий означает пустой список `events`; данные событий приведены ниже.

| Шаг / tick | Позиция | Робот | Груз | Статус задания | phase | Оставшийся route | Событие |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | `(0,1)` | `busy` | — | `in_progress` | `plan_pickup` | `[]` | `task_assigned` |
| 2 | `(0,1)` | `busy` | — | `in_progress` | `to_pickup` | `(1,1) → (1,0) → (2,0) → (3,0) → (4,0) → (4,1)` | — |
| 3 | `(1,1)` | `busy` | — | `in_progress` | `to_pickup` | `(1,0) → (2,0) → (3,0) → (4,0) → (4,1)` | — |
| 4 | `(1,0)` | `busy` | — | `in_progress` | `to_pickup` | `(2,0) → (3,0) → (4,0) → (4,1)` | — |
| 5 | `(2,0)` | `busy` | — | `in_progress` | `to_pickup` | `(3,0) → (4,0) → (4,1)` | — |
| 6 | `(3,0)` | `busy` | — | `in_progress` | `to_pickup` | `(4,0) → (4,1)` | — |
| 7 | `(4,0)` | `busy` | — | `in_progress` | `to_pickup` | `(4,1)` | — |
| 8 | `(4,1)` | `busy` | — | `in_progress` | `to_pickup` | `[]` | — |
| 9 | `(4,1)` | `busy` | `task-1` | `in_progress` | `plan_delivery` | `[]` | `cargo_picked_up` |
| 10 | `(4,1)` | `busy` | `task-1` | `in_progress` | `to_delivery` | `(4,2) → (4,3)` | — |
| 11 | `(4,2)` | `busy` | `task-1` | `in_progress` | `to_delivery` | `(4,3)` | — |
| 12 | `(4,3)` | `busy` | `task-1` | `in_progress` | `to_delivery` | `[]` | — |
| 13 | `(4,3)` | `idle` | — | `completed` | `done` | `[]` | `task_completed` |

В приложении результаты шагов 1, 9 и 13 сначала ожидают подтверждения истории:
до этого они не публикуются и следующий шаг не вызывается. Порядок принятия
состояния описан в [исполнении и командах](execution.md).

После принятия шага 13 следующий `step` возвращает прежнее состояние без событий,
`tick` остаётся 13. Запуск активен до сброса; робот остаётся на станции назначения.

## Доменные данные событий

Общие поля каждого события в этом примере:

| Поле | Значение |
| --- | --- |
| `warehouseId` | `warehouse-1` |
| `runId` | `run-1` |
| `taskId` | `task-1` |
| `robotId` | `robot-1` |

Дополнительные данные зависят от типа события:

| Шаг | type | Остальные поля |
| --- | --- | --- |
| 1 | `task_assigned` | `pickupStationId: pickup-1`, `deliveryStationId: delivery-1`, `position: (0,1)` |
| 9 | `cargo_picked_up` | `stationId: pickup-1`, `position: (4,1)` |
| 13 | `task_completed` | `stationId: delivery-1`, `position: (4,3)` |

Это доменные данные ядра. Идентификатор события, даты, номера сообщений и процесса
добавляет приложение по ADR-003. Они не входят в результат расчёта ядра.

## Вариант с ошибкой пути

В отдельном варианте заменяем препятствия исходной карты клетками `(3,3)`, `(5,3)`,
`(4,2)`, `(4,4)`. Они окружают станцию назначения `(4,3)`; остальные данные прежние.
До получения теперь четыре прямых перемещения: `(1,1) → (2,1) → (3,1) → (4,1)`.

| Шаги | Результат |
| --- | --- |
| 1 | Робот назначен на задание |
| 2 | Построен путь к получению |
| 3–6 | Робот проходит четыре клетки до станции получения |
| 7 | Груз получен, этап `plan_delivery` |
| 8 | Поиск к назначению возвращает `kind: unreachable`; рассчитан переход ошибки |

Ожидаемое состояние после принятия шага 8:

| Часть состояния | Поля и значения |
| --- | --- |
| Склад, запуск и карта | Прежние ID и карта этого варианта |
| Запуск | `status: running`, `tick: 8` |
| Робот | `id: robot-1`, `position: (4,1)`, `status: waiting`, `carryingTaskId: task-1` |
| Задание | `id: task-1`, прежние ссылки на станции, `assignedRobotId: robot-1` |
| Исполнение задания | `status: failed`, `phase: failed`, `error` с полями ниже |
| Маршрут | `route: []` |

Поля ошибки `task.error`:

| Поле | Значение |
| --- | --- |
| `code` | `NO_PATH` |
| `phase` | `delivery` |
| `from` | `(4,1)` |
| `goal` | `(4,3)` |
| `targetStationId` | `delivery-1` |

Шаг возвращает одно событие `type: task_failed`: общие идентификаторы из раздела
событий, `position: (4,1)` и `error` с теми же полями, что у `task.error`.
Переход ожидает подтверждения истории по общим правилам.

После принятия повторный шаг ничего не меняет и не возвращает событий.
`waiting` здесь означает остановку с грузом после ошибки, а не повторную попытку;
причину клиент получает из `task.error`. Продолжение запуска не исправляет `failed`.

## Граничные случаи и ожидаемый результат


Все примеры используют карту 20×20. Если препятствия не перечислены, их нет.

| Случай | Данные | Ожидаемый результат |
| --- | --- | --- |
| Прямой путь | Из `(0,1)` в `(4,1)` | `found`, клетки `(1,1)…(4,1)`, четыре перемещения |
| Обход | Из `(0,1)` в `(4,1)`, препятствия `(2,1)`, `(2,2)` | Кратчайший путь из шести перемещений через строку `y = 0`; полный маршрут в примере |
| Нет пути к получению | Получение `(4,1)` окружено `(3,1)`, `(5,1)`, `(4,0)`, `(4,2)`; робот `(0,1)` | `unreachable`; `NO_PATH`, этап `pickup`; робот без груза, задание `failed` |
| Нет пути к назначению | Получение `(4,1)`, назначение `(4,3)` окружено `(3,3)`, `(5,3)`, `(4,2)`, `(4,4)`; робот `(0,1)` | После получения груза: `NO_PATH`, этап `delivery`, робот с грузом `waiting` |
| Робот уже в цели | Поиск из `(4,1)` в `(4,1)` | `found`, `route: []`; операция с грузом — отдельный шаг нужного этапа |
| Робот изначально на назначении | Отдельный тест функции доставки с позицией в назначении | Получение груза не пропускается; такой старт полного сценария отклоняется предложенной валидацией начальной расстановки |
| Переход по диагонали | Из `(0,0)` в `(1,1)`; препятствия `(1,0)`, `(0,1)` | `unreachable`, диагонального перехода нет |
| Одинаковые станции задания | Одинаковый `pickupStationId` и `deliveryStationId` | `INVALID_SCENARIO`, не нулевой путь доставки |
| Нет станции или некорректная координата | Несуществующий ID, дробь, выход за границу | Ошибка входа; поиск не превращает её в `NO_PATH` |
