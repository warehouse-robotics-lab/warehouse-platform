# Часть 3 — Исполнение и команды

[К основному предложению](../001-simulation-v1.md)

## Исполнитель склада

Приложение хранит принятое состояние `committedState`, ожидающий переход
`pendingTransition`, буфер команд, результаты обработанных команд и счётчики
сообщений. Подтверждения, команды и шаги меняют состояние последовательно.

Предлагаемый интервал шага — 500 мс после завершения предыдущего. На паузе,
при ожидании истории и без работы тики не накапливаются. Запоздалый сигнал
после паузы или сброса не выполняет шаг. Ожидание одного склада не мешает другим.

## История и снимки

1. Шаг без события сразу принимается; приложение сохраняет полный снимок
   в Redis и публикует через Pub/Sub.
2. Шаг с событием сохраняется как кандидат. Приложение отправляет событие
   истории, останавливает шаги склада и продолжает принимать сообщения.
3. Подтверждение API принимает кандидат и разрешает его публикацию.
   До этого клиент видит последнее принятое состояние.
4. Повтор события использует прежний идентификатор; повтор подтверждения
   не применяет переход снова. Отказ или предельный срок ожидания закрывает
   исполнитель по [ADR-003](../../adr/003-module-interaction.md).

Пауза, продолжение и сброс ждут завершения ожидающего перехода истории.
Само подтверждение нельзя ставить за ожидающей его командой: обработчик
сохраняет состояние ожидания и возвращает управление, не блокируясь на сети.
Идентификаторы, номера и даты сообщений добавляет приложение, а не ядро.

Полный снимок содержит идентификаторы склада, запуска, процесса и карты,
версию карты, версию снимка, `tick`, статус запуска, карту, робота, задание
и маршрут. Кандидат и внутренние буферы не публикуются. Версия снимка растёт
при изменении состояния, в том числе при паузе; повторная публикация сохраняет версию.

Снимок обновляется и без движения, включая паузу и ожидание истории, чаще его TTL.
Потерянное обновление заменяется следующим полным снимком. После перезапуска
состояние исполнения не восстанавливается; история сохраняется по ADR-003.

## Команды

| Команда | Поведение |
| --- | --- |
| `start` | Принимает идентификаторы запуска, карту с начальным роботом и задание; создаёт `running`, `tick = 0` |
| `pause` | Переводит в `paused`, сохраняет позицию, груз, маршрут и этап |
| `resume` | Возвращает `running`, без компенсации времени паузы |
| `reset` | После подтверждения владельцем в UI завершает запуск; после сохранения результата API показывает исходную карту |

Повторные пауза и продолжение в соответствующем состоянии успешны без изменений.
Новый `start` при активном запуске даёт `RUN_ALREADY_ACTIVE`. Чужой `runId`
отклоняется, неизвестная команда даёт `UNSUPPORTED_COMMAND`. Повторы одной команды
возвращают прежний результат; порядок, пропуски номеров и регистрация процесса
следуют ADR-003. Принятие в очередь ещё не означает выполнения.

При сбросе таймер отменяется и снимок удаляется. Завершённая доставка остаётся
в истории; незавершённое задание предлагается отмечать как прерванное сбросом,
передавая его исход с результатом команды в API. Второе событие `task_failed`
при этом не создаётся. Результат команды сохраняется на окно повторов,
даже после удаления рабочего состояния. Новый запуск получает новый `runId`.

До инфраструктурной реализации нужно согласовать с API исход задания при сбросе,
конверты сообщений, TTL, сроки ожидания, повторов и хранения результатов.
Общие данные не зависят от выбора ts-rest или tRPC.
